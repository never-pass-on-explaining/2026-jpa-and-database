LAZY 프록시를 루프에서 하나씩 초기화하기 때문입니다. 같은 팀은 1차 캐시에서 꺼내므로 실제 횟수는 서로 다른 팀 수만큼입니다. 팀이 몇 개 없는 로컬에서는 안 보이다가 운영에서 터지는 이유입니다.

해결 방법

방법장점단점
@EntityGraph한 줄로 끝복잡한 조건엔 한계
fetch join쿼리 1번countQuery 분리 필요
DTO 직접 조회필요한 컬럼만, 가장 가벼움변경 감지 불가, 재사용성 낮음
batch_fetch_size코드 변경 없음N번을 1번으로 묶을 뿐, 0은 아님
// MemberRepository.java
public interface MemberRepository extends JpaRepository<Member, Long> {

    // ToOne이라 페이징과 같이 써도 안전
    @EntityGraph(attributePaths = "team")
    Page<Member> findAll(Pageable pageable);

    // fetch join은 count 쿼리에 쓸 수 없으므로 분리
    @Query(value = "select m from Member m join fetch m.team",
           countQuery = "select count(m) from Member m")
    Page<Member> findAllWithTeam(Pageable pageable);
}
// MemberRepositoryCustomImpl.java
public class MemberRepositoryCustomImpl implements MemberRepositoryCustom {

    public List<MemberDto> findMembers(Pageable pageable) {
        return queryFactory
                .select(new QMemberDto(member.name, team.name))
                .from(member)
                .join(member.team, team)
                .offset(pageable.getOffset())
                .limit(pageable.getPageSize())
                .fetch();
    }
}

// application.yml
// spring.jpa.properties.hibernate.default_batch_fetch_size: 100
// → where team_id in (?, ?, ...) 한 번으로 묶어서 조회

batch_fetch_size는 전역으로 깔아두고(안전망), 핵심 조회만 fetch join이나 DTO 조회로 명시적으로 최적화한다.

2)

컬렉션 fetch join과 페이징

1)에서 회원은 팀을 하나만 가지니까, 회원 20명을 팀과 fetch join해도 결과는 딱 20줄이었습니다. 그래서 페이징이 문제없이 됐죠.

이번엔 반대입니다. 주문 하나에는 주문상품이 여러 개 있습니다. 주문 목록에 상품까지 한 번에 보여주려고 같은 방식으로 fetch join을 걸면 함정에 빠집니다.

// OrderRepositoryCustomImpl.java
public class OrderRepositoryCustomImpl implements OrderRepositoryCustom {

    public List<Order> findOrders() {
        return queryFactory
                .selectFrom(order)
                .join(order.orderItems, orderItem).fetchJoin()   // OneToMany
                .offset(0)
                .limit(20)
                .fetch();
        // 로컬: 정상, 20건 반환
        // 운영: OOM
    }
}
WARN HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory

조인하면 줄이 불어난다

주문 1번에 상품이 3개면, 조인 결과에서 주문 1번은 3줄로 나옵니다. 결과가 주문 단위가 아니라 상품 단위로 늘어나는 거죠.

주문상품
1번키보드
1번마우스
1번모니터
2번노트북
……

이 상태에서 DB에 limit 20을 걸면 주문 20개가 아니라 줄 20개가 잘립니다. 주문 4~5개에서 끝나고, 마지막 주문은 상품이 몇 개 잘린 채로 올 수도 있습니다.

그래서 Hibernate는 메모리에서 자른다

Hibernate는 데이터가 망가지는 걸 막으려고 SQL에 limit을 안 붙입니다. 대신 전체를 다 가져온 다음 자바 메모리에서 주문 20개를 골라냅니다. 결과는 정확해서 로컬 테스트에선 아무 문제가 없어 보입니다.

하지만 운영에 주문이 100만 건이면, 화면에 20개 보여주려고 100만 건과 그 상품 전부를 메모리에 올립니다. 그러다 서버가 터집니다. 에러도 없이 위의 경고 한 줄만 남아서 알아채기 어렵습니다.

해결의 핵심은 주문만 먼저 20개 정확히 가져오고, 그 20개의 상품은 따로 한 번에 가져오는 것입니다.

해결 방법

// OrderRepositoryCustomImpl.java
public class OrderRepositoryCustomImpl implements OrderRepositoryCustom {

    public List<Order> findOrders(Pageable pageable) {
        return queryFactory
                .selectFrom(order)
                .join(order.member, member).fetchJoin()   // ManyToOne: 행이 안 늘어남
                .offset(pageable.getOffset())
                .limit(pageable.getPageSize())            // SQL limit 정상 적용
                .fetch();
    }
}

// 이후 서비스에서 orderItems 접근 시 batch_fetch_size에 의해
// select ... from order_item where order_id in (?, ... 20개)
// → 주문 1번 + 상품 1번 = 총 2번
// OrderRepositoryCustomImpl.java
public class OrderRepositoryCustomImpl implements OrderRepositoryCustom {

    public List<Order> findOrdersWithItems(Pageable pageable) {
        // 1단계: 주문 id만 페이징 (행이 안 늘어나서 limit 정상 적용)
        List<Long> ids = queryFactory
                .select(order.id).from(order)
                .orderBy(order.orderDate.desc())
                .offset(pageable.getOffset())
                .limit(pageable.getPageSize())
                .fetch();

        // 2단계: 그 id들만 컬렉션 fetch join
        return queryFactory
                .selectFrom(order)
                .join(order.orderItems, orderItem).fetchJoin()
                .where(order.id.in(ids))
                .orderBy(order.orderDate.desc())
                .fetch();
    }
}
# application.yml
spring:
  jpa:
    properties:
      hibernate:
        query:
          fail_on_pagination_over_collection_fetch: true

하나짜리 연관을 fetch join하면 줄 수가 그대로라 페이징이 되고, 여러 개짜리 연관(컬렉션)을 fetch join하면 줄이 불어나서 DB 페이징이 불가능해진다.

3)

깊은 페이징 문제

select * from orders
order by order_date desc
limit 20 offset 1000000;
page 1 → 5 ms page 50,000 → 3,200 ms rows examined 1,000,020 / returned 20

offset은 건너뛰기가 아니라 읽고 버리기입니다. 1,000,020행을 읽은 뒤 앞의 100만 행을 버립니다. 뒤 페이지일수록 선형으로 느려집니다.

Slice로 바꿔도 해결되지 않습니다. Slice가 없애는 건 count 쿼리뿐이고, 목록 쿼리는 여전히 offset입니다.

해결: 키셋(no-offset) 페이징

offset이 "300페이지 펴줘" 하면 1페이지부터 넘겨서 찾아가는 방식이라면, 키셋은 책갈피를 꽂아두고 거기서부터 읽는 방식입니다.

첫 요청은 조건 없이 최신순 20개를 가져옵니다. 클라이언트는 그중 마지막 주문의 날짜와 id를 책갈피로 기억해 두었다가, 다음 요청 때 같이 보냅니다. 서버는 "그보다 오래된 주문"에서 다시 20개를 가져옵니다. 날짜·id 인덱스가 있으면 책갈피 위치를 바로 찾아가므로 몇 페이지든 속도가 같습니다.

// OrderRepositoryCustomImpl.java
public class OrderRepositoryCustomImpl implements OrderRepositoryCustom {

    // lastDate, lastId = 클라이언트가 마지막으로 받은 행의 값
    public List<OrderDto> findNext(LocalDateTime lastDate, Long lastId, int size) {
        return queryFactory
                .select(new QOrderDto(order.id, order.status, order.orderDate))
                .from(order)
                .where(cursor(lastDate, lastId))
                .orderBy(order.orderDate.desc(), order.id.desc())   // id = tie-breaker
                .limit(size)
                .fetch();
    }

    private BooleanExpression cursor(LocalDateTime lastDate, Long lastId) {
        if (lastDate == null || lastId == null) return null;   // 첫 페이지
        return order.orderDate.lt(lastDate)
                .or(order.orderDate.eq(lastDate).and(order.id.lt(lastId)));
    }
}

// create index idx_orders_date_id on orders (order_date desc, id desc);

37페이지로 점프가능불가능
조회 중 데이터 추가중복·누락안정적
어울리는 UI페이지 번호더보기, 무한 스크롤

조건이 두 줄인 이유는 날짜가 같은 주문 때문입니다. 10시 정각 주문이 3개인데 그중 하나까지만 봤다면, "10시보다 이전"만 걸었을 때 나머지 2개를 건너뜁니다. 그래서 "날짜가 같으면 id가 더 작은 것"까지 조건에 넣고, 정렬에도 id를 보조 기준(tie-breaker)으로 붙입니다.

페이지 번호 UI를 꼭 유지해야 한다면

  • 커버링 인덱스로 id만 먼저 찾기. 100만 행을 읽는 건 같지만 인덱스만 읽어서 훨씬 빠릅니다.
  • 페이지 수 제한. 최대 N페이지까지만 노출합니다. 5만 페이지를 넘기는 건 대부분 크롤러입니다.
  • 검색 조건 강제. 기간 필터를 필수로 받아 범위 자체를 줄입니다.
select o.*
from orders o
join (
    select id from orders
    order by order_date desc, id desc
    limit 20 offset 1000000      -- 인덱스만 읽음
) t on o.id = t.id;              -- 테이블 접근은 20행뿐

무한 스크롤은 키셋, 페이지 번호가 필요하면 커버링 인덱스와 페이지 제한.

코드 리뷰할 때 볼 것

  • 목록 조회 후 map이나 루프에서 연관 엔티티에 접근하는가
  • 컬렉션 fetch join에 페이징이 붙어 있는가
  • fetch join 쿼리에 countQuery가 분리되어 있는가
  • 정렬에 유일 컬럼이 포함되어 있는가
  • 무한 스크롤인데 offset을 쓰고 있지 않은가
