# 3장. 영속성 관리 (Persistence Management)


## 3.1 엔터티 매니저 팩토리와 엔터티 매니저

| 구분 | 엔터티 매니저 팩토리 (`EntityManagerFactory`) | 엔터티 매니저 (`EntityManager`) |
| :--- | :--- | :--- |
| **생성 비용** | 매우 큼 (생성 시 데이터베이스 커넥션 풀 생성 및 준비) | 매우 적음 |
| **스레드 안전성** | **Thread-safe** (여러 스레드가 동시에 접근해도 안전함) | **Non Thread-safe** (스레드 간 절대 공유 금지) |
| **생성 및 수명** | 애플리케이션 전체에서 **단 하나만 생성**하여 공유 | 고객 요청/트랜잭션 단위마다 생성하고 사용 후 폐기 |
| **DB 커넥션** | 애플리케이션 스타트업 시점에 생성 | 실제 데이터베이스 연결이 필요한 시점(트랜잭션 시작 등)에 커넥션 획득 |

> 💡 **참고**: 스프링 데이터 JPA 환경에서는 `@PersistenceContext` 또는 `@Autowired`를 통해 `EntityManager`를 주입받아 사용할 때, 실제로는 프록시 `EntityManager`가 주입되어 스레드별로 가상/독립적인 영속성 컨텍스트를 생성하므로 안전하게 공유할 수 있습니다.

---

## 3.2 영속성 컨텍스트란?

* **영속성 컨텍스트(Persistence Context)**: *"엔터티를 영구 저장하는 환경"*이라는 뜻입니다.
* 논리적인 개념으로 눈에 직접 보이지 않으며, **엔터티 매니저를 통해 영속성 컨텍스트에 접근하고 관리**합니다.
* `EntityManager.persist(entity)`를 실행하면 엔터티를 DB에 직접 바로 저장하는 것이 아니라, **영속성 컨텍스트에 저장**합니다.
* 엔터티 매니저와 영속성 컨텍스트는 1:1 관계(기본)이거나, J2EE/Spring 환경에서는 N:1(여러 엔터티 매니저가 동일한 영속성 컨텍스트 참조) 구조를 가질 수 있습니다.

---

## 3.3 엔터티의 생명주기 (Entity Lifecycle)

엔터티는 4가지 생명주기 상태를 가집니다.

```
       [ 비영속 (New/Transient) ]
                  │
                  │ persist()
                  ▼
       [  영속 (Managed)  ] ─── remove() ───► [ 삭제 (Removed) ]
             │         ▲
  detach()   │         │ merge()
  clear()    │         │
  close()    ▼         │
       [ 준영속 (Detached) ]
```

### 1. 비영속 (New / Transient)
* 영속성 컨텍스트 및 데이터베이스와 **전혀 관계가 없는** 순수한 객체 상태입니다.
* `persist()` 호출 전의 상태입니다.
```java
// 순수한 객체 상태 (비영속)
Member member = new Member();
member.setId("member1");
member.setUsername("회원1");
```

### 2. 영속 (Managed)
* 영속성 컨텍스트에 의해 **관리되는 상태**입니다.
* `em.persist(entity)` 또는 DB에서 조회해온 엔터티가 이 상태에 해당합니다.
```java
// 객체를 영속성 컨텍스트에 저장 (영속)
em.persist(member);
```

### 3. 준영속 (Detached)
* 영속성 컨텍스트에 저장되었다가 **분리(detached)된 상태**입니다.
* 영속성 컨텍스트가 제공하는 모든 기능(1차 캐시, 변경 감지 등)이 작동하지 않습니다.
```java
// 특정 엔터티만 지정하여 준영속 상태로 전환
em.detach(member);
```

### 4. 삭제 (Removed)
* 엔터티를 영속성 컨텍스트와 데이터베이스에서 **삭제하기로 표시한 상태**입니다.
```java
// 객체를 영속성 컨텍스트 및 DB에서 삭제
em.remove(member);
```

## 3.4 영속성 컨텍스트의 특징 및 이점

### 1. 영속성 컨텍스트와 식별자 값
* 영속성 컨텍스트는 엔터티를 식별자 값(`@Id`로 매핑된 PK)으로 구분합니다.
* 따라서 **영속 상태의 엔터티는 반드시 식별자 값이 존재**해야 합니다. (없으면 예외 발생)

### 2. 영속성 컨텍스트가 엔터티를 관리할 때의 5가지 핵심 이점

#### ① 1차 캐시 (First Level Cache)
* 영속성 컨텍스트 내부에 존재하는 내장 캐시입니다. Map 형태로 저장되며 Key는 `@Id` 값, Value는 엔터티 객체입니다.
* `em.find()` 호출 시 먼저 1차 캐시에서 조회를 수행합니다. 존재하면 DB 조회 없이 즉시 반환합니다.
* 1차 캐시에 없으면 DB를 조회한 후 1차 캐시에 저장하고 영속 상태로 반환합니다.

#### ② 영속 엔터티의 동일성(Identity) 보장
* REPEATABLE READ 등급의 트랜잭션 격리 수준을 데이터베이스가 아닌 애플리케이션 차원에서 제공합니다.
```java
Member a = em.find(Member.class, "member1");
Member b = em.find(Member.class, "member1");

System.out.println(a == b); // true (주소값이 완전히 동일함)
```

#### ③ 트랜잭션을 지원하는 쓰기 지연 (Transactional Write-Behind)
* `em.persist(member)`를 호출해도 DB에 INSERT SQL을 즉시 보내지 않습니다.
* 쓰기 지연 SQL 저장소(Write-Behind SQL Store)에 SQL을 모아두었다가, **트랜잭션을 커밋하는 순간(Flush)** 모아둔 쿼리를 데이터베이스에 일괄 전송(Batch)합니다.

#### ④ 변경 감지 (Dirty Checking)
* 엔터티의 수정 내용을 자동으로 감지하여 UPDATE 쿼리를 생성합니다.
* **원리**: JPA는 엔터티를 영속성 컨텍스트에 처음 올릴 때의 상태를 **스냅샷(Snapshot)**으로 만들어 둡니다. 플러시 시점에 엔터티와 스냅샷을 비교하여 변경된 내용을 찾습니다.
* 따로 `em.update()`나 `em.save()` 같은 메소드를 호출할 필요가 없습니다.

#### ⑤ 지연 로딩 (Lazy Loading)
* 연관된 객체를 실제 사용하는 시점까지 데이터베이스 조회를 미루는 기술입니다. 프록시 객체를 활용하여 구현됩니다.

## 3.5 플러시 (Flush)

플러시는 **영속성 컨텍스트의 변경 내용을 데이터베이스에 동기화/반영하는 작업**입니다. (영속성 컨텍스트를 비우는 것이 아닙니다.)

### 플러시 동작 과정
1. **변경 감지(Dirty Checking)** 동작: 영속성 컨텍스트 내의 모든 엔터티와 스냅샷을 비교하여 수정된 엔터티를 찾음.
2. 수정된 엔터티가 있으면 수정 쿼리(UPDATE)를 생성하여 쓰기 지연 SQL 저장소에 등록.
3. 쓰기 지연 SQL 저장소의 쿼리들(INSERT, UPDATE, DELETE)을 **데이터베이스에 전송**.

### 영속성 컨텍스트를 플러시하는 3가지 방법
1. **`em.flush()` 직접 호출**: 테스트나 강제 동기화가 필요한 특수한 경우 사용.
2. **트랜잭션 커밋 시 자동 호출**: 트랜잭션을 커밋하기 전에 JPA가 자동으로 플러시를 수행함.
3. **JPQL 쿼리 실행 시 자동 호출**: JPQL은 SQL로 변환되어 DB에서 직접 조회하므로, 이전까지 영속성 컨텍스트에만 반영되어 있던 변경 사항들이 DB에 미리 반영되어야 하기 때문.

### 플러시 모드 옵션 (`FlushModeType`)
* `FlushModeType.AUTO` (기본값): 커밋이나 JPQL 실행 시 플러시 수행.
* `FlushModeType.COMMIT`: 커밋할 때만 플러시 수행 (성능 최적화가 필요한 특수한 상황에서 활용).

## 3.6 준영속 (Detached)

영속 상태의 엔터티가 영속성 컨텍스트에서 **분리된 상태**를 의미합니다. 영속성 컨텍스트가 제공하는 기능(1차 캐시, 변경 감지, 지연 로딩 등)을 더 이상 이용할 수 없습니다.

### 준영속 상태로 전환하는 방법
* **`em.detach(entity)`**: 특정 엔터티만 지정하여 준영속 상태로 전환.
* **`em.clear()`**: 영속성 컨텍스트를 완전히 초기화 (모든 엔터티를 준영속 상태로 만듦).
* **`em.close()`**: 영속성 컨텍스트를 종료.

### 준영속 상태의 특징
* 거의 비영속 상태에 가깝습니다.
* **식별자 값을 보유**하고 있습니다. (한 번 영속 상태였으므로 반드시 `@Id` 값을 가지고 있음)
* 지연 로딩을 시도할 때 `LazyInitializationException` 예외가 발생합니다.

### 병합: `merge()`
* 준영속 상태의 엔터티를 다시 **영속 상태로 변경**할 때 사용합니다.
* **동작 방식**: 준영속 엔터티의 식별자 값으로 1차 캐시(없으면 DB)에서 조회한 후, 준영속 엔터티의 모든 값을 조회한 영속 엔터티에 덮어씁니다. 새로운 영속 엔터티를 반환합니다.
> ⚠️ **주의**: `merge()`는 모든 필드를 교체하므로, 값이 없는 필드는 `null`로 덮어써질 위험이 있습니다. 실무에서는 변경 감지(Dirty Checking)를 사용하는 것이 권장됩니다.
