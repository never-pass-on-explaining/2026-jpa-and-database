# Chapter 3. 영속성 관리

## 3.1 엔티티 매니저 팩토리와 엔티티 매니저

- 엔티티 매니저 팩토리: 엔티티 매니저를 생성하는 객체
    - 생성비용이 매우 커서 애플리케이션 전체에서 하나만 만들어서 공유함
    - 여러 스레드가 동시에 접근해도 안전함
- 엔티티 매니저: 엔티티를 저장하고, 수정하고, 삭제하고, 조회하는 등 엔티티와 관련된 모든 일을 처리함
    - 엔티티를 저장하는 가상의 데이터베이스

#### 엔티티 매니저 팩토리와 엔티티 매니저의 차이

|  | 엔티티 매니저 팩토리 | 엔티티 매니저 |
| --- | --- | --- |
| 관리 대상 | 매핑 메타 데이터, 커넥션 풀, 설정 정보 | 영속성 컨텍스트 (1차 캐시, 쓰기 지연 SQL 저장소, 스냅샷) |
| 상태 | 생성 후 불변 | 요청마다 계속 변함 |
| 스레드 공유 | 안전 - 매핑 정보를 읽기만 함 | 위험 - 1차 캐시가 공유되어 다른 요청의 엔티티가 조회되고,<br>스냅샷도 섞여 의도하지 않은 UPDATE가 발생할 수 있음 |
| 생성 비용 | 큼 (엔티티 클래스 스캔 + 매핑 정보 생성 + 커넥션 풀) | 거의 없음 (팩토리가 만들어둔 매핑 정보를 그대로 사용) |
| 개수 | 애플리케이션당 하나 | 요청마다 새로 생성 |

#### 엔티티 매니저 팩토리 생성

```java
// 순수 JPA에서 META-INF/persistence.xml
EntityManagerFactory emf = Persistence.createEntityManagerFactory("jpabook");
```

- `Persistence.createEntityManagerFactory("jpabook")` 호출 시 `META-INF/persistence.xml` 의 정보를 바탕으로 생성됨
- `"jpabook"`은 persistence.xml에 정의된 영속성 유닛(persistence-unit) 이름
- 순수 JPA(Java SE) 환경 기준
    - 스프링에서는 `LocalContainerEntityManagerFactoryBean`
    - 스프링 부트에서는 자동 구성이 대신 만들어 빈으로 등록해줌

## 3.2 영속성 컨텍스트

- 영속성 컨텍스트: 엔티티를 영구 저장하는 환경
    - 엔티티 매니저로 엔티티를 저장하거나 조회하면 엔티티 매니저는 영속성 컨텍스트에 엔티티를 보관하고 관리함

```java
em.persist(member);
```

- `persist()`는 단순히 저장하는 게 아니라 엔티티 매니저를 사용해서 회원 엔티티를 영속성 컨텍스트에 저장하는 것
- 논리적인 개념이라 눈에 보이지 않음
- 엔티티 매니저를 생성할 때 영속성 컨텍스트가 하나 만들어지고, 엔티티 매니저를 통해서만 접근과 관리할 수 있음

---

## 3.3 엔티티의 생명주기

- 비영속(new/transient): 영속성 컨텍스트와 전혀 관계가 없는 상태
- 영속(managed): 영속성 컨텍스트에 저장된 상태
- 준영속(detached): 영속성 컨텍스트에 저장되어있다가 분리된 상태
- 삭제(removed): 삭제된 상태

#### 상태 전이

| 전이 | 메서드 |
| --- | --- |
| 비영속 → 영속 | `persist()` |
| DB → 영속 | `find()`, JPQL |
| 영속 → 준영속 | `detach()`, `clear()`, `close()` |
| 준영속 → 영속 | `merge()` |
| 영속 → 삭제 | `remove()` |

## 3.4 영속성 컨텍스트의 특징

#### 영속성 컨텍스트와 식별자 값

- 영속성 컨텍스트는 엔티티를 식별자 값(`@Id`로 테이블 기본 키와 매핑한 값)으로 구분함
- 따라서 영속 상태는 식별자 값이 반드시 있어야 하고, 없으면 예외가 발생함

#### 영속성 컨텍스트와 데이터베이스 저장

- JPA는 보통 트랜잭션을 커밋하는 순간 영속성 컨텍스트에 새로 저장된 엔티티를 데이터베이스에 반영함
    - 이를 플러시(flush)라고 함

#### 영속성 컨텍스트가 엔티티를 관리할 때의 장점

- 1차 캐시
- 동일성 보장
- 트랜잭션을 지원하는 쓰기 지연
- 변경 감지
- 지연 로딩

### 3.4.1 엔티티 조회

- 영속성 컨텍스트는 내부에 1차 캐시를 가지고 있고, 영속 상태의 엔티티는 모두 여기 저장됨
- 영속성 컨텍스트 내부에 `Map`이 하나 있는 구조
    - 키: `@Id`로 매핑한 식별자
    - 값: 엔티티의 인스턴스
- 1차 캐시의 키인 식별자 값은 데이터베이스 기본 키와 매핑되어 있음
    - 영속성 컨텍스트에 저장하고 조회하는 모든 기준이 데이터베이스 기본 키 값

#### 1차 캐시에서 조회

- `em.find()`를 호출하면 먼저 1차 캐시에서 식별자 값으로 엔티티를 찾고, 없으면 데이터베이스에서 조회함
- 1차 캐시에 있으면 DB를 조회하지 않고 메모리에서 바로 반환

```java
// EntityManager.find() 메소드 정의
// 첫 번째 파라미터는 엔티티 클래스 타입, 두 번째는 조회할 엔티티의 식별자 값
public <T> T find(Class<T> entityClass, Object primaryKey);

// 엔티티를 생성한 상태 (비영속)
Member member = new Member();
member.setId("member1");
member.setUsername("회원1");

// 엔티티를 영속 - 1차 캐시에 저장된다. 아직 DB에는 저장되지 않음
em.persist(member);

// 1차 캐시에서 조회 - SELECT 쿼리가 나가지 않는다
Member findMember = em.find(Member.class, "member1");
```

#### 데이터베이스에서 조회

- `em.find()`를 호출하는데 엔티티가 1차 캐시에 없으면 엔티티 매니저는 데이터베이스를 조회해서 엔티티를 생성함
- 그리고 1차 캐시에 저장한 후에 영속 상태의 엔티티를 반환함

1. `em.find(Member.class, "member2")` 를 실행
2. `member2` 가 1차 캐시에 없으므로 데이터베이스에서 조회
3. 조회한 데이터를 `member2` 엔티티를 생성해서 1차 캐시에 저장 (영속 상태)
4. 조회한 엔티티를 반환

이제 `member1` , `member2` 는 1차 캐시에 있으므로 다시 조회하면 메모리에서 바로 반환됨

#### 영속 엔티티의 동일성 보장

```java
Member a = em.find(Member.class, "member1");
Member b = em.find(Member.class, "member1");

System.out.println(a == b); // 동일성 비교 - true
```

- `em.find()` 를 반복 호출해도 영속성 컨텍스트는 1차 캐시에 있는 같은 엔티티 인스턴스를 반환함
- 따라서 영속성 컨텍스트는 성능상 이점과 엔티티의 동일성 보장함

### 3.4.2 엔티티 등록

```java
EntityManager em = emf.createEntityManager();
EntityTransaction tx = em.getTransaction();

// 엔티티 매니저는 데이터 변경 시 트랜잭션을 시작해야 한다
tx.begin();

em.persist(memberA);
em.persist(memberB);
// 여기까지 INSERT SQL을 데이터베이스에 보내지 않는다

// 커밋하는 순간 데이터베이스에 INSERT SQL을 보냄
tx.commit();
```

- 엔티티 매니저는 트랜잭션을 커밋하기 직전까지 DB에 엔티티를 저장하지 않고, 내부 쓰기 지연 SQL 저장소에 INSERT SQL을 모아둠
- 커밋할 때 모아둔 쿼리를 데이터베이스에 보냄 → 트랜잭션을 지원하는 쓰기 지연

#### 트랜잭션을 지원하는 쓰기 지연이 가능한 이유

1. 데이터를 저장하는 즉시 등록 쿼리를 DB에 보내고, 마지막에 트랜잭션을 커밋
2. 등록 쿼리를 메모리에 모아뒀다가, 커밋할 때 한 번에 보낸 후 커밋

- 트랜잭션 범위 안에서 실행되므로 둘의 결과는 같음
    - 커밋하면 함께 저장되고 롤백하면 함께 저장되지 않음
    - 등록 쿼리를 그때그때 보내도 커밋하지 않으면 소용없음
- 결국 커밋 직전에만 SQL을 전달하면 되기 때문에 쓰기 지연이 가능함
- 모아둔 쿼리를 한 번에 전달해서 성능을 최적화할 수 있음

### 3.4.3 엔티티 수정

#### SQL 수정 쿼리의 문제점

- SQL을 사용하면 수정 쿼리를 직접 작성해야 하고, 요구사항이 늘면 수정 쿼리도 계속 늘어남
- 쿼리를 합치면 실수로 일부 값을 누락할 위험이 생김
- 결국 비즈니스 로직을 분석하려면 SQL을 계속 확인해야 함
    - 비즈니스 로직이 SQL에 의존하게 됨

#### 변경 감지 (dirty checking)

```java
tx.begin();

// 영속 엔티티 조회
Member memberA = em.find(Member.class, "memberA");

// 영속 엔티티 데이터 수정
memberA.setUsername("hi");
memberA.setAge(27);

// em.update(member) -> 이런 업데이트 느낌의 코드가 있을거라 생각
tx.commit();
```

- JPA로 엔티티를 수정할 때는 조회해서 데이터만 변경하면 됨
- 엔티티의 변경사항을 데이터베이스에 자동으로 반영하는 기능 - 변경 감지

동작 순서

1. 트랜잭션을 커밋하면 엔티티 매니저 내부에서 먼저 플러시(`flush()`)가 호출됨
2. 엔티티와 스냅샷을 비교해서 변경된 엔티티를 찾음
3. 변경된 엔티티가 있으면 수정 쿼리를 생성해서 쓰기 지연 SQL 저장소에 보냄
4. 쓰기 지연 저장소의 SQL을 데이터베이스에 보냄
5. 데이터베이스 트랜잭션을 커밋

변경 감지는 영속 상태의 엔티티에만 적용됨

- UPDATE는 모든 필드를 대상으로 한다
    - 이름과 나이만 수정해도 JPA 기본 전략은 엔티티의 모든 필드를 업데이트함
    - 전송량이 늘어나는 단점이 있음
        - 수정 쿼리가 항상 같으므로 로딩 시점에 미리 생성해두고 재사용 가능
        - DB도 동일한 쿼리를 받으면 이전에 파싱한 쿼리를 재사용 가능
    - 필드가 많거나 저장 내용이 크면 `@DynamicUpdate`로 변경된 데이터만 동적 생성 (하이버네이트 확장)
        - `@DynamicInsert`는 null이 아닌 필드만 INSERT를 생성

### 3.4.4 엔티티 삭제

```java
Member memberA = em.find(Member.class, "memberA"); // 삭제 대상 엔티티 조회
em.remove(memberA); // 엔티티 삭제
```

- 삭제하려면 먼저 삭제 대상 엔티티를 조회해야 함
- 즉시 삭제되는 것이 아니라 등록과 비슷하게 삭제 쿼리를 쓰기 지연 SQL 저장소에 등록하고, 커밋해서 플러시를 호출할 때 실제 DELETE를 전달함
- 단, `em.remove()`를 호출하는 순간 영속성 컨텍스트에서 제거됨
- 삭제된 엔티티는 재사용하지 말고 가비지 컬렉션 대상이 되도록 두는 것이 좋음

## 3.5 플러시

- 플러시(`flush()`)는 영속성 컨텍스트의 변경 내용을 데이터베이스에 반영함

1. 변경 감지가 동작해서 영속성 컨텍스트에 있는 모든 엔티티를 스냅샷과 비교하고, 수정된 엔티티는 수정 쿼리를 만들어 쓰기 지연 SQL 저장소에 등록
2. 쓰기 지연 SQL 저장소의 쿼리를 데이터베이스에 전송 (등록/수정/삭제 쿼리)

#### 플러시하는 방법 3가지

| 방법 | 설명 |
| --- | --- |
| `em.flush()`를 직접 호출 | 강제로 플러시. 테스트나 다른 프레임워크와 함께 쓸 때를 제외하면 거의 사용하지 않음 |
| 트랜잭션 커밋 시 자동 호출 | 커밋 전에 플러시하지 않으면 변경 내용이 DB에 반영되지 않으므로 JPA가 자동 호출 |
| JPQL 쿼리 실행 시 자동 호출 | 아래 참고 |

#### JPQL 쿼리 실행 시 플러시가 자동 호출되는 이유

```java
em.persist(memberA);
em.persist(memberB);
em.persist(memberC);

// 중간에 JPQL 실행
query = em.createQuery("select m from Member m", Member.class);
List<Member> members = query.getResultList();
```

- `persist()`한 엔티티는 영속성 컨텍스트에는 있지만 아직 DB에는 없음
- JPQL은 SQL로 변환되어 데이터베이스에서 조회하므로 memberA, B, C가 결과에 포함되지 않음
- JPA는 이 문제를 예방하기 위해 JPQL 실행 직전에 플러시를 자동으로 호출함
- 참고: 식별자 기준으로 조회하는 `find()`는 플러시가 실행되지 않음

## 3.6 준영속

- 영속성 컨텍스트가 관리하는 영속 상태의 엔티티가 영속성 컨텍스트에서 분리된 것
- 준영속 상태의 엔티티는 영속성 컨텍스트가 제공하는 기능을 사용할 수 없음

### 3.6.1 detach()

```java
em.persist(member);
em.detach(member); // 영속성 컨텍스트에서 분리, 준영속 상태
```

- 특정 엔티티만 준영속 상태로 전환
- 호출하는 순간 1차 캐시부터 쓰기 지연 SQL 저장소까지 해당 엔티티를 관리하기 위한 모든 정보가 제거됨
- 심지어 쓰기 지연 SQL 저장소의 INSERT SQL도 제거되어 DB에 저장되지 않음

### 3.6.2 clear()

```java
Member member = em.find(Member.class, "memberA");
em.clear(); // 영속성 컨텍스트 초기화
member.setUsername("changeName"); // 준영속 - 변경 감지 동작하지 않음
```

- 영속성 컨텍스트를 초기화해서 해당 영속성 컨텍스트의 모든 엔티티를 준영속으로 만듦
- 영속성 컨텍스트를 제거하고 새로 만든 것과 같음

### 3.6.3 close()

- 영속성 컨텍스트를 종료하면 관리하던 영속 상태의 엔티티가 모두 준영속이 됨

> 영속 상태의 엔티티는 주로 영속성 컨텍스트가 종료되면서 준영속이 됨<br>
> 개발자가 직접 준영속으로 만드는 일은 드물다

### 3.6.4 준영속 상태의 특징

| 특징 | 설명 |
| --- | --- |
| 거의 비영속에 가깝다 | 1차 캐시, 쓰기 지연, 변경 감지, 지연 로딩을 포함한 어떤 기능도 동작하지 않음 |
| 식별자 값을 가지고 있다 | 비영속은 식별자가 없을 수도 있지만, 준영속은 이미 한 번 영속이었으므로 반드시 가지고 있음 |
| 지연 로딩을 할 수 없다 | 지연 로딩은 프록시를 실제 사용할 때 영속성 컨텍스트를 통해 데이터를 불러오는데, 준영속은 관리 대상이 아니라 문제가 발생 |

### 3.6.5 merge()

```java
Member mergeMember = em.merge(member);
```

- 준영속 상태의 엔티티를 받아서 그 정보로 새로운 영속 상태의 엔티티를 반환함

동작 순서

1. `merge()` 실행
2. 파라미터로 넘어온 준영속 엔티티의 식별자 값으로 1차 캐시에서 조회
    1. 1차 캐시에 없으면 데이터베이스에서 조회하고 1차 캐시에 저장
3. 조회한 영속 엔티티에 파라미터 엔티티의 값을 채워 넣음
4. 그 영속 엔티티를 반환

- 파라미터로 넘긴 엔티티는 병합 후에도 준영속 상태로 남음
    - `em.contains(member)` → false, `em.contains(mergeMember)` → true
    - 둘은 서로 다른 인스턴스
- 따라서 준영속 참조를 영속 참조로 바꿔주는 것이 안전함

#### 비영속 병합

- 병합은 비영속 엔티티도 영속 상태로 만들 수 있음
- 식별자 값으로 조회할 수 있으면 불러서 병합하고, 없으면 새로 생성해서 병합
    - 병합은 save or update 기능을 수행함
