# Chapter 3. 영속성 관리

## 1. 엔티티 매니저 팩토리와 엔티티 매니저

엔티티 매니저는 엔티티를 저장하고, 수정하고, 삭제하고 조회하는 등 엔티티와 관련된 모든 일을 처리한다.

엔티티 매니저는 엔티티를 저장하는 가상의 데이터베이스이다.

엔티티 매니저 팩토리는 여러 스레드가 동시에 접근해도 안전하므로 스레드 간에 공유 가능, 엔티티 매니저는 여러 스레드가 동시에 접근하면 동시성 문제가 발생하므로 스레드 간에 공유하면 안된다.

> `"jpabook"`은 `META-INF/persistence.xml`에 정의된 영속성 유닛(persistence-unit) 이름이며, 코드의 문자열과 일치해야 한다. (Spring Boot + Spring Data JPA는 설정 파일만으로 스프링이 내부에서 자동 생성해주므로 이 코드를 직접 쓸 일은 거의 없다.)

```java
// 엔티티 매니저 팩토리 생성 (스레드 간 공유 가능)
EntityManagerFactory emf = Persistence.createEntityManagerFactory("jpabook");

// 엔티티 매니저 생성 (스레드 간 공유 금지)
EntityManager em = emf.createEntityManager();

em.close();  // 엔티티 매니저 종료
emf.close(); // 엔티티 매니저 팩토리 종료
```

## 2. 영속성 컨텍스트

영속성 컨텍스트는 엔티티를 영구 저장하는 환경이다. 엔티티 매니저로 엔티티를 저장하거나 조회하면 엔티티 매니저는 영속성 컨텍스트에 엔티티를 보관하고 관리한다.

persist() 메소드는 엔티티 매니저를 사용해서 회원 엔티티를 영속성 컨텍스트에 저장한다.

```java
Member member = new Member();
member.setId(1L);
member.setName("member1");

// em.persist(member)를 호출하면 member 엔티티가 영속성 컨텍스트에 저장(관리)된다
em.persist(member);
```

## 3. 엔티티의 생명주기

엔티티에는 4가지 상태가 존재한다(비영속/영속/준영속/삭제).

① 비영속(new/transient): 영속성 컨텍스트와 전혀 관계가 없는 새로운 상태  
② 영속(managed): 영속성 컨텍스트에 저장된 상태  
③ 준영속(detached): 영속성 컨텍스트에 저장되었다가 분리된 상태  
④ 삭제(removed): 삭제된 상태

영속 상태는 식별자 값이 반드시 있어야 한다.

JPA 는 보통 트랜잭션을 커밋하는 순간 영속성 컨텍스트에 새로 저장된 엔티티를 데이터베이스에 반영하는데 이것을 플러시라고 한다.

## 4. 영속성 컨텍스트의 특징

영속성 컨텍스트가 엔티티를 관리하면 다음과 같은 장점이 있다  
① 1차 캐시  
② 동일성보장  
③ 트랜잭션을 지원하는 쓰기 지연  
④ 변경감지  
⑤ 지연로딩

### 1차 캐시

영속성 컨텍스트는 내부에 캐시를 가지고 있는데 이것을 1차 캐시라 한다.

em.find() 를 호출하면 먼저 1차 캐시에서 엔티티를 찾고 찾는 엔티티가 1차 캐시에 없으면 데이터베이스에서 조회한다.

영속성 컨텍스트는 성능상 이점과 엔티티의 동일성을 보장한다.

```java
Member member = new Member();
member.setId(1L);
member.setName("member1");

em.persist(member); // 1차 캐시에 저장됨

Member findMember1 = em.find(Member.class, 1L); // 1차 캐시에 있으므로 DB 조회 없이 반환
Member findMember2 = em.find(Member.class, 2L); // 1차 캐시에 없으므로 DB에서 조회 후 1차 캐시에 저장

System.out.println(findMember1 == member); // true (동일성 보장)
```

### 쓰기 지연

트랜잭션을 커밋할때 모아둔 쿼리를 데이터베이스에 보내는데 이것을 트랜잭션을 지원하는 쓰기 지연이라 한다.

소스코드단에서 트랜잭션 커밋 -> 영속성 컨텍스트 플러시 -> 실제 데이터베이스 트랜잭션 커밋

```java
EntityTransaction tx = em.getTransaction();
tx.begin();

// 아래 두 insert 쿼리는 즉시 DB로 전송되지 않고 내부 쓰기 지연 SQL 저장소에 쌓인다
em.persist(memberA);
em.persist(memberB);

// tx.commit()이 호출되는 시점에 쌓아둔 쿼리가 한 번에 DB로 전송(플러시)되고,
// 이후 실제 데이터베이스 트랜잭션이 커밋된다
tx.commit();
```

### 변경 감지

엔티티의 변경사항을 데이터베이스에 자동으로 반영하는 기능을 변경 감지라고 한다.

```java
EntityTransaction tx = em.getTransaction();
tx.begin();

Member member = em.find(Member.class, 1L); // 영속 상태의 엔티티 조회

member.setName("member2"); // 별도의 em.update() 호출 없이 값만 변경

// 커밋 시점에 1차 캐시에 보관된 최초 상태(스냅샷)와 현재 엔티티를 비교해
// 변경분을 감지하여 UPDATE 쿼리를 자동으로 생성, 반영한다
tx.commit();
```

### 지연 로딩

지연 로딩은 엔티티를 실제 사용하는 시점까지 데이터베이스 조회를 미루는 기능이다. 연관된 엔티티를 즉시 조회하지 않고, 실제로 그 엔티티를 사용할 때 영속성 컨텍스트가 프록시(가짜) 객체를 초기화하면서 데이터베이스를 조회한다.

```java
Member member = em.find(Member.class, 1L); // Member만 조회, Team은 아직 조회하지 않음(프록시 객체)

Team team = member.getTeam(); // 프록시 객체 반환, 아직 DB 조회 없음
team.getName(); // 실제로 Team의 값을 사용하는 시점에 DB 조회가 발생(초기화)
```

## 5. 플러시

플러시는 영속성 컨텍스트의 변경 내용을 데이터베이스에 반영한다.

영속성 컨텍스트를 플러시하는 방법은 3가지이다  
① 직접호출  
② 트랜잭션 커밋 시  
③ JPQL 쿼리 실행시

```java
// 1번 예시: 직접 호출
em.persist(member);
em.flush(); // 강제로 즉시 SQL을 DB에 반영
```

```java
// 2번 예시: 트랜잭션 커밋 시
em.persist(member);
tx.commit(); // 커밋 전에 자동으로 플러시 호출
```

```java
// 3번 예시: JPQL 쿼리 실행 시
em.persist(member); // 아직 DB에 반영되지 않은 상태
em.createQuery("select m from Member m", Member.class).getResultList();
// JPQL 실행 전에 자동으로 플러시가 호출되어 방금 저장한 member도 조회 결과에 포함됨
```

## 6. 준영속 상태

영속성 컨텍스트가 관리하는 영속 상태의 엔티티가 영속성 컨텍스트에서 분리된 것을 준영속 상태라고 하며, 준영속 상태의 엔티티는 영속성 컨텍스트가 제공하는 기능을 사용할 수 없다.

```java
Member member = em.find(Member.class, 1L); // 영속 상태

em.detach(member); // 준영속 상태로 전환 (영속성 컨텍스트에서 분리)

member.setName("member2"); // 값을 변경해도 변경 감지가 동작하지 않아 DB에 반영되지 않음
```

## 심화학습

### 엔티티 매니저 / 팩토리

**Q. 엔티티 매니저 팩토리는 스레드 세이프한데 왜 엔티티 매니저는 스레드 세이프하지 않은가?**

엔티티 매니저 팩토리는 커넥션풀, 설정정보 등 애플리케이션 전체에서 공유하는 변하지 않는 자원만 들고 있는 반면, 엔티티 매니저는 내부에 영속성 컨텍스트(1차 캐시, 쓰기 지연 SQL 저장소 등 상태를 가진 자원)를 들고 있어서 여러 스레드가 동시에 접근하면 상태가 꼬여 동시성 문제가 발생한다.

**Q. 스프링에서 `@PersistenceContext`로 주입받은 엔티티 매니저를 여러 스레드가 동시에 써도 문제가 안 되는 이유는?**

스프링이 주입하는 것은 실제 EntityManager가 아니라 프록시이며, 실제로는 트랜잭션이 시작될 때마다 스레드별로 별도의 진짜 EntityManager를 생성해 연결해주기 때문에 스레드 간 공유 문제가 없다.

### 영속성 컨텍스트 & 1차 캐시

**Q. `em.find()`로 같은 id를 두 번 조회하면 SQL이 몇 번 나가는가? 이걸로 뭘 보장할 수 있는가?**

첫 조회에서만 SQL이 나가고 이후엔 1차 캐시에서 반환되어 SQL이 나가지 않는다. 두 조회 결과가 `==` 비교로 같음을 보장하는 동일성 보장 효과가 있다 — 자바 컬렉션에서 값을 꺼내오는 것과 같은 방식으로 동작한다.

### 쓰기 지연 (Write-Behind)

**Q. 쓰기 지연 SQL 저장소에 쿼리를 모아뒀다가 커밋 시점에 한 번에 보내는 게 어떤 성능 이점이 있는가?**

JDBC의 batch 기능을 활용해 여러 건의 INSERT/UPDATE를 한 번의 네트워크 왕복으로 처리할 수 있어 DB와의 통신 횟수를 줄일 수 있다.

**Q. `@GeneratedValue(strategy = IDENTITY)` 전략을 쓰면 쓰기 지연이 왜 동작하지 않는가?**

IDENTITY 전략은 DB가 auto increment로 식별자를 채번하기 때문에, 식별자 값을 알아야 영속성 컨텍스트(1차 캐시)에 엔티티를 저장할 수 있다. 그래서 `persist()` 호출 시점에 즉시 INSERT 쿼리를 실행해서 식별자를 받아와야 하며, 쓰기 지연 없이 바로 SQL이 나간다.

### 변경 감지 (Dirty Checking)

**Q. 변경 감지는 어떻게 "무엇이 바뀌었는지" 아는가?**

엔티티를 영속성 컨텍스트에 최초로 등록하는 시점의 상태를 스냅샷으로 저장해두고, 플러시 시점에 현재 엔티티와 스냅샷을 필드 단위로 비교해서 변경된 부분을 찾아낸다.

**Q. 준영속/비영속 상태의 엔티티는 왜 변경 감지가 안 되는가?**

변경 감지는 영속성 컨텍스트가 스냅샷을 들고 관리하는 영속 상태의 엔티티에 대해서만 동작한다. 준영속/비영속 엔티티는 영속성 컨텍스트 밖에 있어 비교할 스냅샷 자체가 없으므로 변경 감지가 불가능하다.

**Q. 필드가 많은 엔티티에서 하나만 바꿔도 UPDATE 쿼리는 모든 컬럼을 다 포함해서 나가는데, 이유와 줄이는 방법은?**

기본 전략은 수정 쿼리를 애플리케이션 로딩 시점에 미리 만들어두고 재사용하기 위함이며, 항상 같은 쿼리를 사용하면 DB도 이전에 파싱한 쿼리를 재사용(캐싱)할 수 있어 성능에 유리하기 때문이다. 컬럼이 아주 많은 엔티티라면 `@DynamicUpdate`를 붙여서 실제로 변경된 컬럼만 포함하는 UPDATE 쿼리를 동적으로 생성하게 할 수 있다.

### 플러시

**Q. 플러시와 커밋의 차이는? 플러시했다고 트랜잭션이 끝나는가?**

플러시는 영속성 컨텍스트의 변경 내용을 DB에 SQL로 반영하는 것일 뿐, 트랜잭션을 커밋하거나 종료하는 것이 아니다. 플러시 이후에도 트랜잭션은 계속 진행 중이며, 이후 롤백하면 반영했던 SQL도 함께 롤백된다.

**Q. `FlushModeType.COMMIT`으로 바꾸면 어떤 상황에 쓰는가?**

기본값(AUTO)은 커밋 또는 JPQL 실행 전에 자동으로 플러시가 일어나는데, COMMIT으로 설정하면 커밋 시점에만 플러시가 일어나고 JPQL 실행 전 플러시는 생략된다. 조회 성능이 중요하고 JPQL 조회 전에 최신 상태 반영이 꼭 필요하지 않은 경우 플러시 횟수를 줄이기 위해 사용할 수 있다.

```java
em.setFlushMode(FlushModeType.COMMIT); // 커밋 시점에만 플러시, JPQL 실행 전 자동 플러시 생략
```

### 지연 로딩

**Q. 지연 로딩과 즉시 로딩의 차이, 실무에서 지연 로딩을 기본으로 쓰라고 권장하는 이유는?**

즉시 로딩(EAGER)은 엔티티 조회 시 연관된 엔티티까지 함께(주로 JOIN으로) 즉시 가져오고, 지연 로딩(LAZY)은 연관 엔티티를 프록시로 두었다가 실제 사용 시점에 조회한다. 실무에서는 EAGER가 예상치 못한 JOIN을 만들거나 N+1 문제를 예측하기 어렵게 만들기 때문에, 연관관계는 기본적으로 LAZY로 설정하고 필요한 경우에만 fetch join 등으로 명시적으로 최적화하는 것을 권장한다.

**Q. 지연 로딩으로 가져온 프록시 객체를 준영속 상태에서 접근하면 어떻게 되는가?**

프록시를 초기화하려면 영속성 컨텍스트가 필요한데, 준영속 상태는 영속성 컨텍스트의 관리를 벗어난 상태이므로 초기화할 수 없어 `LazyInitializationException`이 발생한다.

### 종합 시나리오형

**Q. 트랜잭션 커밋 직전에 예외가 발생해서 롤백됐다. 이미 1차 캐시에 저장했던 엔티티는 어떻게 되는가?**

롤백은 DB 트랜잭션만 되돌릴 뿐 영속성 컨텍스트(1차 캐시)의 상태를 자동으로 되돌려주지는 않는다. 그래서 롤백 이후에도 1차 캐시에는 커밋되지 않은 엔티티가 그대로 남아있을 수 있고, 이 영속성 컨텍스트를 계속 사용하면 DB와 애플리케이션 메모리 상태가 불일치할 위험이 있다. (그래서 스프링은 트랜잭션 롤백 시 영속성 컨텍스트도 함께 종료하는 것이 기본 동작이다.)

**Q. 컨트롤러에서 서비스 계층을 나와 준영속 상태가 된 엔티티를 그대로 뷰에서 수정 후 다시 저장하려 한다면 어떤 방식을 써야 하는가?**

`merge()`로 준영속 엔티티의 값을 새로운 영속 엔티티에 복사해서 저장하거나, id로 새 트랜잭션에서 엔티티를 다시 조회한 뒤 변경 감지를 이용해 값을 바꾸는 방식을 쓴다. 실무에서는 merge보다 변경 감지 방식을 권장하는 경우가 많다 — merge는 넘어온 엔티티의 모든 필드로 덮어써버리기 때문에 null인 필드가 있으면 그 값으로도 덮어써지는 위험이 있다.
