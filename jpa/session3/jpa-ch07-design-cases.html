1. 공통 매핑 정보 설계

Case 1

여러 엔티티에 같은 컬럼(id, 등록일, 수정일)이 반복된다

7장 · @MappedSuperclass, 상속 관계 매핑

상황

Member, Seller, Order 모두 createdAt, updatedAt을 가진다. 엔티티마다 복사해 넣기는 싫다.

선택지

  • 상속 관계 매핑 (@Inheritance) — 부모도 테이블이 된다
  • @MappedSuperclass — 매핑 정보만 물려준다

추천 설계

@MappedSuperclass
public abstract class BaseEntity {
    private LocalDateTime createdAt;
    private LocalDateTime updatedAt;
}

@Entity
public class Member extends BaseEntity {
    @Id @GeneratedValue
    @Column(name = "MEMBER_ID")
    private Long id;          // id는 엔티티마다 직접 선언
    private String name;
}
판단 기준: "부모 타입으로 조회할 일이 있는가?" select b from BaseEntity b 같은 조회는 의미가 없다. 공통 컬럼은 조회 대상이 아니라 재사용 대상이므로 @MappedSuperclass가 맞다.

id도 BaseEntity에 넣으면?

테이블마다 PK 컬럼명(MEMBER_ID, SELLER_ID...)이 다르면 엔티티마다 재정의가 필요하다.

@Entity
@AttributeOverride(name = "id", column = @Column(name = "MEMBER_ID"))
public class Member extends BaseEntity { ... }

모든 엔티티에 오버라이드가 붙게 되므로, PK 컬럼명이 테이블마다 다르면 id는 각 엔티티에 두고 날짜 같은 부가 컬럼만 BaseEntity로 올리는 편이 깔끔하다.

주의 BaseEntity에 실수로 @Entity를 붙이면 상속 관계 매핑이 되어 BASE_ENTITY 테이블이 생기고 조회할 때마다 조인이 발생한다.

2. 타입별로 달라지는 도메인

Case 2

결제수단(카드/계좌이체)처럼 타입마다 속성이 다르다

7장 · 상속 관계 매핑

상황

모든 결제는 금액·결제일을 가지지만, 카드는 카드번호·할부개월, 계좌이체는 은행명·계좌번호를 가진다. 결제수단은 앞으로 늘어날 수 있다(간편결제 등).

선택지와 판단 기준

이런 상황이면선택
자식 컬럼이 필수값(not null)이다 / 자식 타입이 늘어날 수 있다 / 특정 자식만 FK로 참조해야 한다JOINED
자식 고유 컬럼이 1~2개로 단순하다 / 타입이 거의 안 늘어난다 / 부모 타입 목록 조회가 잦다SINGLE_TABLE
—TABLE_PER_CLASS는 쓰지 않는다 (부모 조회 시 UNION)

추천 설계: 결제수단 → JOINED

카드번호·은행명은 반드시 있어야 하는 값이고, 결제수단도 늘어날 수 있으므로 JOINED가 맞다.

@Entity
@Inheritance(strategy = InheritanceType.JOINED)
@DiscriminatorColumn
public abstract class Payment {
    @Id @GeneratedValue
    @Column(name = "PAYMENT_ID")
    private Long id;
    private int amount;
}

@Entity
@DiscriminatorValue("CARD")
public class CardPayment extends Payment {
    @Column(nullable = false)
    private String cardNumber;
    private int installment;
}

반대 예: 알림(이메일/SMS) → SINGLE_TABLE

이메일은 수신주소, SMS는 전화번호 정도로 자식 고유 컬럼이 1개뿐이고, "내 알림 목록"처럼 부모 타입으로 조회하는 일이 대부분이다. 이럴 때는 조인 없는 SINGLE_TABLE이 낫다.

주의 상속 계층은 1단계로 유지한다. 계층이 깊어지면 JOINED는 조인이, SINGLE_TABLE은 null 컬럼이 급격히 늘어난다.

3. 식별자 설계

Case 3

부모에 종속된 자식(주문-주문상품)의 PK를 어떻게 잡을까

7장 · 식별 관계 / 비식별 관계

상황

주문상품은 주문 없이 존재할 수 없다. 주문상품의 PK를 주문 ID를 포함한 복합 키로 할지, 독립적인 대리 키로 할지 정해야 한다.

선택지

추천 설계: ② 필수적 비식별 관계 + 대리 키

@Entity
public class OrderItem {
    @Id @GeneratedValue
    @Column(name = "ORDER_ITEM_ID")
    private Long id;

    @ManyToOne(optional = false)                    // 필수 관계
    @JoinColumn(name = "ORDER_ID", nullable = false)
    private Order order;

    private String itemName;
}
① 식별 관계② 비식별 + 대리 키
자식 아래로 테이블이 더 생기면PK 컬럼이 계속 늘어남항상 PK 1개
JPA 매핑식별자 클래스 + equals/hashCode 필요Long id 하나로 끝
요구사항 변경PK에 비즈니스 의미가 섞여 변경이 어려움PK는 의미가 없어 영향 없음
필수적(NOT NULL)으로 두는 이유 FK가 항상 있으므로 주문과 함께 조회할 때 내부 조인만으로 충분하다. 선택적(nullable)이면 외부 조인이 필요하다.
Case 4

레거시 테이블이 복합 키로 되어 있다

7장 · @IdClass / @EmbeddedId

상황

기존 성적 테이블 SCORE의 PK가 (STUDENT_NO, SUBJECT_CODE)다. 테이블 구조는 바꿀 수 없고 JPA로 매핑해야 한다.

선택지

@IdClass@EmbeddedId
엔티티 모양PK 필드가 엔티티에 그대로 있음PK를 식별자 객체 하나로 가짐
필드 접근score.getStudentNo()score.getId().getStudentNo()
JPQLs.studentNos.id.studentNo
어울리는 경우컬럼 중심 기존 쿼리가 많을 때식별자를 값 하나로 주고받을 때

추천 설계: @EmbeddedId

레거시 복합 키는 "학번 + 과목코드"처럼 그 자체로 의미 있는 값인 경우가 많다. 식별자를 하나의 객체로 다루면 메서드 파라미터로 넘기거나 비교하기 편하다. 팀 컨벤션이 있다면 그것을 따른다.

@Embeddable
public class ScoreId implements Serializable {
    @Column(name = "STUDENT_NO")
    private String studentNo;
    @Column(name = "SUBJECT_CODE")
    private String subjectCode;

    protected ScoreId() {}                       // 기본 생성자
    public ScoreId(String studentNo, String subjectCode) { ... }

    @Override public boolean equals(Object o) {  // 값 비교
        if (this == o) return true;
        if (!(o instanceof ScoreId that)) return false;
        return Objects.equals(studentNo, that.studentNo)
            && Objects.equals(subjectCode, that.subjectCode);
    }
    @Override public int hashCode() {
        return Objects.hash(studentNo, subjectCode);
    }
}

@Entity
public class Score {
    @EmbeddedId
    private ScoreId id;
    private int point;
}

Score score = em.find(Score.class, new ScoreId("2026001", "DB01"));
식별자 클래스 체크리스트 Serializable 구현 · equals()/hashCode() 구현 · 기본 생성자 · public 클래스. 그리고 setter를 두지 않는다 — 영속 상태 엔티티의 PK 값을 바꾸면 영속성 컨텍스트가 엔티티를 찾지 못한다.
Case 5

회원-회원상세처럼 1:1로 확장 정보를 붙여야 한다

7장 · @MapsId, 일대일 식별 관계

상황

회원 테이블은 자주 조회되고, 주소·생년월일 같은 상세 정보는 가끔만 쓴다. 상세 정보를 별도 테이블로 분리한다. 회원 없는 상세 정보는 없다.

선택지

  • 비식별: MEMBER_DETAIL에 자체 PK + MEMBER_ID FK(유니크)
  • 식별: MEMBER_DETAIL의 PK가 곧 MEMBER_ID (PK 공유)

추천 설계: PK 공유 (@MapsId)

@Entity
public class MemberDetail {
    @Id
    private Long id;              // 값은 Member의 id가 그대로 들어감

    @MapsId                       // FK를 PK에도 매핑
    @OneToOne
    @JoinColumn(name = "MEMBER_ID")
    private Member member;

    private String address;
}
  • 불필요한 PK 컬럼과 유니크 제약이 없다
  • 두 테이블이 PK = PK로 조인되어 단순하다
예외: 나중에 1:N이 될 수 있다면 비식별로 예를 들어 "회원별 배송지"처럼 여러 개가 될 가능성이 있으면, 자체 PK + FK 구조로 두고 FK의 유니크 제약만 풀면 된다. PK를 공유한 구조는 1:N으로 바꾸기 어렵다.

4. 연관관계 설계

Case 6

연결 테이블에 컬럼이 필요해졌다 (수강 신청일, 성적)

7장 · 조인 테이블, 복합 키

상황

학생과 강의는 N:M이다. @JoinTable로 연결 테이블을 매핑했는데, 신청일과 성적을 저장해야 한다는 요구가 왔다.

문제

@JoinTable은 FK 두 개만 매핑한다. 연결 테이블이 엔티티가 아니라서 ENROLLED_AT, GRADE를 매핑할 필드를 둘 곳이 없다.

추천 설계: 연결 테이블을 엔티티로 승격 + 대리 키

@Entity
@Table(uniqueConstraints = @UniqueConstraint(
    columnNames = {"STUDENT_ID", "COURSE_ID"}))   // 중복 신청 방지
public class Enrollment {
    @Id @GeneratedValue
    @Column(name = "ENROLLMENT_ID")
    private Long id;

    @ManyToOne
    @JoinColumn(name = "STUDENT_ID")
    private Student student;

    @ManyToOne
    @JoinColumn(name = "COURSE_ID")
    private Course course;

    private LocalDateTime enrolledAt;
    private String grade;
}

PK를 (STUDENT_ID, COURSE_ID) 복합 키로 하면?

가능하지만 식별자 클래스(EnrollmentId)와 equals/hashCode, @MapsId 두 개가 필요하다. 더 큰 문제는 "재수강 허용" 같은 요구가 오면 같은 학생-강의 조합이 두 번 들어가야 해서 PK 구조 자체를 바꿔야 한다는 점이다. 대리 키라면 유니크 제약만 수정하면 된다.

정리 연결 테이블은 처음부터 엔티티로 만들고, PK는 대리 키, 비즈니스 규칙(중복 금지)은 유니크 제약으로 표현한다.
Case 7

관계가 있을 수도 없을 수도 있다

7장 · 조인 컬럼 / 조인 테이블

상황

게시글은 카테고리에 속할 수도 있고, 카테고리 없이 작성될 수도 있다.

선택지

// ① 조인 컬럼: POST 테이블에 nullable FK
@ManyToOne
@JoinColumn(name = "CATEGORY_ID")          // 카테고리 없으면 null
private Category category;

// ② 조인 테이블: POST_CATEGORY 연결 테이블
@ManyToOne
@JoinTable(name = "POST_CATEGORY",
    joinColumns = @JoinColumn(name = "POST_ID"),
    inverseJoinColumns = @JoinColumn(name = "CATEGORY_ID"))
private Category category;                  // 카테고리 없으면 행 자체가 없음
① 조인 컬럼② 조인 테이블
관계 없을 때FK에 null연결 테이블에 행 없음
조회외부 조인 1번외부 조인 2번 (테이블이 하나 더)
테이블 수그대로+1

추천 설계: ① 조인 컬럼 (nullable FK)

null FK 몇 개가 테이블 하나를 더 관리하는 비용보다 훨씬 싸다. 대부분의 선택적 관계는 조인 컬럼으로 충분하다.

조인 테이블을 고려할 만한 경우 관계가 있는 데이터가 극히 일부여서 FK 컬럼이 거의 전부 null인 경우, 또는 기존 테이블에 FK 컬럼을 추가할 수 없는 경우(레거시 테이블 변경 불가).
