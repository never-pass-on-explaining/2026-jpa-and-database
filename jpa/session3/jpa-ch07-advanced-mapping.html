1. 상속 관계 매핑

관계형 DB에는 상속 개념이 없다. 대신 슈퍼타입-서브타입 관계 모델링 기법이 객체의 상속과 가장 유사하며, 이를 테이블로 구현하는 방법이 3가지다.

1) 조인 전략 (JOINED)

부모·자식을 각각 테이블로 만들고, 자식 테이블이 부모의 PK를 받아 PK + FK로 사용한다.

@Entity
@Inheritance(strategy = InheritanceType.JOINED)
@DiscriminatorColumn(name = "DTYPE")
public abstract class Item {
    @Id @GeneratedValue
    @Column(name = "ITEM_ID")
    private Long id;
    private String name;
    private int price;
}

@Entity
@DiscriminatorValue("A")
public class Album extends Item {
    private String artist;
}

@Entity
@DiscriminatorValue("M")
@PrimaryKeyJoinColumn(name = "MOVIE_ID")
public class Movie extends Item {
    private String director;
    private String actor;
}
-- Album 저장 시: INSERT 2번
insert into Item (name, price, DTYPE, ITEM_ID) values (?, ?, 'A', ?);
insert into Album (artist, ITEM_ID) values (?, ?);

-- Album 조회 시: 조인
select ... from Album a inner join Item i on a.ITEM_ID = i.ITEM_ID where a.ITEM_ID = ?;
  • 장점: 테이블 정규화, FK 무결성 제약 활용 가능, 저장 공간 효율적
  • 단점: 조회 시 조인이 많아 성능 저하 가능, 쿼리 복잡, INSERT 2번

2) 단일 테이블 전략 (SINGLE_TABLE)

테이블 하나에 부모·자식의 모든 컬럼을 넣고, 구분 컬럼(DTYPE)으로 구분한다.

@Entity
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name = "DTYPE")
public abstract class Item { ... }

@Entity @DiscriminatorValue("A")
public class Album extends Item { ... }
  • 장점: 조인이 없어 조회 성능이 가장 빠름, 쿼리 단순
  • 단점: 자식 엔티티의 컬럼은 모두 null 허용이어야 함, 테이블이 커질 수 있어 오히려 느려질 수 있음
  • 구분 컬럼이 반드시 필요 — @DiscriminatorColumn을 생략해도 Hibernate가 DTYPE을 자동 생성

조인 전략 vs 단일 테이블 — 언제 무엇을 쓸까

판단 기준조인 전략단일 테이블
자식 고유 컬럼많고 서로 다름1~2개로 단순
자식 컬럼 not null 필요가능불가 (자식 컬럼 null 허용 필수)
특정 자식만 FK로 참조
예: ALBUM_REVIEW → ALBUM		가능불가
자식 타입 확장 가능성높음 (테이블만 추가)낮음
부모 타입 목록 조회잦지 않음 (자식 수만큼 outer join)잦고 성능이 중요
한 줄 요약정합성·확장성단순함·조회 성능

조인 전략 예: 결제수단(카드 / 계좌이체), 상품(도서 / 강의), 알림(이메일 / SMS)

3) 구현 클래스마다 테이블 전략 (TABLE_PER_CLASS)

자식 엔티티마다 테이블을 만들고, 각 테이블에 부모 컬럼까지 모두 포함한다. 구분 컬럼을 쓰지 않는다.

-- 부모 타입으로 조회하면 모든 자식 테이블을 UNION
select ... from (
    select ... from Album union all
    select ... from Movie union all
    select ... from Book
) i where i.ITEM_ID = ?;
  • 장점: 서브타입을 명확히 구분, not null 제약 사용 가능
  • 단점: 부모 타입 조회 시 UNION으로 느림, 자식 테이블을 통합해서 쿼리하기 어려움
  • GenerationType.IDENTITY 사용 불가 — 여러 테이블 간 ID가 겹치면 안 되기 때문
DB 설계자·ORM 전문가 모두 추천하지 않는 전략

전략 비교

JOINEDSINGLE_TABLETABLE_PER_CLASS
테이블부모 1 + 자식 N1개자식 N
구분 컬럼선택필수 (자동 생성)사용 안 함
조회조인조인 없음 (가장 빠름)부모 조회 시 UNION

선택 기준 기본은 JOINED. 구조가 단순하고 확장 가능성이 낮으면 SINGLE_TABLE. TABLE_PER_CLASS는 쓰지 않는다.

2. @MappedSuperclass

부모 클래스는 테이블과 매핑하지 않고, 자식 엔티티에게 매핑 정보(공통 필드)만 물려주고 싶을 때 사용한다. 상속 관계 매핑이 아니다.

@MappedSuperclass
public abstract class BaseEntity {
    @Id @GeneratedValue
    private Long id;
    private String name;
}

@Entity
public class Member extends BaseEntity {
    private String email;       // MEMBER 테이블: id, name, email
}

@Entity
@AttributeOverride(name = "id", column = @Column(name = "SELLER_ID"))
public class Seller extends BaseEntity {
    private String shopName;    // SELLER 테이블: SELLER_ID, name, shopName
}
  • 주 용도: 등록일, 수정일, 등록자, 수정자 같은 공통 컬럼 모으기
  • @Entity 클래스는 @Entity 또는 @MappedSuperclass가 붙은 클래스만 상속할 수 있다

3. 복합 키와 식별 관계 매핑

식별 관계 vs 비식별 관계

구분의미
식별 관계부모의 PK를 받아서 자식의 PK + FK로 사용
비식별 관계부모의 PK를 받아서 자식의 FK로만 사용
└ 필수적 비식별FK에 null 불허 → 연관관계 필수
└ 선택적 비식별FK에 null 허용 → 연관관계 선택

복합 키를 쓰려면 식별자 클래스가 필요하다

JPA는 영속성 컨텍스트에 엔티티를 저장할 때 식별자를 키로 사용하고, 식별자를 구분할 때 equals()/hashCode()로 동등성 비교를 한다. 식별자 필드가 2개 이상이면 이를 담을 별도 클래스를 만들고 equals/hashCode를 반드시 구현해야 한다.

식별자 클래스 공통 조건

  • Serializable 구현
  • equals(), hashCode() 구현
  • 기본 생성자 필수
  • 클래스는 public

1) @IdClass — DB에 가까운 방식

@Entity
@IdClass(ParentId.class)
public class Parent {
    @Id @Column(name = "PARENT_ID1")
    private String id1;
    @Id @Column(name = "PARENT_ID2")
    private String id2;
    private String name;
}

public class ParentId implements Serializable {
    private String id1;   // Parent.id1과 필드명 일치
    private String id2;   // Parent.id2와 필드명 일치

    public ParentId() {}
    public ParentId(String id1, String id2) { ... }
    @Override public boolean equals(Object o) { ... }
    @Override public int hashCode() { ... }
}
  • 식별자 클래스의 속성명 = 엔티티의 식별자 속성명

2) @EmbeddedId — 객체지향적인 방식

@Entity
public class Parent {
    @EmbeddedId
    private ParentId id;
    private String name;
}

@Embeddable
public class ParentId implements Serializable {
    @Column(name = "PARENT_ID1")
    private String id1;
    @Column(name = "PARENT_ID2")
    private String id2;
    // 기본 생성자, equals, hashCode
}

@IdClass vs @EmbeddedId

@IdClass@EmbeddedId
성격DB 친화적객체지향적
식별자 클래스 어노테이션없음@Embeddable
JPQLselect p.id1, p.id2 from Parent pselect p.id.id1, p.id.id2 from Parent p

3) 식별 관계 매핑

부모 → 자식 → 손자로 PK가 계속 전파되는 구조.

@IdClass — @Id와 @ManyToOne을 같이 사용

@Entity
@IdClass(ChildId.class)
public class Child {
    @Id @ManyToOne
    @JoinColumn(name = "PARENT_ID")
    private Parent parent;

    @Id @Column(name = "CHILD_ID")
    private String childId;
}

@EmbeddedId — @MapsId로 FK와 PK 속성을 연결

@Entity
public class Child {
    @EmbeddedId
    private ChildId id;

    @MapsId("parentId")   // ChildId.parentId 필드에 매핑
    @ManyToOne
    @JoinColumn(name = "PARENT_ID")
    private Parent parent;
}

@Embeddable
public class ChildId implements Serializable {
    private String parentId;  // @MapsId("parentId")로 매핑
    @Column(name = "CHILD_ID")
    private String id;
}
  • @MapsId: FK와 매핑한 연관관계를 기본 키에도 매핑하겠다는 뜻. 1:1 식별 관계에서도 사용 (속성값 생략)

식별 vs 비식별 — 무엇을 선택할까

  • 식별 관계는 자식으로 갈수록 PK 컬럼이 계속 늘어나 조인·SQL이 복잡해지고 인덱스가 커진다
  • 식별 관계는 비즈니스 의미가 있는 자연 키를 조합하는 경우가 많아, 비즈니스 요구사항 변경에 취약하다
  • JPA에서 복합 키는 식별자 클래스를 별도로 만들어야 해 번거롭다
권장 비식별 관계 + Long 타입 대리 키(@GeneratedValue). 필수적 비식별 관계(not null)를 쓰면 내부 조인만 사용할 수 있어 성능상 유리하다.

4. 조인 테이블

테이블 연관관계를 설계하는 방법은 두 가지다.

  • 조인 컬럼: 외래 키 컬럼으로 관리 (@JoinColumn). 선택적 비식별 관계면 FK에 null이 생기고 외부 조인을 써야 한다.
  • 조인 테이블: 별도 테이블(연결 테이블)로 관리 (@JoinTable). null 문제는 없지만 테이블이 하나 늘고 조인도 한 번 더 한다.

@JoinTable 속성

@Entity
public class Parent {
    @Id @GeneratedValue
    @Column(name = "PARENT_ID")
    private Long id;

    @OneToMany
    @JoinTable(
        name = "PARENT_CHILD",
        joinColumns = @JoinColumn(name = "PARENT_ID"),
        inverseJoinColumns = @JoinColumn(name = "CHILD_ID")
    )
    private List<Child> children = new ArrayList<>();
}

관계별 조인 테이블 특징

관계연결 테이블의 유니크 제약
1:1양쪽 FK 컬럼 각각에 유니크 제약
1:NN 쪽 FK 컬럼(CHILD_ID)에 유니크 제약
N:11:N의 방향만 반대, 동일한 구조
N:M두 FK 컬럼을 합친 복합 유니크 제약
연결 테이블에 컬럼을 추가하면 @JoinTable을 쓸 수 없다 수량, 등록일 같은 컬럼이 필요하면 연결 테이블을 별도 엔티티로 승격해서 @ManyToOne 두 개로 풀어야 한다.
권장 기본은 조인 컬럼을 사용하고, 필요할 때만 조인 테이블을 사용한다.

※ Spring Boot 3 이상은 javax.persistence 대신 jakarta.persistence 패키지를 사용한다.
