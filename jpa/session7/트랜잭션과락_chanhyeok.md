# Chapter 16. 트랜잭션과 락, 2차 캐시

## 1. 트랜잭션과 격리 수준

트랜잭션은 ACID(원자성, 일관성, 격리성, 지속성)를 보장해야 한다. 문제는 격리성이다. 완벽히 보장하려면 트랜잭션을 거의 차례대로 실행해야 해서 성능이 크게 떨어진다. 그래서 ANSI 표준은 격리 수준을 4단계로 나눴다.

| 격리 수준 | DIRTY READ | NON-REPEATABLE READ | PHANTOM READ |
| --- | :---: | :---: | :---: |
| READ UNCOMMITTED | O | O | O |
| READ COMMITTED | | O | O |
| REPEATABLE READ | | | O |
| SERIALIZABLE | | | |

- **DIRTY READ**: 커밋하지 않은 데이터를 읽는다. 상대가 롤백하면 존재한 적 없는 데이터를 쓴 셈이 된다.
- **NON-REPEATABLE READ**: 같은 행을 다시 읽었더니 값이 바뀌어 있다.
- **PHANTOM READ**: 같은 조건으로 다시 조회했더니 결과 집합의 행 수가 달라져 있다.

DB는 보통 READ COMMITTED를 기본으로 쓴다. 다만 격리 수준별 동작은 DB마다 다르다. MVCC를 쓰는 MySQL InnoDB는 기본이 REPEATABLE READ인데 일반 SELECT에서는 PHANTOM READ도 보이지 않는다.

## 2. 낙관적 락과 비관적 락

영속성 컨텍스트 덕분에 DB가 READ COMMITTED여도 엔티티는 **애플리케이션 레벨에서 REPEATABLE READ**가 된다. 한 번 조회한 엔티티는 1차 캐시에 있는 같은 인스턴스가 돌아오기 때문이다. 스칼라 값을 직접 조회하면 이 효과가 없다. 더 높은 격리가 필요한 로직에만 락을 쓴다.

| 구분 | 낙관적 락 | 비관적 락 |
| --- | --- | --- |
| 가정 | 대부분 충돌하지 않는다 | 충돌한다, 일단 락부터 건다 |
| 수단 | JPA 버전 관리 (애플리케이션 락) | DB 락 (`select for update`) |
| 충돌을 아는 시점 | 커밋할 때 | 접근하는 즉시 |

### 두 번의 갱신 분실 문제

A와 B가 같은 글을 동시에 수정 화면으로 열고, A가 먼저 저장한 뒤 B가 저장하면 A의 수정이 사라진다. 화면을 연 요청과 저장 요청은 서로 다른 트랜잭션이라 **트랜잭션 범위를 넘어서는 문제**이고, 격리 수준으로는 못 막는다.

선택지는 마지막 커밋만 인정(기본), 최초 커밋만 인정, 충돌 내용 병합(직접 구현) 세 가지다. `@Version`을 쓰면 **최초 커밋만 인정하기**를 쉽게 구현할 수 있다.

## 3. @Version

```java
@Entity
public class Board {
    @Id private String id;
    private String title;

    @Version
    private Long version;
}
```

엔티티를 수정할 때마다 버전이 자동으로 오른다. 플러시할 때 UPDATE의 WHERE 절에 조회 시점의 버전을 넣는다.

```sql
UPDATE BOARD SET TITLE = ?, VERSION = ?   -- 버전 + 1
WHERE ID = ? AND VERSION = ?              -- 조회 시점의 버전
```

다른 트랜잭션이 먼저 버전을 올렸으면 수정 대상이 0건이 되고, JPA는 이를 충돌로 보고 예외를 던진다. 조회할 때 미리 락을 잡지 않고 **확인과 갱신을 UPDATE 한 문장으로** 처리한다. UPDATE 자체는 행 락을 잡지만, 그 락은 커밋까지의 짧은 구간에만 걸린다.

버전이 오르는 경우는 엔티티 값, 임베디드 타입, 값 타입 컬렉션을 수정했을 때다. 연관관계 필드는 **연관관계의 주인**을 수정할 때만 오른다. 벌크 연산은 버전을 무시하므로 `m.version = m.version + 1`로 직접 올려야 한다.

## 4. JPA 낙관적 락

> JPA 추천 전략은 **READ COMMITTED + 낙관적 버전 관리**다.

락은 `LockModeType`으로 건다. 스프링 데이터 JPA에서는 리포지토리 메서드에 `@Lock`을 붙이고, 직접 쓸 때는 `em.find()`나 JPQL의 `setLockMode()`에 넘긴다.

낙관적 락 옵션은 **어디서부터 어디까지 보장하는가**로 구분된다.

| 옵션 | 보장 구간 | 버전 확인 | 막는 것 |
| --- | --- | --- | --- |
| `NONE` (`@Version`만) | 조회부터 **수정 시점**까지 | 수정할 때 UPDATE | 두 번의 갱신 분실 |
| `OPTIMISTIC` | 조회부터 **트랜잭션 끝**까지 | 커밋할 때 SELECT | DIRTY READ, NON-REPEATABLE READ |
| `OPTIMISTIC_FORCE_INCREMENT` | 논리적인 엔티티 묶음 | 커밋할 때 UPDATE로 강제 증가 | 묶음 단위의 갱신 분실 |

- **OPTIMISTIC**: 엔티티를 수정하지 않고 조회만 해도, 커밋할 때 버전이 바뀌었으면 예외가 난다.
- **OPTIMISTIC_FORCE_INCREMENT**: 게시물과 첨부파일에서 첨부파일이 연관관계의 주인이면, 첨부파일만 추가했을 때 게시물 버전은 안 오른다. 이때 게시물 버전을 강제로 올린다. 엔티티도 수정하면 버전이 2 오를 수 있다. 책은 이것을 **DDD Aggregate Root**에 쓸 수 있다고 한다. 루트가 관리하는 엔티티가 바뀌면 루트 버전을 올려 묶음 전체를 버전 관리하는 것이다.

충돌하면 스프링에서는 `ObjectOptimisticLockingFailureException`으로 받는다.

## 5. JPA 비관적 락

DB 락 메커니즘에 의존하고 버전은 쓰지 않는다. 스칼라 조회에도 쓸 수 있고, 수정하는 즉시 충돌을 감지한다.

| 옵션 | 동작 |
| --- | --- |
| `PESSIMISTIC_WRITE` | `select for update`. 일반적인 비관적 락 |
| `PESSIMISTIC_READ` | 공유 락 `for share`. 잘 안 쓴다 |

락을 얻을 때까지 대기하므로 `jakarta.persistence.lock.timeout` 힌트로 타임아웃을 준다. 단, **DB에 따라 동작하지 않을 수 있다.**

## 6. 2차 캐시

DB 접근은 메모리 접근보다 수만 배 이상 비싸다. 1차 캐시는 영속성 컨텍스트 자체라 끌 수 없지만, 트랜잭션이나 요청이 끝나면 사라져서 전체 DB 접근을 크게 줄이지는 못한다. 그래서 애플리케이션 범위의 **2차 캐시(공유 캐시)**를 쓴다.

| 구분 | 1차 캐시 | 2차 캐시 |
| --- | --- | --- |
| 범위 | 영속성 컨텍스트 | 영속성 유닛 (애플리케이션) |
| 돌려주는 것 | 보관한 엔티티 그대로 | **복사본** |
| 동일성 (`a == b`) | 보장 | 영속성 컨텍스트가 다르면 보장 안 함 |

복사본을 주는 이유는 동시성이다. 원본을 공유하면 동시 수정을 막으려고 락을 걸어야 하는데, 락보다 복사가 훨씬 싸다.

### JPA 표준

엔티티에 `@Cacheable`을 붙이고 캐시 모드를 `ENABLE_SELECTIVE`(`@Cacheable` 붙은 것만 캐시)로 두는 게 보통이다. JPA 표준은 **엔티티 캐시만** 정의한다.

### 하이버네이트

| 캐시 | 캐시하는 것 |
| --- | --- |
| 엔티티 캐시 | 엔티티 전체 |
| 컬렉션 캐시 | 연관 컬렉션. 엔티티면 **식별자만** |
| 쿼리 캐시 | 쿼리와 파라미터를 키로 결과. 엔티티면 **식별자만** |

동시성 전략은 `@Cache(usage = ...)`로 고른다.

| 전략 | 설명 |
| --- | --- |
| `READ_ONLY` | 수정 불가. 불변이라 복사 없이 원본을 반환한다 |
| `NONSTRICT_READ_WRITE` | 동시 수정 시 일관성이 깨질 수 있다 |
| `READ_WRITE` | READ COMMITTED 정도의 격리 |

쿼리 캐시는 대상 테이블이 한 번이라도 바뀌면 통째로 무효화된다. 그래서 **변경이 거의 없는 테이블**에만 효과가 있다.

### 쿼리 캐시와 컬렉션 캐시의 함정

쿼리 캐시와 컬렉션 캐시는 식별자만 들고 있어서, 실제 엔티티는 엔티티 캐시에서 하나씩 찾는다. 대상 엔티티에 엔티티 캐시가 없으면 결과 100건에 **SQL이 100번** 나간다. 쿼리 캐시나 컬렉션 캐시를 쓰면 대상 엔티티에 **엔티티 캐시를 꼭 함께** 건다.

## 7. 정리

- 격리 수준이 낮을수록 동시성은 높지만 이상 현상이 생긴다. 영속성 컨텍스트는 READ COMMITTED에서도 엔티티의 반복 가능한 읽기를 제공한다.
- 두 번의 갱신 분실은 트랜잭션 범위 밖의 문제라 `@Version`으로 최초 커밋만 인정한다.
- 낙관적 락 옵션은 보장 구간으로 구분하고, 비관적 락은 DB 락이라 즉시 충돌을 감지하지만 대기와 타임아웃을 고려해야 한다.
- 2차 캐시는 복사본을 돌려주는 애플리케이션 범위 캐시다. 쿼리 캐시는 변경이 드문 테이블에만, 엔티티 캐시와 함께 쓴다.
