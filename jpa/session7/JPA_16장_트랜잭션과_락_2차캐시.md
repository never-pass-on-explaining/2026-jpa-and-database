## 1. 트랜잭션 기초

### 1.1 트랜잭션 ACID

| 속성 | 설명 |
|---|---|
| **원자성 (Atomicity)** | 트랜잭션 내 작업은 모두 성공하거나 모두 실패한다. |
| **일관성 (Consistency)** | 트랜잭션은 항상 일관된 DB 상태를 유지한다. (무결성 제약조건 등) |
| **격리성 (Isolation)** | 동시에 실행되는 트랜잭션들이 서로 영향을 주지 않도록 격리한다. |
| **지속성 (Durability)** | 성공적으로 끝난 트랜잭션의 결과는 영구히 기록된다. |

- 원자성·일관성·지속성은 보장하기 쉽지만, **격리성을 완벽히 보장하려면 트랜잭션을 거의 차례대로 실행**해야 해서 동시성 처리 성능이 크게 떨어진다.
- 그래서 ANSI 표준은 격리 수준을 4단계로 정의한다.

### 1.2 트랜잭션 격리 수준 4단계

격리 수준이 낮을수록 동시성은 높고, 문제는 많아진다.

1. **READ UNCOMMITTED** – 커밋되지 않은 데이터도 읽음
2. **READ COMMITTED** – 커밋된 데이터만 읽음
3. **REPEATABLE READ** – 한 트랜잭션 안에서 같은 데이터를 반복 조회해도 결과가 같음
4. **SERIALIZABLE** – 가장 엄격, 트랜잭션을 순차 실행하는 것과 같은 효과

### 1.3 격리 수준별 문제점

| 격리 수준 | Dirty Read | Non-Repeatable Read | Phantom Read |
|---|:---:|:---:|:---:|
| READ UNCOMMITTED | O | O | O |
| READ COMMITTED | X | O | O |
| REPEATABLE READ | X | X | O |
| SERIALIZABLE | X | X | X |

- **Dirty Read**: 트랜잭션1이 수정 중이고 **커밋하지 않은** 데이터를 트랜잭션2가 읽음. 트랜잭션1이 롤백하면 트랜잭션2는 존재하지 않는 데이터를 읽은 셈 → 정합성 문제
- **Non-Repeatable Read**: 트랜잭션1이 회원 A를 조회 → 트랜잭션2가 회원 A를 수정·커밋 → 트랜잭션1이 다시 조회하면 **다른 값**이 나옴
- **Phantom Read**: 트랜잭션1이 `age > 10` 조건으로 조회 → 트랜잭션2가 조건에 맞는 회원을 **추가**·커밋 → 트랜잭션1이 다시 조회하면 **결과 행 수가 달라짐**

> 💡 **Non-Repeatable Read vs Phantom Read**
> - Non-Repeatable Read: **이미 읽은 행의 값**이 바뀜 (UPDATE/DELETE 원인)
> - Phantom Read: 같은 조건 조회 시 **행이 새로 생김** (INSERT 원인)
> - REPEATABLE READ는 이미 읽은 행만 보호하고 **아직 없는 행은 막지 못해** Phantom Read가 남는다. (단, MySQL InnoDB는 MVCC + 갭 락으로 대부분 방지)

### 1.4 JPA와 격리 수준

- 대부분의 애플리케이션은 성능을 위해 **READ COMMITTED**를 기본으로 사용한다.

  | DB | 기본 격리 수준 |
  |---|---|
  | MySQL / MariaDB (InnoDB) | REPEATABLE READ |
  | PostgreSQL | READ COMMITTED |
  | Oracle | READ COMMITTED |
  | SQL Server | READ COMMITTED |

  > MySQL 계열만 REPEATABLE READ가 기본이다. DB를 바꾸면 같은 코드라도 동시성 동작이 달라질 수 있다.
- JPA는 **영속성 컨텍스트(1차 캐시)** 덕분에 이미 조회한 엔티티를 다시 조회하면 캐시에서 반환하므로, 애플리케이션 레벨에서 **REPEATABLE READ** 효과를 얻는다.
  - 단, 엔티티가 아닌 스칼라 값을 직접 조회하면 영속성 컨텍스트 관리 대상이 아니므로 반복 가능한 읽기가 보장되지 않는다.
- 더 높은 격리가 필요하면 **낙관적 락 / 비관적 락**을 사용한다.

## 2. 낙관적 락 vs 비관적 락 개념

### 2.1 낙관적 락 (Optimistic Lock)

- "트랜잭션 대부분은 충돌하지 않는다"고 **낙관적으로 가정**
- DB 락이 아니라 **JPA가 제공하는 버전 관리 기능**을 사용 → 애플리케이션 레벨 락
- **트랜잭션을 커밋하기 전까지는 충돌을 알 수 없다.**

### 2.2 비관적 락 (Pessimistic Lock)

- "트랜잭션이 충돌한다"고 **비관적으로 가정**하고 **우선 락을 건다**
- **데이터베이스의 락 기능** 사용 — 대표적으로 `SELECT ... FOR UPDATE`

### 2.3 두 번의 갱신 분실 문제 (Second Lost Updates)

> 사용자 A와 B가 동시에 같은 게시글을 수정 → A가 먼저 완료, B가 나중에 완료 → **A의 수정 내용이 사라지고 B의 내용만 남음**

이 문제는 DB 트랜잭션 범위를 넘어서기 때문에 트랜잭션만으로는 해결할 수 없다. 해결 방법 3가지:

| 방법 | 설명 |
|---|---|
| **마지막 커밋만 인정하기** | A의 내용은 무시, 마지막에 커밋한 B의 내용만 인정 (기본 동작) |
| **최초 커밋만 인정하기** | A가 먼저 커밋했으므로 B가 커밋할 때 **오류 발생** |
| **충돌하는 갱신 내용 병합하기** | A와 B의 수정 사항을 병합 (개발자가 직접 구현) |

→ JPA의 **`@Version`** 을 사용하면 **최초 커밋만 인정하기**를 쉽게 구현할 수 있다.

## 3. @Version

### 3.1 사용법

```java
@Entity
public class Board {

    @Id
    private String id;
    private String title;

    @Version
    private Integer version;
}
```

- 적용 가능 타입: `Long(long)`, `Integer(int)`, `Short(short)`, `Timestamp`
- 엔티티를 수정할 때마다 버전이 하나씩 **자동 증가**
- 수정 시점에 조회 시점의 버전과 다르면 **예외 발생**

```java
// 트랜잭션 1: 조회 (title="제목A", version=1)
Board board = em.find(Board.class, id);

// --- 이 사이에 트랜잭션 2가 같은 게시물을 수정 → version=2 ---

board.setTitle("제목B");
save(board);
tx.commit(); // 예외 발생! DB version=2, 엔티티 version=1
```

### 3.2 버전 정보 비교 방법

엔티티 수정 후 플러시 시점에 아래 UPDATE 쿼리를 실행한다.

```sql
UPDATE BOARD
SET
    TITLE = ?,
    VERSION = ?        -- 버전 + 1 증가
WHERE
    ID = ?
    AND VERSION = ?    -- 버전 비교
```

- DB 버전과 엔티티 버전이 같으면 → 수정 + 버전 증가
- 이미 다른 트랜잭션이 버전을 올렸다면 → WHERE 조건 불일치로 수정 대상 0건 → **`OptimisticLockException`** 발생

### 3.3 버전이 증가하는 조건

- 엔티티의 **값 타입(임베디드 포함)** 이 수정되면 버전 증가
- **연관관계 필드**는 외래 키를 관리하는 **연관관계의 주인 필드**를 수정할 때만 버전 증가
- `@Version`으로 추가한 필드는 **JPA가 직접 관리** → 개발자가 임의로 수정하면 안 됨 (벌크 연산 제외)

### 3.4 주의점

- **벌크 연산은 버전을 무시**한다. 버전을 증가시키려면 직접 명시해야 한다.

```sql
UPDATE Member m SET m.name = '변경', m.version = m.version + 1
```

## 4. JPA 락 사용

> 💡 JPA 추천 전략: **READ COMMITTED 격리 수준 + 낙관적 버전 관리**
> (두 번의 갱신 분실 문제 예방)

### 4.1 락을 거는 위치

```java
// 1) 조회하면서 즉시 락
Board board = em.find(Board.class, id, LockModeType.OPTIMISTIC);

// 2) 필요할 때 락
Board board = em.find(Board.class, id);
em.lock(board, LockModeType.OPTIMISTIC);
```

락을 적용할 수 있는 위치:
- `EntityManager.lock()`, `EntityManager.find()`, `EntityManager.refresh()`
- `Query.setLockMode()` (TypeQuery 포함)
- `@NamedQuery`의 `lockMode` 속성
- (Spring Data JPA) 리포지토리 메서드에 `@Lock`

### 4.2 LockModeType 종류

| 락 모드 | 타입 | 설명 |
|---|---|---|
| 낙관적 락 | `OPTIMISTIC` | 낙관적 락 사용 |
| 낙관적 락 | `OPTIMISTIC_FORCE_INCREMENT` | 낙관적 락 + 버전 정보 강제 증가 |
| 비관적 락 | `PESSIMISTIC_READ` | 비관적 락, 읽기 락 사용 |
| 비관적 락 | `PESSIMISTIC_WRITE` | 비관적 락, 쓰기 락 사용 |
| 비관적 락 | `PESSIMISTIC_FORCE_INCREMENT` | 비관적 락 + 버전 정보 강제 증가 |
| 기타 | `NONE` | 락 없음 |
| 기타 | `READ` | JPA 1.0 호환 기능, `OPTIMISTIC`과 같음 |
| 기타 | `WRITE` | JPA 1.0 호환 기능, `OPTIMISTIC_FORCE_INCREMENT`와 같음 |

### 4.3 낙관적 락 옵션

> JPA의 낙관적 락은 **버전(`@Version`)을 사용**한다. 따라서 버전이 있어야 한다.

#### NONE
- 락 옵션 없이도 엔티티에 `@Version`만 있으면 낙관적 락 적용
- **용도**: 조회한 엔티티를 수정할 때, 다른 트랜잭션에 의해 변경(삭제)되지 않아야 함
- **동작**: 엔티티 **수정 시** 버전 체크 + 버전 증가
- **효과**: 두 번의 갱신 분실 문제 예방

#### OPTIMISTIC
- `NONE`은 엔티티를 수정해야 버전을 체크하지만, `OPTIMISTIC`은 **엔티티를 조회만 해도** 버전을 체크
- **용도**: 조회한 엔티티는 트랜잭션이 끝날 때까지 다른 트랜잭션에 의해 변경되지 않아야 함
- **동작**: **트랜잭션 커밋 시** 버전 정보를 조회(SELECT)해서 현재 엔티티 버전과 같은지 검증
- **효과**: **Dirty Read, Non-Repeatable Read 방지**

```java
// 트랜잭션 1: 조회 (version=1)
Board board = em.find(Board.class, id, LockModeType.OPTIMISTIC);

// --- 중간에 트랜잭션 2가 수정 → version=2 ---

tx.commit(); // 수정하지 않았지만 커밋 시 버전 검증 → 예외 발생
```

#### OPTIMISTIC_FORCE_INCREMENT
- 낙관적 락 + **버전 정보 강제 증가**
- **용도**: 논리적인 단위의 엔티티 묶음을 관리
  - 예) 게시물(Board)과 첨부파일(Attachment)이 1:N, 첨부파일만 추가해도 **게시물의 버전도 올려야** 할 때
  - 연관관계 주인이 아닌 쪽(게시물)은 원래 버전이 증가하지 않음 → 강제 증가 필요
- **동작**: 엔티티를 수정하지 않아도 **트랜잭션 커밋 시 UPDATE로 버전 증가**, 이때 버전 검증
  - 엔티티를 수정하면 수정 시 버전 UPDATE가 추가로 발생 → **최대 버전 2 증가** 가능
- **효과**: 강제로 버전을 증가시켜 **논리적 단위의 엔티티 묶음을 버전 관리**

### 4.4 비관적 락 옵션

- DB 트랜잭션 락 메커니즘에 의존 (주로 `SELECT ... FOR UPDATE`)
- 버전 정보는 사용하지 않음 (`@Version` 불필요)
- 특징
  - **엔티티가 아닌 스칼라 타입을 조회할 때도 사용 가능**
  - 데이터를 수정하는 즉시 트랜잭션 충돌 감지 가능

#### PESSIMISTIC_WRITE (일반적인 비관적 락)
- **용도**: 데이터베이스에 쓰기 락을 건다
- **동작**: `SELECT ... FOR UPDATE`
- **효과**: **Non-Repeatable Read 방지**, 락이 걸린 로우는 다른 트랜잭션이 수정할 수 없음

#### PESSIMISTIC_READ
- 데이터를 반복 읽기만 하고 수정하지 않는 용도로 락을 걸 때 사용 (잘 쓰지 않음)
- DB 대부분은 방언에 의해 `PESSIMISTIC_WRITE`로 동작
  - MySQL: `LOCK IN SHARE MODE`
  - PostgreSQL: `FOR SHARE`

#### PESSIMISTIC_FORCE_INCREMENT
- 비관적 락 중 **유일하게 버전 정보를 사용**, 버전 강제 증가
- 하이버네이트는 `nowait`를 지원하는 DB에 대해 `FOR UPDATE NOWAIT` 적용
  - 오라클: `FOR UPDATE NOWAIT`
  - PostgreSQL: `FOR UPDATE NOWAIT`
  - `nowait` 미지원 DB: `FOR UPDATE`

### 4.5 비관적 락과 타임아웃

- 비관적 락을 사용하면 락을 획득할 때까지 트랜잭션이 **대기**
- 무한정 기다릴 수 없으므로 타임아웃 설정 가능

```java
Map<String, Object> properties = new HashMap<>();
properties.put("javax.persistence.lock.timeout", 10000); // 10초

Board board = em.find(Board.class, "boardId",
        LockModeType.PESSIMISTIC_WRITE, properties);
```

- 10초간 대기해도 응답이 없으면 `javax.persistence.LockTimeoutException` 발생
- **DB 특성에 따라 동작하지 않을 수 있음**

### 4.6 락 관련 예외

| 구분 | 예외 |
|---|---|
| 낙관적 락 | `javax.persistence.OptimisticLockException` (JPA) |
| | `org.hibernate.StaleObjectStateException` (하이버네이트) |
| | `org.springframework.orm.ObjectOptimisticLockingFailureException` (스프링) |
| 비관적 락 | `javax.persistence.PessimisticLockException` (JPA) |
| | `org.springframework.dao.PessimisticLockingFailureException` (스프링) |
| 타임아웃 | `javax.persistence.LockTimeoutException` |

## 5. 1차 캐시와 2차 캐시

> 💡 **한 줄 비유**
> - **1차 캐시 = 내 책상 위 메모지**: 요청 하나 동안만 쓰고 버림. 같은 요청 안에서 중복 조회를 막고 동일성(`a == b`)과 변경 감지의 기반이 됨. JPA가 자동으로 해줌.
> - **2차 캐시 = 사무실 공용 캐비닛**: 모든 요청이 공유하고 서버가 꺼질 때까지 유지. 요청 간 DB 접근 자체를 줄임. 직접 설정해야 하고, 캐시가 옛날 값을 들고 있지 않도록 신경 써야 함.
> - 1차 캐시는 요청이 끝나면 사라져서 전체 DB 부하는 거의 못 줄인다. 그래서 2차 캐시가 필요하다.

### 5.1 1차 캐시

- **영속성 컨텍스트 내부**의 엔티티 보관 저장소
- 일반적인 웹 애플리케이션 환경(트랜잭션 범위 영속성 컨텍스트)에서는 **트랜잭션을 시작하고 종료할 때까지만 유효**
  - OSIV를 사용해도 클라이언트 요청이 들어오고 끝날 때까지만 유효
- 따라서 애플리케이션 전체로 보면 **DB 접근 횟수를 획기적으로 줄이지는 못함**

**1차 캐시 특징**
- 같은 엔티티가 있으면 **해당 엔티티를 그대로 반환** → **객체 동일성(a == b) 보장**
- 기본적으로 영속성 컨텍스트 범위의 캐시 (컨테이너 환경: 트랜잭션 범위, OSIV: 요청 범위)

### 5.2 2차 캐시 (공유 캐시)

- **애플리케이션 범위**의 캐시
- 애플리케이션을 종료할 때까지 캐시 유지 (분산 캐시·클러스터링 환경이면 더 오래 유지 가능)
- 동작 흐름
  1. 영속성 컨텍스트는 엔티티가 필요하면 **2차 캐시를 먼저 조회**
  2. 2차 캐시에 없으면 DB 조회
  3. 결과를 **2차 캐시에 보관**
  4. 2차 캐시는 자신이 보관한 엔티티를 **복사해서 반환**

**왜 복사본을 반환할까?**
- 2차 캐시는 동시성을 극대화하기 위해 캐시한 객체를 직접 반환하지 않고 **복사본을 반환**
- 원본을 그대로 반환하면 여러 곳에서 같은 객체를 동시에 수정하는 문제 발생 → 해결하려면 락이 필요해 동시성이 떨어짐
- 락에 비하면 **객체 복사 비용이 훨씬 저렴**

**2차 캐시 특징**
- 영속성 유닛 범위의 캐시
- 조회한 객체를 그대로 반환하지 않고 **복사본을 만들어 반환**
- **DB 기본 키 기준**으로 캐시하지만, 영속성 컨텍스트가 다르면 **객체 동일성(a == b)은 보장하지 않음**

| 구분 | 1차 캐시 | 2차 캐시 |
|---|---|---|
| 범위 | 영속성 컨텍스트 (트랜잭션/요청) | 애플리케이션 (영속성 유닛) |
| 반환 | 원본 엔티티 | 복사본 |
| 동일성 보장 | O | X (다른 영속성 컨텍스트 간) |
| 공유 | X | O |

### 5.3 JPA 2차 캐시 기능

JPA 2.0부터 캐시 표준 정의 (여러 구현체가 공통으로 사용하는 부분만 표준화)

#### 캐시 모드 설정

```java
@Cacheable
@Entity
public class Member {

    @Id @GeneratedValue
    private Long id;
}
```

```xml
<!-- persistence.xml -->
<persistence-unit name="test">
    <shared-cache-mode>ENABLE_SELECTIVE</shared-cache-mode>
</persistence-unit>
```

```xml
<!-- 스프링 프레임워크 XML 설정 -->
<bean id="entityManagerFactory"
      class="org.springframework.orm.jpa.LocalContainerEntityManagerFactoryBean">
    <property name="sharedCacheMode" value="ENABLE_SELECTIVE"/>
</bean>
```

**SharedCacheMode 캐시 모드**

| 캐시 모드 | 설명 |
|---|---|
| `ALL` | 모든 엔티티 캐시 |
| `NONE` | 캐시 사용 안 함 |
| `ENABLE_SELECTIVE` | `@Cacheable(true)` 설정한 엔티티만 캐시 **(보통 이걸 사용)** |
| `DISABLE_SELECTIVE` | 모든 엔티티 캐시, `@Cacheable(false)`로 명시한 엔티티만 제외 |
| `UNSPECIFIED` | JPA 구현체가 정의한 설정 따름 |

#### 캐시 조회·저장 방식 설정

캐시를 무시하고 DB를 직접 조회하거나 캐시를 갱신하려면 캐시 조회 모드와 보관 모드 사용

```java
em.setProperty("javax.persistence.cache.retrieveMode", CacheRetrieveMode.BYPASS);
```

| 프로퍼티 | 옵션 | 설명 |
|---|---|---|
| `javax.persistence.cache.retrieveMode` (조회 모드) | `USE` | 캐시에서 조회 (기본값) |
| | `BYPASS` | 캐시 무시, DB 직접 접근 |
| `javax.persistence.cache.storeMode` (보관 모드) | `USE` | 조회한 데이터를 캐시에 저장. 이미 있으면 최신 상태로 갱신하지 않음. 트랜잭션 커밋 시 등록·수정한 엔티티도 저장 (기본값) |
| | `BYPASS` | 캐시에 저장하지 않음 |
| | `REFRESH` | `USE` 전략 + DB에서 조회한 엔티티를 **최신 상태로 다시 캐시** |

캐시 모드는 `EntityManager.setProperty()`로 엔티티 매니저 단위, 또는 `find()`, `refresh()`에 설정 가능, `Query.setHint()`(TypeQuery 포함)에도 사용 가능

```java
Map<String, Object> param = new HashMap<>();
param.put("javax.persistence.cache.retrieveMode", CacheRetrieveMode.BYPASS);
param.put("javax.persistence.cache.storeMode", CacheStoreMode.BYPASS);

em.find(TestEntity.class, id, param);

em.createQuery("select e from TestEntity e where e.id = :id", TestEntity.class)
  .setParameter("id", id)
  .setHint("javax.persistence.cache.retrieveMode", CacheRetrieveMode.BYPASS)
  .setHint("javax.persistence.cache.storeMode", CacheStoreMode.BYPASS)
  .getSingleResult();
```

#### JPA 캐시 관리 API

```java
Cache cache = emf.getCache();
boolean contains = cache.contains(TestEntity.class, testEntity.getId());
```

```java
public interface Cache {
    boolean contains(Class cls, Object primaryKey); // 캐시에 엔티티가 있는지
    void evict(Class cls, Object primaryKey);       // 특정 식별자 엔티티 제거
    void evict(Class cls);                          // 해당 엔티티 전체 제거
    void evictAll();                                // 모든 캐시 데이터 제거
    <T> T unwrap(Class<T> cls);                     // 구현체의 캐시 인터페이스 반환
}
```

> JPA 표준 캐시 기능은 여기까지. 실제 캐시 적용은 구현체 설정이 필요하다.

### 5.4 하이버네이트 2차 캐시

> 책에서는 EHCACHE 설정 예제를 다루지만 Hibernate 4.x 기준이다. Hibernate 6부터는 JCache(`hibernate-jcache`)로 바뀌었고, 실무에서는 Spring Cache(`@Cacheable`) + Redis로 서비스 레이어에서 캐시하는 경우가 더 많다. 여기서는 개념과 함정만 정리한다.

#### 캐시 종류

| 캐시 | 설명 |
|---|---|
| **엔티티 캐시** | 엔티티 단위로 캐시. 식별자로 조회하거나 연관 엔티티를 로딩할 때 사용 |
| **컬렉션 캐시** | 엔티티와 연관된 컬렉션을 캐시. **식별자 값만 캐시** |
| **쿼리 캐시** | 쿼리 + 파라미터를 키로 결과를 캐시. 결과가 엔티티면 **식별자 값만 캐시** |

```java
@Cacheable
@Cache(usage = CacheConcurrencyStrategy.READ_WRITE)   // 하이버네이트 전용
@Entity
public class ParentMember {
    @Id @GeneratedValue
    private Long id;

    @Cache(usage = CacheConcurrencyStrategy.READ_WRITE) // 컬렉션 캐시
    @OneToMany(mappedBy = "parentMember")
    private List<ChildMember> childMembers = new ArrayList<>();
}
```

#### 캐시 동시성 전략 (CacheConcurrencyStrategy)

| 전략 | 설명 |
|---|---|
| `READ_ONLY` | 읽기 전용. 등록·삭제 가능, **수정 불가**. 복사 없이 원본 반환 → 가장 빠름 |
| `NONSTRICT_READ_WRITE` | 엄격하지 않은 읽고 쓰기. 동시 수정 시 일관성이 깨질 수 있음 |
| `READ_WRITE` | 읽고 쓰기 가능. **READ COMMITTED** 수준 격리 보장 |
| `TRANSACTIONAL` | 컨테이너 관리 환경용. **REPEATABLE READ** 수준 격리 |

#### ⚠️ 쿼리 캐시·컬렉션 캐시의 함정

쿼리 캐시와 컬렉션 캐시는 **식별자만 캐시**하고, 실제 엔티티는 식별자로 **엔티티 캐시**에서 하나씩 찾는다.

```
1. select m from Member m → 쿼리 캐시 적중 (식별자 100개)
2. 식별자로 엔티티 캐시 조회
3. Member에 엔티티 캐시가 없으면 → DB에서 한 건씩 조회
4. 결과: SQL 100번 실행 (N+1)
```

→ **쿼리 캐시나 컬렉션 캐시를 쓰면 대상 엔티티에 반드시 엔티티 캐시도 적용해야 한다.**

또한 쿼리 캐시는 대상 테이블이 하나라도 변경되면 무효화되므로, **변경이 거의 없는 테이블**에만 효과적이다.

## 6. 정리

- **트랜잭션 격리 수준**은 4단계가 있으며, 격리 수준이 낮을수록 동시성은 증가하지만 문제(Dirty Read, Non-Repeatable Read, Phantom Read)가 발생한다.
- 영속성 컨텍스트는 **애플리케이션 레벨의 REPEATABLE READ**를 제공한다.
- JPA 추천 전략: **READ COMMITTED + 낙관적 버전 관리**
- **낙관적 락**은 애플리케이션 레벨에서 버전(`@Version`)으로 동작하며, 충돌은 커밋 시점에 알 수 있다.
  - `NONE` → 수정 시 버전 체크 / `OPTIMISTIC` → 조회만 해도 커밋 시 버전 체크 / `OPTIMISTIC_FORCE_INCREMENT` → 논리적 묶음 버전 관리
- **비관적 락**은 DB 락(`SELECT ... FOR UPDATE`)을 사용하며, 스칼라 조회에도 쓸 수 있고 즉시 충돌을 감지한다. 타임아웃 설정이 가능하다.

**락 선택 기준**

| 상황 | 추천 |
|---|---|
| 충돌이 드물고 성능이 중요 | 낙관적 락 (`@Version`) |
| 충돌이 잦고, 실패 후 재시도 비용이 큼 (예: 재고, 좌석 예약) | 비관적 락 (`PESSIMISTIC_WRITE`) |
| 연관 엔티티 변경 시 부모까지 버전 관리 | `OPTIMISTIC_FORCE_INCREMENT` |

- **2차 캐시**는 애플리케이션 범위 캐시로 DB 조회 횟수를 줄여 성능을 높인다. 동시성을 위해 복사본을 반환한다.
  - 변경이 적고 자주 조회하는 데이터(코드성 데이터 등)에 적합
  - 쿼리 캐시·컬렉션 캐시를 쓸 때는 반드시 대상 엔티티에 **엔티티 캐시**를 함께 적용할 것
