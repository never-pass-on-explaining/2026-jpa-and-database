## 1. 트랜잭션 범위의 영속성 컨텍스트

- 스프링 같은 컨테이너 환경은 **트랜잭션 범위의 영속성 컨텍스트** 전략을 기본으로 사용한다.
  - 트랜잭션이 시작될 때 영속성 컨텍스트가 생성되고, 트랜잭션이 끝날 때 함께 종료된다.
- 보통 서비스 계층에 `@Transactional`을 붙여 트랜잭션을 시작한다.
  - 메서드가 정상 종료되면 커밋 직전에 플러시하고, 예외가 발생하면 롤백한다.
- **트랜잭션이 같으면 같은 영속성 컨텍스트를 사용한다.**
  - 여러 리포지토리에서 `EntityManager`를 주입받아 사용해도 같은 영속성 컨텍스트에 접근한다.
- **트랜잭션이 다르면 다른 영속성 컨텍스트를 사용한다.**
  - 같은 `EntityManager`를 주입받더라도 스레드마다 다른 트랜잭션, 다른 영속성 컨텍스트가 할당된다.
  - 따라서 멀티스레드 환경에서도 안전하다.

## 2. 준영속 상태와 지연 로딩

### 문제

컨트롤러와 뷰 같은 프레젠테이션 계층에는 트랜잭션이 없으므로, 이 계층에서 다루는 엔티티는 **준영속 상태**다.

- **변경 감지 불가**: 프레젠테이션 계층에서 엔티티를 수정해도 DB에 반영되지 않는다.
  - 오히려 바람직하다. 데이터 변경은 비즈니스 계층의 책임이기 때문이다.
- **지연 로딩 불가**: 초기화되지 않은 프록시에 접근하면 예외가 발생한다.
  - 하이버네이트 구현체에서는 `LazyInitializationException`이 발생한다.

### 해결 방법

준영속 상태의 지연 로딩 문제는 두 갈래로 해결한다.

1. 뷰가 필요한 엔티티를 **미리 로딩**해 둔다.
2. OSIV를 사용해 엔티티를 **항상 영속 상태로 유지**한다. (3절)

미리 로딩하는 방법은 다음과 같다.

#### 1) 글로벌 페치 전략 수정

```java
@ManyToOne(fetch = FetchType.EAGER)
private Member member;
```

- 단점: 사용하지 않는 엔티티까지 로딩한다.
- 단점: JPQL을 사용할 때 **N+1 문제**가 발생한다.
  - JPQL은 글로벌 페치 전략을 참고하지 않고 쿼리를 그대로 SQL로 만든다.
  - 그래서 즉시 로딩 대상을 조회 결과 수만큼 추가로 조회한다.

#### 2) JPQL 페치 조인

```sql
select o from Order o join fetch o.member
```

- N+1 문제를 해결하는 가장 현실적인 방법이다.
- 단점: 화면에 맞춘 리포지토리 메서드가 늘어난다.
  - 예: `findOrder()`, `findOrderWithMember()`
  - 결과적으로 프레젠테이션 계층이 데이터 접근 계층을 논리적으로 침범하게 된다.
- 무분별하게 최적화하기보다 적절히 타협하는 것이 좋다.

#### 3) 강제로 초기화

- 핵심: 영속성 컨텍스트가 닫히기 전에 프록시에 한 번 접근해, 실제 데이터를 미리 채워 둔다.
- 프록시는 처음 값에 접근하는 순간 영속성 컨텍스트를 통해 DB를 조회한다.
  - 컨트롤러에서는 영속성 컨텍스트가 이미 닫혀 있어 조회에 실패한다.
  - 그래서 트랜잭션이 살아 있는 서비스 계층에서 미리 접근한다.

```java
@Transactional
public Order findOrder(Long id) {
    Order order = orderRepository.findOne(id);
    order.getMember().getName(); // 이 시점에 SELECT 실행 → 프록시 초기화
    return order;
}
```

- `getName()`의 반환값은 쓰지 않는다. 프록시를 깨우기 위한 호출일 뿐이다.
  - 의도를 명확히 하려면 하이버네이트의 `Hibernate.initialize(order.getMember())`를 사용한다.
- 한 번 초기화된 프록시는 영속성 컨텍스트가 닫힌 뒤에도 채워진 데이터를 그대로 읽을 수 있다.
- 단점: 뷰가 어떤 데이터를 필요로 하는지 서비스 계층이 알아야 한다.
  - 화면이 바뀌면 서비스 코드도 함께 고쳐야 한다.
  - 결국 프레젠테이션 계층의 관심사가 서비스 계층으로 새어 들어온다.
  - 그래서 이 초기화 책임을 FACADE 계층으로 옮기는 방법이 나온다.

#### 4) FACADE 계층 추가

- 프레젠테이션 계층과 서비스 계층 사이에 FACADE 계층을 두고, 이곳에서 트랜잭션을 시작해 프록시를 초기화한다.
- 효과: 두 계층 사이의 논리적 의존성을 분리하고, 서비스 계층은 비즈니스 로직에 집중할 수 있다.
- 단점: 계층이 하나 더 늘어난다.
  - FACADE에는 서비스를 단순히 호출만 하는 위임 코드가 많아진다.

### 근본 원인

**엔티티를 프레젠테이션 계층에서 사용하기 때문에** 지연 로딩 문제가 발생한다. 이 문제를 정면으로 해결하는 것이 OSIV다.

## 3. OSIV (Open Session In View)

영속성 컨텍스트를 뷰 렌더링이 끝나는 시점까지 열어 두는 방식이다.
(하이버네이트에서는 OSIV, JPA에서는 OEIV라고 부르지만 관례상 OSIV로 통칭한다.)

### 요청 당 트랜잭션 방식의 OSIV (과거 방식)

- 서블릿 필터나 인터셉터에서 요청이 들어올 때 트랜잭션을 시작하고, 요청이 끝날 때 트랜잭션을 종료한다.
- 문제: 프레젠테이션 계층이 엔티티를 수정할 수 있고, 수정한 내용이 DB에 반영된다.
  - 예: 화면 표시용으로 이름을 마스킹 처리했는데, 그 값이 DB에 저장되어 버린다.
- 이를 막기 위해 다음과 같은 방법을 썼지만, 모두 코드량이 늘어나는 단점이 있다.
  - 엔티티를 읽기 전용 인터페이스로 제공
  - 엔티티를 래핑
  - DTO만 반환

### 스프링 OSIV: 비즈니스 계층 트랜잭션

영속성 컨텍스트는 요청 전체 동안 유지하되, **트랜잭션은 비즈니스 계층에서만 사용**한다.

- 필터 방식: `OpenEntityManagerInViewFilter`
- 인터셉터 방식: `OpenEntityManagerInViewInterceptor`

**동작 흐름**

1. 요청이 들어오면 영속성 컨텍스트를 생성한다. 트랜잭션은 시작하지 않는다.
2. 서비스 계층에서 트랜잭션을 시작하면, 1에서 생성한 영속성 컨텍스트를 사용한다.
3. 서비스 계층이 끝나면 트랜잭션을 커밋하고 플러시한다. 영속성 컨텍스트는 종료하지 않는다.
4. 컨트롤러와 뷰에서는 엔티티가 여전히 영속 상태다.
   - 지연 로딩이 가능하다. (트랜잭션 없이 읽기)
5. 요청이 끝나면 영속성 컨텍스트를 종료한다. 이때 플러시는 하지 않는다.

**트랜잭션 없이 읽기 (Nontransactional reads)**

- 엔티티를 변경하지 않고 조회만 할 때는 트랜잭션이 없어도 된다.
  - 프록시 초기화도 조회에 해당한다.
- 프레젠테이션 계층에서 엔티티를 수정해도 트랜잭션이 없어 플러시되지 않는다.
  - 강제로 `flush()`를 호출하면 `TransactionRequiredException`이 발생한다.

### 주의사항

- 프레젠테이션 계층에서 엔티티를 수정한 직후 같은 요청 안에서 트랜잭션을 시작하는 서비스 계층을 호출하면 문제가 생긴다.
  - 트랜잭션이 커밋될 때 플러시가 일어나 **수정한 내용이 DB에 반영된다.**
- 해결: 비즈니스 로직을 먼저 모두 호출한 뒤 엔티티를 변경한다.

### 정리

| 항목 | 내용 |
|---|---|
| 특징 | 하나의 영속성 컨텍스트를 요청 전체에서 공유하고, 프레젠테이션 계층은 트랜잭션 없이 읽기만 가능 |
| 장점 | 엔티티가 계속 영속 상태라 지연 로딩 문제가 사라지고, FACADE나 강제 초기화가 필요 없음 |
| 단점 | 같은 요청의 여러 트랜잭션이 영속성 컨텍스트를 공유함 |
| 단점 | 프레젠테이션 계층에서 수정 후 트랜잭션을 시작하면 수정 내용이 반영될 수 있음 |
| 단점 | 지연 로딩 SQL이 프레젠테이션 계층에서 실행되므로 성능 튜닝 시 확인 범위가 넓어짐 |
| 한계 | 같은 JVM 안에서만 동작하므로 원격 호출(JSON API 등)에서는 의미가 없음 |

- 원격 API는 엔티티를 그대로 노출하기보다 **DTO로 변환해 반환**하는 것이 낫다.
  - 엔티티를 노출하면 엔티티 변경이 곧 API 스펙 변경으로 이어지기 때문이다.

## 4. 너무 엄격한 계층

- OSIV를 사용하면 영속성 컨텍스트가 프레젠테이션 계층까지 살아 있다.
  - 따라서 컨트롤러에서 리포지토리를 직접 호출해도 지연 로딩 문제가 없다.
- 단순 조회 화면이라면 서비스 계층을 거치지 않고 리포지토리를 직접 호출하는 것도 고려할 수 있다.
  - 계층을 지나치게 엄격하게 나누기보다 유연하게 설계하자는 관점이다.

---

## 5. 정리

- 스프링 컨테이너는 기본적으로 **트랜잭션 범위의 영속성 컨텍스트** 전략을 사용한다.
- 트랜잭션이 없는 프레젠테이션 계층에서는 엔티티가 **준영속 상태**가 되어 지연 로딩에 실패한다.
- 해결책은 두 가지다.
  - **미리 로딩**: 글로벌 페치 전략 수정, 페치 조인, 강제 초기화, FACADE
  - **OSIV 사용**
- **스프링 OSIV**는 영속성 컨텍스트를 요청 끝까지 유지하면서 트랜잭션은 비즈니스 계층에만 둔다.
  - 그래서 프레젠테이션 계층에서 지연 로딩은 되지만, 데이터 수정은 막힌다.
- OSIV는 같은 JVM 안에서만 유효하며, 원격 API에서는 DTO를 사용한다.
