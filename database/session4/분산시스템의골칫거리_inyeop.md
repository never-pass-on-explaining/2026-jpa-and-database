
### 단일 시스템과 분산 시스템의 차이

- 단일 시스템: 하드웨어가 정상적으로 동작한다면 같은 연산은 항상 같은 결과를 낸다.
- 분산 시스템: 여러 노드가 네트워크를 통해 통신하므로, 네트워크 지연이나 노드 장애 등으로 결과를 예측하기 어렵다.

### 부분 장애(Partial Failure)

분산 시스템에서는 일부 노드나 네트워크에 장애가 발생해도 나머지 시스템은 정상적으로 동작할 수 있다. 이처럼 시스템의 일부에서만 발생하는 장애를 부분 장애라고 한다.

따라서 분산 시스템을 설계할 때는 부분 장애를 고려하고, 일부 구성 요소에 장애가 발생하더라도 애플리케이션이 올바르게 동작하도록 내결함성(Fault Tolerance) 을 확보해야 한다.

> 내결함성: 일부 구성 요소에 장애가 발생하더라도 장애를 우회·격리하거나 감지·복구하여 시스템이 정상적으로 동작하도록 하는 능력.

### 부분 장애가 발생할 수 있는 세 가지 영역

- 네트워크: 메시지 지연, 유실, 응답 누락
- 시간: 시계 오차, 시간 동기화 문제
- 프로세스: 프로세스 중단, 응답 지연

## 신뢰할 수 없는 네트워크

### 왜 신뢰성이 없나?

분산 시스템에서는 네트워크를 통해 다른 노드에 요청을 보내고 응답을 기다린다. 이 과정에서 다음과 같은 문제가 발생할 수 있다.

- 패킷 유실: 요청 또는 응답이 전달되지 않음
- 네트워크 지연: 패킷이 큐에서 대기하거나 전송 과정에서 늦게 도착함
- 상대 노드 장애: 상대 노드가 중단되거나 응답하지 않음
- 응답 유실: 요청은 처리됐지만 응답이 전달되지 않음

패킷이 언제 도착할지, 또는 아예 도착하지 않을지 보장할 수 없는 네트워크를 비동기 패킷 네트워크(Asynchronous Packet Network) 라고 한다.

### 재시도와 타임아웃

응답이 없을 때는 상대 노드가 장애 상태인지, 단순히 응답이 지연되는 것인지 확실하게 판단할 수 없다.

따라서 일정 시간 동안 응답을 기다린 뒤, 응답이 없으면 타임아웃(Timeout) 으로 처리한다. 필요하다면 재시도할 수도 있다.

타임아웃 설정에 따른 문제

너무 길면
- 장애를 감지하는 데 오랜 시간이 걸린다.
- 사용자가 응답 지연이나 오류를 경험할 수 있다.

너무 짧으면
- 일시적으로 느려진 노드를 장애로 오인할 수 있다.
- 다른 노드가 같은 작업을 넘겨받아 중복 실행할 수 있다.
- 부하가 다른 노드로 전파되어 연쇄 장애가 발생할 수 있다.

### 타임아웃은 어떻게 설정해야 할까?

타임아웃에는 모든 상황에 적용할 수 있는 정답이 없다.

응답 시간이 일정하지 않기 때문에 응답 시간을 반복 측정해 분포를 파악하고, p99와 같은 백분위수를 기준으로 타임아웃을 설정할 수 있다.


## 신뢰성 없는 시계

애플리케이션은 다양한 작업을 수행하기 위해 시계를 사용한다.

- 요청의 타임아웃 여부 판단
- 지난 5분간 평균 초당 응답 수 계산
- 사용자가 서비스에 머문 시간 측정
- 특정 날짜와 시각에 알람 전송
- 로그에 오류 발생 시각 기록

이 중 경과 시간을 측정하는 작업과 실제 시각을 알아야 하는 작업은 서로 다른 종류의 시계를 필요로 한다.

### 왜 신뢰성이 없나?
분산 시스템에서는 노드마다 자체적인 시계를 가지고 있다. 따라서 서로 다른 노드의 시각을 비교해 이벤트의 순서를 판단할 때 문제가 발생할 수 있다.

컴퓨터는 수정 발진기 등의 하드웨어를 이용해 시간의 흐름을 측정한다. 하지만 이 장치는 완벽하지 않으며, 각 노드의 시계가 서로 정확하게 일치한다는 보장도 없다.

* cpu/메인보드에는 일정 주기로 진동하는 수정 발진기가 있음
* 부팅하는 순간부터 카운트가 올라간다.
* OS가 이 카운터를 읽어서 나노초 단위로 환산

### 시계의 종류
현대 컴퓨터는 목적에 따라 사용하는 두 종류의 시계를 제공한다.

**일 기준 시계 (time-of-day clock)**
* 현재 날짜와 시각을 반환하는 시계
* 부팅할 때 현재 시각을 읽고, 그 뒤로는 수정 발진기의 틱을 세서 현재 시각을 계산
* 시각 기록, 로그, 특정 시점의 알람 등에 사용한다.

```kotlin
val now = LocalDateTime.now() // 2026-10-12T16:35 같은 형태
```

**단조 시계 (monotonic clock)**
* 임의의 기준점 이후 경과 시간을 반환하는 시계
* 시각을 물어보면 OS가 수정 발진기 카운터를 반환
* 값 자체는 의미가 없고 두 값의 차이만 의미가 있다. 노드 간 비교는 불가능
* 타임아웃, 응답 시간 같은 경과 시간 측정에 사용

```kotlin
val start = System.nanoTime()
// 작업 수행
val elapsedNanos = System.nanoTime() - start  // 항상 0 이상
```

### 드리프트(Clock Drift)

수정 발진기는 진동 속도가 완벽하게 일정하지 않으며, 온도 등 환경에 따라서도 미세한 차이가 발생한다.

이 때문에 실제 시간과 시계가 측정한 시간 사이에 오차가 생긴다. 이러한 오차가 시간에 따라 누적되는 현상을 시계 드리프트(Clock Drift) 라고 한다.

노드마다 발진기의 특성과 드리프트 정도가 다르므로, 시간이 지날수록 노드 간 시각에 차이가 발생할 수 있다.

### NTP를 이용한 시계 보정

NTP(Network Time Protocol) 는 시간 서버와 통신해 컴퓨터의 시계를 기준 시각에 맞추는 프로토콜이다.

- 시간 비교: 시간 서버와 시각 정보를 주고받고 네트워크 지연을 고려해 시계 오차를 추정한다.
- 점진적 보정(Slewing): 시계의 진행 속도를 조절해 서서히 오차를 줄인다.
- 직접 보정(Step): 시계 값을 직접 변경해 오차를 바로잡는다.

### NTP로 동기화해도 해결되지 않는 이유

1. 네트워크 지연
- NTP 역시 네트워크를 통해 시간 정보를 주고받는다. 왕복 지연을 고려해 오차를 추정하지만, 네트워크의 지연이 불규칙하거나 양방향 지연이 다르면 정확한 시각을 알아내기 어렵다.

2. 시간 점프(Time Jump)
- 일 기준 시계의 값을 직접 보정하면 시각이 앞으로 또는 뒤로 이동할 수 있다. 따라서 일 기준 시계로 경과 시간을 계산하면 음수가 나오거나 실제 경과 시간과 다른 결과가 발생할 수 있다.

3. 윤초
* 하루가 59초나 61초가 되는 보정 때문에 시계가 이상하게 동작해서 장애가 난 사례가 있다.

NTP로 동기화해도 정확도에는 한계가 있으므로, 노드 간 시계가 정확히 맞는다고 가정하면 안 된다.

### 동기화된 시계에 의존할 때 발생하는 문제 : LWW

>**LWW(Last Write Wins)**: 분산 DB에서 같은 데이터에 쓰기가 충돌하면 타임스탬프가 가장 큰 쓰기 하나만 남기고 나머지는 조용히 버리는 충돌 해결 방식.

![신뢰성없는시계](../../images/session4/신뢰성없는시계.png)

**LWW (Last Write Wins)**
* 같은 키에 쓰기가 충돌하면 일 기준 시계 타임스탬프가 가장 큰 쓰기를 남기는 방식
* 노드의 시계가 어긋나 있으면 실제로는 나중에 한 쓰기가 더 작은 타임스탬프를 받아 버려질 수 있다.
* 사용자에게는 쓰기가 성공했다고 응답이 가기 때문에 유실을 알아채기 어렵다.
* 실제로 동시에 일어난 쓰기인지, 순서가 있는 쓰기인지도 구분하지 못한다.

각 노드의 시간이 틀릴 수도 있다는 걸 알고 설계해야 한다.




## 프로세스 중단

실행 중인 스레드나 프로세스는 다양한 이유로 일시 중단됐다가 다시 실행될 수 있다.
- JVM의 STW(Stop-The-World): 가비지 컬렉션 등의 작업을 위해 애플리케이션 스레드가 일시 중단됨
- 가상 머신의 일시 정지: 가상 머신을 중단했다가 나중에 재개함
- 운영체제의 스케줄링: 컨텍스트 스위칭으로 실행 중인 스레드가 CPU를 사용하지 못하고 대기함
- 느린 I/O: 디스크나 네트워크 응답을 기다리면서 실행이 지연됨

이처럼 프로세스가 특정 시점에 멈췄다가 다시 실행되면, 재개 시점에는 주변 상황이 이미 바뀌어 있을 수 있다.

### 프로세스 중단으로 발생하는 문제

```
if (balance >= amount) {   // 여기서 스레드 A가 멈춤
    balance -= amount      // 그사이 스레드 B가 잔액을 바꿈. A는 깨어나서 낡은 조건으로 실행
}
```

- 스레드 A가 잔액을 확인하고 실행을 멈춘다.
- 그 사이 스레드 B가 잔액을 변경한다.
- 스레드 A가 다시 실행되면서 이전에 확인한 조건을 바탕으로 작업을 수행한다.

이처럼 확인한 시점과 실제 작업을 수행하는 시점 사이에 상태가 바뀌면 동시성 문제가 발생할 수 있다.

### 단일 시스템과 분산 시스템의 차이

단일 시스템에서는 여러 스레드가 같은 메모리를 공유하므로 다음과 같은 도구로 동시성을 제어할 수 있다.

- 뮤텍스(Mutex)
- 세마포어(Semaphore)
- 원자적 연산(Atomic Operations)
- 블로킹 큐(Blocking Queue)

하지만 분산 시스템의 각 노드는 서로 다른 메모리 공간을 사용한다. 따라서 한 노드의 메모리에서 동작하는 뮤텍스나 원자적 연산만으로는 여러 노드의 동시 접근을 제어할 수 없다.

그래서 분산 환경에서는 외부 락 서비스(Redis, ZooKeeper)나 데이터베이스 등 추가적인 수단이 필요하다.

### 임차권(Lease)의 필요성

분산 락을 획득한 노드가 장애로 영원히 멈추면 락이 해제되지 않을 수 있다.

이를 방지하기 위해 락에 만료 시간을 설정하는데, 이를 임차권(Lease)이라고 한다.
- 락을 획득한 노드는 정해진 시간 동안 락을 사용할 권리를 얻는다.
- 노드가 죽거나 락을 갱신하지 못하면 임차권이 만료된다.
- 이후 다른 노드가 락을 획득할 수 있다.

하지만 노드가 죽은 게 아니라 잠시 멈춘 경우(STW), 깨어난 노드는 락이 만료된 걸 모르고 작업을 계속할 수 있다.

![임차권문제](../../images/session4/임차권문제.png)

이렇게 노드가 임차권을 가지고 있다고 잘못알고있는 노드가 시스템을 방해할수없도록 보장해야한다.


### 펜싱 토큰(Fencing Token)
- 락 서비스가 임차권을 줄 때마다 **계속 증가하는 번호**를 준다.
- 노드는 쓰기 요청에 토큰을 붙여 보낸다.
- DB(저장소)는 **지금까지 받은 가장 큰 토큰**을 기억하고 있다가, 그보다 **작은 토큰이 오면 거부**한다.

![펜싱토큰](../../images/session4/펜싱토큰.png)

펜싱 토큰은 안전성을 노드가 아닌 저장소에서 보장한다. 대신 저장소가 토큰을 저장하고 비교하는 책임을 가져야 한다.


### 정족수 (quorum)
예를 들어 다음과 같은 상황이 발생할 수 있다.

1. 노드 A가 긴 STW로 1분간 멈춘다.
2. 다른 노드들은 A로부터 응답을 받지 못한다.
3. 다른 노드들은 A가 죽었다고 판단하고 작업을 넘긴다.
4. A가 다시 실행되지만, 자신은 여전히 정상이라고 생각하고 이전 작업을 수행한다.

즉, 노드가 다른 노드의 상태를 잘못 판단할 수 있고, 자기 자신의 상태도 정확하게 인식하지 못할 수 있다.

### 정족수란?

정족수는 분산 시스템에서 결정을 내리기 위해 필요한 최소한의 동의 수를 의미한다.

예를 들어 5개의 노드 중 과반수인 3개 노드가 동의해야 결정을 내리는 방식을 생각할 수 있다.
- 여러 노드의 동의를 바탕으로 리더를 선출한다.
- 일부 노드가 응답하지 않더라도 충분한 노드가 살아 있다면 결정을 내릴 수 있다.
- 한 노드가 스스로 리더라고 주장하더라도, 합의 규칙에 따라 필요한 동의를 얻지 못하면 리더로 인정되지 않을 수 있다.

다만 정족수만으로 모든 문제를 해결하는 것은 아니다. 정족수를 활용하는 구체적인 알고리즘에 따라 리더 선출, 데이터 읽기·쓰기, 장애 대응 방식이 달라진다.
