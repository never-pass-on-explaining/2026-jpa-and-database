# 8장. 분산 시스템의 골칫거리 (The Trouble with Distributed Systems)

> **한 줄 요약**
> 분산 시스템에서는 **네트워크·시계·프로세스 중 무엇도 믿을 수 없다.** 노드는 "확실히 아는 것"이 없고, 받은 메시지로 **추측**할 뿐이다. 그래서 진실은 **다수결(정족수)** 로 정하고, 알고리즘은 **현실을 단순화한 시스템 모델** 위에서 정확성을 증명한다.

## 장의 흐름

| 순서 | 주제 | 핵심 질문 |
|---|---|---|
| 1 | 결함과 부분 장애 | 왜 분산 시스템은 단일 장비보다 어려운가? |

| 3 | 신뢰성 없는 시계 | 시간을 기준으로 순서·만료를 판단해도 되는가? |
| 4 | 지식, 진실, 거짓말 | 노드가 아무것도 확신할 수 없다면 무엇을 믿는가? |

## 1. 결함과 부분 장애

### 단일 장비 vs 분산 시스템

| 구분 | 단일 장비 | 분산 시스템 |
|---|---|---|
| 동작 방식 | 결정적 (정상이면 같은 결과) | 비결정적 |
| 장애 형태 | 전부 동작 or 전부 실패 | **일부만 실패** (부분 장애) |
| 하드웨어 문제 시 | 차라리 크래시 (블루스크린, 커널 패닉) | 일부 노드만 이상하게 동작 |

> 💡 **부분 장애 (Partial Failure)**
> 시스템의 어떤 부분은 잘 동작하는데, 다른 부분은 예측할 수 없는 방식으로 고장 나는 상태. **비결정적**이라 "됐는지 안 됐는지"조차 모를 수 있다는 게 핵심.

### 클라우드 컴퓨팅 vs 슈퍼컴퓨팅

| 구분 | 슈퍼컴퓨터 (HPC, High-Performance Computing) | 클라우드 / 인터넷 서비스 |
|---|---|---|
| 용도 | 과학 계산 등 배치 작업 | 온라인 서비스 |
| 장애 대응 | 체크포인트 저장 → 전체 중단 → 재시작 | **중단 없이** 계속 서비스해야 함 |
| 하드웨어 | 특수·신뢰성 높은 장비 | 상용 장비 → 고장률 높음 |
| 네트워크 | 특수 토폴로지 | IP / 이더넷 |
| 성격 | 단일 노드처럼 동작 | 부분 장애를 전제로 설계 |

### 핵심 원칙

- 신뢰성 없는 구성 요소로 **신뢰성 있는 시스템**을 만든다. (예: IP는 신뢰성 없지만 그 위의 TCP는 재전송·순서 보장을 제공)
- 단, 추상화로 가릴 수 있는 문제에는 **한계**가 있다. TCP도 네트워크 지연까지는 숨기지 못한다.
- 결론: **"언젠가 어떤 부분에 결함이 생긴다"를 가정하고 소프트웨어가 그 결함을 처리**하게 해야 한다. 결함 처리도 설계의 일부다.

## 2. 신뢰성 없는 네트워크

> 💡 **비동기 패킷 네트워크 (Asynchronous Packet Network)**
> 노드가 메시지를 보낼 수는 있지만, **언제 도착할지·도착하긴 할지 아무것도 보장하지 않는** 네트워크. 인터넷과 대부분의 데이터센터 내부 네트워크가 여기에 해당한다.

### 요청을 보내고 응답이 없을 때, 가능한 원인

1. 요청이 손실됨 (케이블 뽑힘 등)
2. 요청이 큐에서 대기 중 (네트워크·수신 측 과부하)
3. 원격 노드가 죽음
4. 원격 노드가 일시 중단됨 (긴 GC 등)
5. 원격 노드가 처리했지만 **응답이 손실됨**
6. 응답이 지연 중

👉 **송신자 입장에서는 이 6가지를 구별할 수 없다.** "응답이 없다"만 안다.
👉 그래서 쓰는 유일한 현실적 도구가 **타임아웃**. 하지만 타임아웃이 나도 "요청이 처리됐는지"는 여전히 모른다. (→ 재시도 시 **멱등성**이 중요해지는 이유)

### 현실의 네트워크 결함

- 데이터센터 네트워크 결함은 생각보다 흔하다. (스위치 소프트웨어 업그레이드 중 재구성, 상어가 해저 케이블을 물어뜯은 사례 등)
- 한쪽 방향만 끊기는 경우도 있다. (보내는 건 되는데 받는 건 안 됨)
- **네트워크 분단 (Network Partition / Netsplit)**: 네트워크 일부가 다른 부분과 차단된 상태.
- 결함을 꼭 **견딜** 필요는 없지만, 결함에 **어떻게 반응하는지 알고, 복구할 수 있음을 보장**해야 한다. → 의도적으로 결함을 일으켜 테스트 (**카오스 엔지니어링**, 예: Netflix Chaos Monkey)

### 결함 감지

노드가 죽었는지 확실히 알려주는 피드백이 **있는 경우**도 있다.

| 상황 | 받을 수 있는 신호 |
|---|---|
| 장비는 살아 있는데 프로세스만 죽음 | OS가 TCP 연결을 `RST`/`FIN`으로 거부·종료 |
| 프로세스는 죽었는데 OS는 살아 있음 | 스크립트가 다른 노드에 알림 (HBase 방식) |
| 스위치 관리 인터페이스 접근 가능 | 하드웨어 수준 링크 장애 감지 |
| 목적지 IP 도달 불가 | 라우터가 ICMP Destination Unreachable 응답 |

- 하지만 이런 신호가 **항상 오지는 않는다.**
- 요청이 성공했음을 확신하려면 **애플리케이션 자체의 긍정 응답**을 받아야 한다. TCP ACK는 "커널 버퍼에 도착했다"는 뜻일 뿐, 애플리케이션이 처리했다는 뜻이 아니다.

### 타임아웃과 기약 없는 지연

**타임아웃 길이의 트레이드오프**

| 타임아웃 | 장점 | 단점 |
|---|---|---|
| 길게 | 오탐(살아 있는 노드를 죽었다고 판단) 감소 | 진짜 장애 시 오래 기다림 → 사용자가 에러를 오래 봄 |
| 짧게 | 장애 빠르게 감지 | **오탐 증가** → 동작 중복 실행, 과부하 노드에 부하 전가 → **연쇄 장애** |

- 가상의 이상적 네트워크: 패킷 최대 지연 `d`, 처리 최대 시간 `r` 이 보장된다면 타임아웃은 `2d + r`이면 충분하다.
- 현실: **비동기 네트워크는 기약 없는 지연(Unbounded Delay)** 이다. 상한이 없다.

**네트워크 혼잡과 큐 대기** — 지연 변동성의 주범은 대부분 **큐**

| 위치 | 큐 대기 원인 |
|---|---|
| 네트워크 스위치 | 여러 노드가 같은 목적지로 동시에 전송 → 스위치 큐가 꽉 차면 패킷 **버림** |
| 수신 장비 OS | 모든 CPU 코어가 바쁨 → 애플리케이션이 처리할 때까지 대기 |
| 가상 머신 | 다른 VM이 CPU 쓰는 동안 일시 정지 → 가상 머신 모니터가 큐에 버퍼링 |
| TCP 흐름 제어 | 송신 측에서 **자기 자신을** 제한 (혼잡 회피) |
| TCP 재전송 | 패킷 손실 시 타임아웃 후 재전송 → 애플리케이션에는 그냥 "지연"으로 보임 |

> 💡 **TCP vs UDP**
> 화상 통화·VoIP처럼 **지연이 신뢰성보다 중요한** 경우 UDP를 쓴다. 늦게 온 데이터는 쓸모가 없으니 재전송하지 않는 것이 낫다.

**실무적 대응**
- 고정 타임아웃보다 **응답 시간 분포를 측정해 자동 조정**하는 방식이 낫다.
- 예: **파이 증가 장애 감지기 (Phi Accrual Failure Detector)** — Akka, Cassandra에서 사용. "죽었다/살았다" 이분법 대신 "죽었을 의심 수준(φ)"을 연속값으로 계산한다.
- 공개 클라우드·멀티 테넌트 환경에서는 **시끄러운 이웃(Noisy Neighbor)** 때문에 지연 변동이 더 크다.

### 동기 네트워크 vs 비동기 네트워크

> 왜 하드웨어 수준에서 지연 상한을 보장하지 않을까?

| 구분 | 전화망 (회선 교환, Circuit-switched) | 인터넷 / TCP (패킷 교환, Packet-switched) |
|---|---|---|
| 방식 | 통화 시 **고정 대역폭 회선** 예약 | 가용 대역폭을 동적으로 공유 |
| 지연 | **제한 있음** (Bounded Delay) — 큐가 없음 | 제한 없음 |
| 최적화 대상 | 일정한 비트 전송률 (음성) | **순간적으로 몰리는 트래픽 (Bursty Traffic)** |
| 자원 활용 | 안 쓰는 동안에도 대역폭 낭비 | 높은 활용률 |

- 웹 페이지 요청, 파일 전송은 필요한 대역폭을 미리 알 수 없다 → 회선을 고정하면 너무 느리거나 낭비된다.
- 결론: **지연 변동성은 자연법칙이 아니라 비용·이득 트레이드오프의 결과**다. 패킷 교환은 활용률이 높아 저렴하지만 지연이 불확실하다.
- 참고: 인피니밴드(InfiniBand) 같은 일부 데이터센터 네트워크는 QoS·흐름 제어로 지연을 상당히 제한하지만, 일반 데이터센터·클라우드에선 기약 없는 지연을 가정해야 한다.

## 3. 신뢰성 없는 시계

시간이 쓰이는 곳: 타임아웃, 응답 시간 백분위, 초당 처리량, 캐시 만료, 로그 타임스탬프, 이벤트 순서...

문제: 장비마다 **자기만의 시계**(수정 발진기)가 있고, 이 시계들은 **조금씩 다르다**. 네트워크 지연 때문에 "어떤 일이 먼저 일어났는지"도 알기 어렵다.

> 💡 **NTP (Network Time Protocol)**
> 서버 그룹(최종적으로는 GPS 수신기 같은 정확한 시간 출처)에서 받은 시간으로 장비 시계를 맞추는 프로토콜.

### 일 기준 시계 vs 단조 시계

| 구분 | 일 기준 시계 (Time-of-day Clock) | 단조 시계 (Monotonic Clock) |
|---|---|---|
| 의미 | 현재 날짜·시간 (벽시계 시간) | 임의 시점부터 흐른 시간 |
| Linux | `clock_gettime(CLOCK_REALTIME)` | `clock_gettime(CLOCK_MONOTONIC)` |
| Java | `System.currentTimeMillis()` | `System.nanoTime()` |
| NTP 동기화 시 | **뒤로 점프 가능** (강제 리셋) | 점프 없음, 속도만 조절(slewing, 최대 0.05%) |
| 절대값 의미 | 있음 | **없음** (다른 장비와 비교 불가) |
| 적합한 용도 | 다른 장비와 비교해야 하는 시각 | **경과 시간 측정** (타임아웃, 응답 시간) |

- 일 기준 시계는 **윤초**도 무시하는 경우가 많고, 거칠게 동작해서 경과 시간 측정에 부적합하다.
- 분산 시스템에서 **경과 시간 측정에는 단조 시계**를 쓰면 일반적으로 안전하다.

### 시계 동기화와 정확도 — 생각보다 부정확하다

| 문제 | 설명 |
|---|---|
| **드리프트 (Drift)** | 수정 시계가 빠르거나 느리게 감. 온도에 따라 달라짐. 구글 가정치 200ppm → 30초마다 동기화 시 6ms, 하루 1회 시 **17초** 오차 |
| 강제 리셋 | NTP 서버와 차이가 너무 크면 동기화를 거부하거나 강제 리셋 → 시간이 **앞뒤로 점프** |
| 방화벽 차단 | NTP 트래픽이 막히면 아무도 모르게 오차 누적 |
| 네트워크 지연 | NTP 정확도는 **네트워크 지연만큼만** 좋을 수 있음. 혼잡하면 오차 100ms 이상 가능 |
| 잘못된 NTP 서버 | 몇 시간씩 틀린 서버도 존재. 클라이언트는 여러 서버를 질의해 이상치를 걸러냄 |
| **윤초** | 1분이 59초/61초가 됨 → 이를 가정하지 않은 시스템이 크게 고장난 사례 다수 |
| 가상 머신 | VM이 일시 정지됐다 재개되면 시계가 **갑자기 앞으로 점프** |
| 사용자 기기 | 사용자가 시간을 일부러 틀리게 설정 가능 (게임 시간 제한 우회 등) |

> 💡 **문지름 (Smearing)**
> 윤초를 한 번에 넣지 않고 **하루에 걸쳐 조금씩** 반영하는 기법. NTP 서버가 의도적으로 "거짓말"을 하게 만드는 셈. (구글 등이 사용)

- 정밀도가 꼭 필요하면 GPS 수신기, **PTP (Precision Time Protocol)**, 세심한 모니터링으로 해결 가능하다. (예: 유럽 MiFID II 규제는 고빈도 거래 펀드에 UTC 기준 100마이크로초 이내 동기화를 요구)

### 동기화된 시계에 의존하기 — 조용한 데이터 손실

- 시계는 대부분 잘 동작하지만, **고장 나도 티가 나지 않는다.** 크래시가 아니라 **조용하고 미묘한 데이터 손실**이 생긴다.
- 대책: 모든 장비 간 **시계 차이를 모니터링**하고, 다른 노드와 너무 멀어진 노드는 **죽은 것으로 선언**하고 클러스터에서 제거한다.

#### ① 이벤트 순서화용 타임스탬프 — LWW의 함정

> 💡 **최종 쓰기 승리 (LWW, Last Write Wins)**
> 동시 쓰기 충돌 시 **타임스탬프가 가장 큰 쓰기만 남기고 나머지를 버리는** 해소 전략. 다중 리더 복제, 리더 없는 DB(Cassandra, Riak)에서 널리 쓴다.

**책의 예시**

```
노드1 시계: 42.004초에 클라이언트 A가 x=1 쓰기
노드3 시계: 42.003초에 클라이언트 B가 x+=1 (x=2) 쓰기   ← 실제로는 B가 A보다 나중!

→ 노드2는 타임스탬프가 더 큰 A(42.004)를 남기고 B의 증가 연산을 조용히 버림
→ 시계 차이는 3ms 미만이었는데도 데이터 손실 발생
```

LWW의 근본 문제
- 시계가 뒤처진 노드는 앞선 노드가 쓴 값을 **일정 시간 동안 덮어쓸 수 없다.** → 에러 없이 쓰기가 사라짐
- 아주 짧은 간격의 **순차 쓰기**와 **진짜 동시 쓰기**를 구별 못함 → 버전 벡터 같은 인과성 추적 필요 (5장)
- 같은 밀리초 타임스탬프 충돌 시 tiebreaker(난수 등)가 필요한데, 이것도 인과성을 깨뜨릴 수 있다.

> **"최근"의 정의는 로컬 일 기준 시계에 의존하고, 그 시계는 틀릴 수 있다.**

> 💡 **논리적 시계 (Logical Clock)**
> 실제 시간이 아니라 **증가하는 카운터**로 이벤트의 **상대적 순서**만 추적하는 방식. 이벤트 순서화에는 물리적 시계(일 기준·단조)보다 안전하다. (9장의 램포트 타임스탬프로 이어짐)

#### ② 시계 읽기는 "시점"이 아니라 "신뢰 구간"

- 시계가 마이크로초 단위로 읽힌다고 그만큼 **정확**한 건 아니다. (정밀도 ≠ 정확도)
- 시계 값은 **신뢰 구간**으로 보는 게 맞다. 예: "95% 확률로 10.3초 ~ 10.5초 사이"
- 대부분의 시스템은 이 불확실성을 **노출하지 않는다.** 예외: **구글 스패너의 트루타임(TrueTime) API** → `[earliest, latest]` 구간을 반환한다.

#### ③ 전역 스냅숏용 동기화된 시계

- 스냅숏 격리(7장)는 보통 **단조 증가하는 트랜잭션 ID**로 구현한다.
- 여러 장비·데이터센터에 분산되면 **전역 단조 증가 ID**를 만드는 게 어렵다. (단일 ID 생성기는 병목)
- **스패너의 방법**: 트루타임 신뢰 구간을 트랜잭션 ID로 사용
    - 두 구간 A=[A_earliest, A_latest], B=[B_earliest, B_latest]가 **겹치지 않으면** (A_latest < B_earliest) B가 확실히 나중
    - 커밋 전 **신뢰 구간 길이만큼 의도적으로 대기** → 구간이 겹치지 않게 보장
    - 대기 시간을 줄이려 데이터센터마다 **GPS 수신기·원자 시계**를 둬서 불확실성을 약 7ms 이내로 유지

### 프로세스 중단 (Process Pause)

**문제 상황: 임차권 (Lease) 기반 리더**

> 💡 **임차권 (Lease)**
> 타임아웃이 있는 잠금. "이 시점까지는 내가 리더"라는 권한을 받고, 계속 리더이려면 만료 전에 **주기적으로 갱신**해야 한다. 노드가 죽으면 갱신이 끊겨 다른 노드가 넘겨받을 수 있다.

```java
while (true) {
    request = getIncomingRequest();
    // 임차권이 최소 10초 남았는지 확인
    if (lease.expiryTimeMillis - System.currentTimeMillis() < 10000) {
        lease = lease.renew();
    }
    if (lease.isValid()) {
        process(request);   // ← 여기 오기 직전에 15초 멈추면?
    }
}
```

**이 코드의 문제 2가지**
1. **동기화된 시계에 의존**: 만료 시각은 다른 장비가 설정했는데, 비교는 로컬 시계로 한다. 시계가 몇 초만 어긋나도 이상하게 동작한다.
2. **실행 중 멈춤을 가정하지 않음**: `isValid()` 확인 직후 15초 멈추면, 깨어났을 때 **임차권은 이미 만료**됐고 다른 노드가 리더인데도 요청을 처리한다.

**스레드가 오래 멈출 수 있는 이유**

| 원인 | 설명 |
|---|---|
| **GC "stop-the-world"** | 수 분간 멈춘 사례도 있음 (JVM 등) |
| VM 일시 정지 | 라이브 마이그레이션 시 메모리 복사를 위해 VM 전체를 멈춤 |
| 노트북 덮개 닫기 | 사용자 기기 실행 일시 정지 |
| 컨텍스트 스위치 / 스틸 타임 | 하이퍼바이저가 다른 VM으로 전환 (Steal Time) |
| 동기 디스크 I/O | 예상치 못한 I/O (예: JVM 클래스 지연 로딩), 네트워크 디스크(EBS)는 지연 변동성 큼 |
| 스와핑 (페이징) | 메모리 부족 시 페이지 폴트 → 디스크 I/O 대기. 심하면 스래싱 |
| `SIGSTOP` | 운영자가 실수로 Ctrl-Z 등 |

👉 **선점(Preemption)** 이 언제든 일어날 수 있고, 멈춘 스레드는 **자신이 멈췄다는 사실조차 모른다.**
👉 단일 장비에는 뮤텍스·세마포어·원자적 카운터 같은 도구가 있지만, 분산 시스템에는 **공유 메모리가 없다.** 메시지만 있을 뿐이다.
👉 결론: 분산 시스템의 노드는 **어느 시점에 상당한 시간 동안 멈출 수 있다고 가정**해야 하고, 그 사이 나머지 시스템은 그 노드를 **죽었다고 선언**할 수 있다.

**응답 시간 보장 — 대응 방법**

| 방법 | 설명 | 한계 |
|---|---|---|
| **엄격한 실시간 (Hard Real-time) 시스템** | **RTOS (Real-Time Operating System, 실시간 운영체제)**, 동적 메모리 할당 제한/금지, 철저한 테스트 | 비용이 매우 큼, 처리량 낮음. 항공기·로켓·자동차 에어백 같은 안전 필수 시스템에만 사용 |
| **GC를 계획된 중단으로 취급** | GC가 임박하면 런타임이 알려주고, 그 노드로 요청을 보내지 않음 → 다른 노드가 처리 | 일부 지연 민감 시스템(예: 금융 거래)에서 사용 |
| **단명 객체만 GC + 주기적 재시작** | Full GC 전에 프로세스를 재시작 (롤링 재시작처럼 계획적으로) | 운영 복잡도 증가 |

> ⚠️ "실시간"은 "빠르다"는 뜻이 아니라 **"데드라인이 보장된다"** 는 뜻이다. 웹의 "실시간"과 다르다.

## 4. 지식, 진실, 그리고 거짓말

> 노드는 네트워크로 받은 메시지를 기반으로 **추측**만 할 수 있다.
> 응답이 없으면 그 노드가 죽은 건지, 네트워크 문제인지 **알 방법이 없다.**

### 진실은 다수결로 결정된다

**책의 시나리오들**
- **비대칭 결함**: 노드가 메시지를 받을 수는 있는데 보낸 응답이 유실됨 → 노드는 멀쩡한데 다른 노드들이 죽었다고 선언
- 노드가 자신의 응답이 전달되지 않는다는 걸 **알아챘음에도**, 다른 노드들의 결정을 막을 수 없음
- **긴 GC 중단**: 다른 노드들이 죽었다고 선언 → GC 끝나고 깨어난 노드는 **아무 일도 없었던 것처럼** 계속 동작

👉 노드는 **자기 자신의 상황 판단조차 믿을 수 없다.**

> 💡 **정족수 (Quorum)**
> 결정을 내리기 위해 필요한 **최소 투표 수**. 보통 과반수. 특정 노드 하나에 대한 의존을 없앤다.
> - 과반수 정족수면 두 개의 정족수가 **동시에 서로 모순된 결정을 내릴 수 없다.** (두 과반수는 반드시 겹친다)
> - 노드의 정족수가 "죽었다"고 선언하면 그 노드는 **죽은 것**이다. 본인이 살아 있다고 느껴도 따라야 한다.

#### 리더와 잠금 — "선택된 자"가 하나여야 하는 상황

- 단일 리더 파티션 (스플릿 브레인 방지)
- 특정 자원·객체에 대한 잠금은 하나의 트랜잭션·클라이언트만
- 특정 사용자명은 한 명만 등록 가능

**책의 예시: 잘못 구현된 분산 잠금 → 파일 손상**

```
1. 클라이언트1이 잠금 서비스에서 임차권 획득
2. 클라이언트1이 긴 GC로 멈춤 → 그 사이 임차권 만료
3. 클라이언트2가 임차권 획득 → 파일에 쓰기
4. 클라이언트1이 깨어남 → 자기가 아직 임차권이 있다고 믿고 파일에 쓰기
→ 💥 파일 손상
```

(실제 사례: HBase에서 이 문제로 데이터가 손상된 적이 있다)

#### 펜싱 토큰 (Fencing Token)

> 💡 **펜싱 (Fencing)**
> 잠금·임차권으로 자원을 보호할 때, **자신이 "선택된 자"라고 잘못 믿는 노드**가 나머지 시스템을 방해하지 못하도록 막는 기법.

**동작 방식**

```
1. 잠금 서버가 잠금을 줄 때마다 **단조 증가하는 번호(펜싱 토큰)** 를 함께 발급
2. 클라이언트는 쓰기 요청마다 토큰을 함께 보냄
3. 저장소는 이미 처리한 것보다 **오래된 토큰의 쓰기는 거부**

클라이언트1: 토큰 33 획득 → GC로 멈춤 → 임차권 만료
클라이언트2: 토큰 34 획득 → 저장소에 쓰기 (token=34) ✅
클라이언트1: 깨어나서 쓰기 (token=33) → ❌ 거부 (이미 34 처리함)
```

- **핵심: 확인 주체가 클라이언트가 아니라 "자원(저장소)"이다.** 클라이언트는 자신이 멈췄다는 걸 모르기 때문에 스스로 확인하는 건 의미가 없다.
- 실무 예시: **ZooKeeper**에서는 트랜잭션 ID `zxid`나 노드 버전 `cversion`을 펜싱 토큰으로 쓸 수 있다.
- 저장소가 펜싱 토큰을 지원하지 않으면? 우회 방법이 필요하다. (예: 파일명에 토큰을 넣는 등)
- 펜싱은 악의적 클라이언트가 아니라 **부주의에 의한 오류(GC, 네트워크 지연)** 로부터 보호하는 장치다.

> 🔎 **참고**: 저자 마틴 클레프만은 같은 논리로 Redis의 분산 잠금 알고리즘 **Redlock**이 펜싱 토큰을 제공하지 않아 안전하지 않다고 비판한 글(*How to do distributed locking*, 2016)을 썼다. 8장 내용의 실전 적용 사례로 읽어볼 만하다.

### 비잔틴 결함

> 💡 **비잔틴 결함 (Byzantine Fault)**
> 노드가 **거짓말**을 하는 상황. 고장 나지 않았는데 오류 메시지를 보내거나, 받지 않은 메시지를 받았다고 주장하는 등.
> **비잔틴 장군 문제**: 신뢰할 수 없는 환경(배신자가 있을 수 있는 환경)에서 합의에 도달하는 문제.

- **비잔틴 내결함성 (Byzantine Fault Tolerance)**: 일부 노드가 오작동·악의적 행동을 해도 시스템이 올바르게 동작하는 성질.

| 비잔틴 내결함성이 필요한 경우 | 이 책(일반 서버 시스템)에서 가정하는 경우 |
|---|---|
| 항공우주 (방사선으로 메모리·레지스터 손상) | 모든 노드가 **한 조직**의 통제 아래 있음 |
| 여러 조직이 참여하는 시스템 (블록체인 등) | 노드는 정직하다고 가정 |
| 참여자가 서로를 속일 동기가 있음 | 비잔틴 내결함성 프로토콜은 **너무 복잡하고 비쌈** |

- 웹 애플리케이션에서 **클라이언트(브라우저)** 는 악의적이라고 가정한다. → 입력 검증, SQL 주입·XSS 방어. 하지만 이는 비잔틴 합의가 아니라 **서버가 결정권을 가지는** 구조로 해결한다.
- 비잔틴 내결함성 알고리즘은 **3분의 2 초과**의 노드가 정상이어야 한다. 같은 소프트웨어 버그가 모든 노드에 있으면 소용없다.
- 다만 **약한 형태의 거짓말**에는 저렴하게 대비할 수 있다.
    - 체크섬 (TCP/UDP 체크섬을 우회하는 패킷 손상 대비)
    - 사용자 입력 검증 (값 범위, 문자열 크기 제한)
    - NTP 클라이언트가 여러 서버를 질의해 이상치 제외

### 시스템 모델과 현실

알고리즘을 하드웨어·소프트웨어 세부 사항에 의존하지 않게 하려면, **어떤 결함을 가정하는지 정형화**해야 한다. → **시스템 모델**

**타이밍 가정**

| 모델 | 가정 | 현실성 |
|---|---|---|
| 동기식 (Synchronous) | 네트워크 지연·프로세스 중단·시계 오차 **모두 상한 있음** | ❌ 대부분의 시스템에 비현실적 |
| **부분 동기식 (Partially Synchronous)** | 대부분 동기식이지만 **가끔 상한을 초과** | ✅ **현실적인 모델** |
| 비동기식 (Asynchronous) | 타이밍에 대해 **아무 가정도 하지 않음** (시계 없음) | 매우 제한적, 설계 가능한 알고리즘이 적음 |

**노드 장애 가정**

| 모델 | 가정 |
|---|---|
| 죽으면 중단 (Crash-stop) | 노드는 죽으면 **영원히** 돌아오지 않음 |
| **죽으면 복구 (Crash-recovery)** | 죽었다가 **나중에 다시 응답**. 안정적 저장소(디스크)는 유지, 메모리는 손실 |
| 비잔틴 (Byzantine) | 노드가 다른 노드를 **속이는 것까지** 포함, 무엇이든 할 수 있음 |

👉 **실제 시스템에 가장 유용한 조합: 부분 동기식 + 죽으면 복구**

#### 알고리즘의 정확성 — 안전성과 활동성

알고리즘이 "정확하다"는 건 **속성(property)** 으로 기술한다. 펜싱 토큰 예시:

| 속성 | 설명 | 종류 |
|---|---|---|
| 유일성 (Uniqueness) | 두 요청이 같은 토큰을 받지 않음 | 안전성 |
| 단조 일련번호 (Monotonic Sequence) | 요청 x가 y보다 먼저 완료되면 토큰 x < y | 안전성 |
| 가용성 (Availability) | 죽지 않은 노드가 요청하면 결국 응답을 받음 | **활동성** |

| 구분 | 안전성 (Safety) | 활동성 (Liveness) |
|---|---|---|
| 의미 | **나쁜 일은 일어나지 않는다** | **좋은 일은 결국 일어난다** |
| 위반 시 | 위반된 **특정 시점**을 지목할 수 있음 | 특정 시점 지목 불가 ("아직 안 일어났을 뿐") |
| 되돌림 | 위반되면 **되돌릴 수 없음** (이미 손상) | 나중에 만족될 수도 있음 |
| 단서 문구 | — | 정의에 보통 **"결국 (eventually)"** 이 포함됨 |
| 분산 알고리즘 요구 | **모든 상황에서** 항상 성립해야 함 | **조건부**로 허용 (예: 과반수 노드가 살아 있고 네트워크가 결국 복구된다면) |

> 💡 최종적 일관성(Eventual Consistency)도 "결국"이 들어가는 **활동성** 속성이다.

#### 시스템 모델을 현실에 대응시키기

- 시스템 모델은 현실을 **단순화한 추상화**다.
- 예: 죽으면 복구 모델은 "안정적 저장소는 유지된다"고 가정하지만, 현실에선 디스크가 손상되거나 펌웨어 버그로 하드웨어 재부팅 시 인식 못하는 경우도 있다.
- 정족수 알고리즘은 노드가 저장했다고 선언한 데이터를 **기억한다고** 가정한다. 노드가 기억상실에 걸리면 정족수 조건이 깨진다.
- 그래서 실제 구현에는 **"불가능하다고 가정한 일"이 일어났을 때 처리하는 코드**가 필요하다. (예: `printf("Sucks to be you")` 후 `exit(666)` — 사람이 정리하게 하는 것도 처리 방법)
- 결론: **알고리즘이 이론적으로 정확하다는 증명은 현실 구현의 정확성을 보장하지 않는다.** 그래도 이론적 분석은 문제를 일찍 발견하게 해주고, 경험적 테스트(카오스 테스트 등)와 **함께** 쓰여야 한다.

## 핵심 정리 표

| 문제 | 현상 | 대응 |
|---|---|---|
| 네트워크 | 패킷 손실·지연, 응답 없을 때 원인 구별 불가 | 타임아웃(동적 조정), 멱등성, 재시도 |
| 시계 | 드리프트, 점프, 노드 간 불일치 | 경과 시간은 단조 시계, 순서는 논리적 시계, 시계 오차 모니터링, 신뢰 구간(TrueTime) |
| 프로세스 중단 | GC·VM 정지 등으로 임의 시간 멈춤, 본인은 모름 | 펜싱 토큰, GC를 계획된 중단으로 취급 |
| 노드의 판단 | 노드는 자기 상태도 확신 불가 | 정족수(과반수 투표) |
| 거짓말하는 노드 | 비잔틴 결함 | 일반 서버 환경에선 가정 X, 체크섬·입력 검증으로 약한 대비 |
| 알고리즘 정확성 | 현실이 모델 가정을 벗어남 | 안전성/활동성 구분, 부분 동기식 + 죽으면 복구 모델 |
