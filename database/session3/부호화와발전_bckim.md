# 4장. 부호화와 발전 (Encoding and Evolution)

> 『데이터 중심 애플리케이션 설계』 4장 학습 정리
> 이 장의 핵심 질문: **구버전 코드와 신버전 코드가 동시에 돌아갈 때, 데이터를 어떻게 주고받아야 깨지지 않는가?**

---

## 1. 부호화란?

**메모리 속 데이터를 바이트 열로 바꾸는 것.** 직렬화(serialization), 마샬링(marshalling)이라고도 한다. 반대 방향은 복호화(decoding).

| 표현 | 특징 |
|---|---|
| 메모리 속 표현 | 객체, 리스트, 해시맵. 포인터로 서로를 참조. CPU가 다루기 좋음 |
| 바이트 열 표현 | 포인터 없이 스스로 완결됨. 파일 저장, 네트워크 전송에 사용 |

- 포인터는 해당 프로세스 안에서만 의미가 있다.
- 그래서 프로세스 밖으로 데이터를 보내려면 부호화가 반드시 필요하다.

---

## 2. 왜 호환성이 문제인가

애플리케이션은 계속 바뀌고, 바뀐 코드가 **한 번에 배포되지 않는다.**

- **롤링 업그레이드**: 서버 몇 대씩 순차 배포 → 구버전과 신버전 노드가 공존
- **클라이언트 앱**: 사용자가 업데이트하지 않으면 구버전이 계속 남음
- **롤백**: 신버전이 쓴 데이터를 구버전 코드가 읽게 됨

그래서 두 방향의 호환성이 모두 필요하다.

| 용어 | 의미 | 난이도 |
|---|---|---|
| 하위 호환성 (backward) | **새 코드가 옛 데이터**를 읽을 수 있음 | 쉬움. 새 코드는 옛 형식을 알고 있음 |
| 상위 호환성 (forward) | **옛 코드가 새 데이터**를 읽을 수 있음 | 어려움. 옛 코드는 모르는 필드를 무시해야 함 |

---

## 3. 부호화 형식 비교

| 분류 | 예시 | 장점 | 한계 |
|---|---|---|---|
| 언어 전용 | Java `Serializable`, Python pickle | 코드 한 줄로 가능 | 다른 언어와 호환 불가, 역직렬화 보안 취약점, 버전 관리 취약 |
| 텍스트 | JSON, XML, CSV | 사람이 읽을 수 있음, 범용 | 숫자 정밀도 모호(2^53 초과 정수), 바이너리는 Base64로 우회, 스키마는 선택 사항 |
| 바이너리 + 스키마 | Thrift, Protocol Buffers, Avro | 작고 빠름, 스키마가 곧 문서 | 사람이 읽기 어려움, 스키마 관리 필요 |

---

## 4. 바이너리 + 스키마 방식

### 4.1 공통 아이디어

- 데이터 구조를 **스키마**(IDL: 인터페이스 정의 언어)로 미리 정의한다.
- 필드 이름을 매번 보내지 않는다. 이름 대신 **태그 번호**를 보내거나(Thrift, Protobuf), 아예 아무 표식도 없이 값만 보낸다(Avro).
- 스키마에서 여러 언어의 코드를 생성할 수 있다.

책의 예시 레코드(사용자 이름, 좋아하는 숫자, 관심사 목록)를 부호화한 크기:

| 형식 | 크기 |
|---|---|
| JSON (공백 제거) | 81 바이트 |
| MessagePack (JSON의 바이너리 버전) | 66 바이트 |
| Thrift BinaryProtocol | 59 바이트 |
| Thrift CompactProtocol | 34 바이트 |
| Protocol Buffers | 33 바이트 |
| Avro | 32 바이트 |

> MessagePack처럼 **스키마 없이** 바이너리로만 바꾸면 절약 폭이 작다. 필드 이름을 여전히 매번 보내기 때문이다.

### 4.2 Thrift와 Protocol Buffers: 태그 번호 방식

```protobuf
message Person {
  string user_name = 1;
  int64 favorite_number = 2;
  repeated string interests = 3;
}
```

- 각 필드는 이름이 아니라 **태그 번호**(`= 1`, `= 2`)로 식별된다.
- 바이트 열에는 `태그 번호 + 타입 + 값`이 들어간다.
- 정수는 가변 길이로 부호화해서 작은 숫자는 1바이트만 쓴다.

**스키마 발전 규칙**

| 변경 | 가능 여부 | 이유 |
|---|---|---|
| 필드 추가 | 가능 | 옛 코드는 모르는 태그를 건너뜀 → 상위 호환성 |
| 새 필드를 필수(required)로 추가 | 불가 | 옛 데이터에는 그 필드가 없음 → 하위 호환성 깨짐 |
| 필드 삭제 | 선택 필드만 가능 | 삭제한 태그 번호는 **재사용 금지** (`reserved`로 막기) |
| 필드 이름 변경 | 바이너리상 가능 | 바이트 열에는 이름이 없음 (JSON 변환을 쓰면 깨짐) |
| 타입 변경 | 대부분 위험 | 예: 32비트 → 64비트는 옛 코드가 값을 잘라서 읽음 |

**proto3 주의점: "값이 0"과 "값이 없음"의 구분**
- proto3는 기본값(0, 빈 문자열, false)을 전송하지 않는다.
- 그래서 받는 쪽은 "0으로 설정됨"과 "설정 안 됨"을 구분할 수 없다.
- 해결 방법: `optional` 키워드(protobuf 3.15부터 정식), wrapper 타입(`google.protobuf.Int32Value`), `oneof`

### 4.3 Avro: 태그 번호 없는 방식

- 바이트 열에 태그 번호도 타입 정보도 없다. **값만 순서대로** 이어 붙인다.
- 그래서 **데이터를 쓸 때 사용한 스키마를 정확히 알아야만** 읽을 수 있다.

**쓰기 스키마(writer schema)와 읽기 스키마(reader schema)**

| 스키마 | 의미 |
|---|---|
| 쓰기 스키마 | 데이터를 부호화할 때 사용한 스키마 |
| 읽기 스키마 | 데이터를 읽는 애플리케이션이 기대하는 스키마 |

- 두 스키마가 달라도 된다. Avro 라이브러리가 **필드 이름**으로 둘을 맞춰준다.
- 쓰기 스키마에만 있는 필드 → 무시
- 읽기 스키마에만 있는 필드 → 읽기 스키마의 기본값으로 채움

**스키마 발전 규칙**
- **기본값이 있는 필드만** 추가하거나 삭제할 수 있다.
- null을 허용하려면 union 타입으로 명시해야 한다: `["null", "string"]`

**읽는 쪽은 쓰기 스키마를 어떻게 알까?**

| 상황 | 방법 |
|---|---|
| 레코드가 많은 대용량 파일 | 파일 맨 앞에 쓰기 스키마를 한 번만 기록 |
| 레코드마다 쓴 시점이 다른 DB | 레코드마다 스키마 버전 번호를 붙이고, 스키마 목록을 따로 관리 (예: Schema Registry) |
| 네트워크 연결 | 연결을 맺을 때 스키마 버전을 협상 |

**Avro의 장점: 동적으로 생성되는 스키마에 유리**
- 태그 번호를 사람이 관리할 필요가 없다.
- 예: DB 테이블 구조에서 스키마를 자동 생성해 덤프 → 컬럼이 바뀌면 스키마를 새로 만들기만 하면 됨
- Thrift나 Protobuf였다면 컬럼마다 태그 번호를 수동으로 배정하고 관리해야 한다.

### 4.4 스키마 방식의 장점 정리

- JSON보다 훨씬 작다. 필드 이름을 생략할 수 있기 때문이다.
- 스키마 자체가 항상 최신 문서다. 스키마 없이는 복호화할 수 없으므로 문서가 코드와 어긋날 수 없다.
- 배포 전에 스키마 호환성을 검사할 수 있다.
- 정적 타입 언어에서는 코드 생성으로 컴파일 시점 타입 검사가 가능하다.

### 4.5 현업에서 쓰는 곳

요즘 애플리케이션은 **외부 경계는 REST + JSON, 내부는 바이너리 + 스키마**로 나누는 경우가 많다.

```
[브라우저 / 외부 파트너] ──REST + JSON──▶ [API Gateway / BFF]
                                              │
                                       gRPC + Protobuf     (내부 동기 호출)
                                              ▼
                                        [내부 서비스] ──Kafka + Avro/Protobuf──▶ [다른 서비스, 데이터 파이프라인]
                                                                                     │
                                                                           Parquet / Avro 파일 (분석용 저장소)
```

| 사용처 | 대표 기술 | 이유 |
|---|---|---|
| 내부 마이크로서비스 간 호출 | gRPC + Protobuf | 호출량이 많아 직렬화 비용과 크기가 누적됨, 여러 언어 코드 생성 |
| 이벤트 스트리밍 | Kafka + Avro/Protobuf + Schema Registry | 프로듀서와 컨슈머가 따로 배포됨, 호환되지 않는 스키마 등록을 차단 |
| 분석용 대용량 저장 | Parquet, ORC, Avro 파일 | 수십억 행, 스키마가 파일에 붙어 있어 수년 뒤에도 읽기 가능 |
| 모바일 / 게임 | Protobuf, FlatBuffers | 대역폭, 배터리, 파싱 속도 |

**JSON이 외부에서 계속 쓰이는 이유**
- 브라우저가 기본 지원한다 (gRPC는 gRPC-Web과 프록시 필요).
- curl이나 개발자 도구로 바로 보고 디버깅할 수 있다.
- 외부 개발자에게 스키마 파일과 코드 생성 도구를 강요하기 어렵다.

## 5. 데이터플로 모드: 데이터는 어떤 경로로 흐르는가

책은 데이터가 프로세스 사이를 오가는 경로를 세 가지로 나눈다.

| 모드 | 쓰는 쪽 → 읽는 쪽 | 호환성 관점의 특징 |
|---|---|---|
| 데이터베이스 | 과거의 나 → 미래의 나 | 데이터가 코드보다 오래 산다 |
| 서비스 호출 (REST, RPC) | 클라이언트 ↔ 서버 | 서버와 클라이언트의 배포 시점이 다름 |
| 비동기 메시지 전달 | 송신자 → 브로커 → 수신자 | 송신자와 수신자가 서로를 모름 |

### 5.1 데이터베이스를 통한 흐름

- **데이터가 코드보다 오래 산다.** 5년 전에 쓴 레코드를 오늘 배포한 코드가 읽는다.
- 대부분의 DB는 컬럼 추가 시 기존 행을 다시 쓰지 않고, 읽을 때 null(기본값)로 채운다.
- **함정: 옛 코드가 새 필드를 지워버리는 문제**
    1. 새 코드가 `phone` 필드가 포함된 레코드를 씀
    2. 옛 코드가 그 레코드를 읽어 모델 객체로 변환 → 모르는 `phone`은 버려짐
    3. 옛 코드가 수정 후 다시 저장 → `phone` 값이 사라짐
- 대응: 모르는 필드를 보존하도록 처리하거나, 전체 덮어쓰기 대신 부분 업데이트를 사용

### 5.2 서비스를 통한 흐름: REST와 RPC

**RPC (Remote Procedure Call)**
원격 서버의 함수를 로컬 함수처럼 호출하게 해주는 방식. 이 성질을 위치 투명성(location transparency)이라고 한다.

```java
// 로컬 호출처럼 보이지만 실제로는 네트워크 요청
User user = userService.getUser(123);
```

**책의 지적: 네트워크 호출은 로컬 호출과 근본적으로 다르다**

| 로컬 함수 | 네트워크 요청 |
|---|---|
| 성공 또는 예외, 결과가 명확함 | 타임아웃이 나면 **성공했는지 알 수 없음** |
| 재시도해도 안전 | 재시도하면 중복 실행 가능 → **멱등성** 필요 |
| 실행 시간이 거의 일정 | 지연 시간이 크게 흔들림 |
| 참조(포인터)를 넘길 수 있음 | 모든 인자를 부호화해서 보내야 함 |
| 같은 언어 | 서버와 클라이언트 언어가 다를 수 있음 → 타입 변환 문제 |

- 문제는 원격 호출을 로컬처럼 **숨기려는 것**이다.
- 요즘 RPC 프레임워크(gRPC, Finagle, Rest.li)는 오히려 원격 호출임을 드러낸다: Future/Promise, 스트림, deadline

**서비스 API의 호환성**

책의 가정: **서버를 먼저 배포하고, 클라이언트는 나중에 배포한다.**

| 방향 | 누가 읽나 | 필요한 호환성 |
|---|---|---|
| 요청 | 새 서버가 옛 클라이언트의 요청을 읽음 | 하위 호환성 |
| 응답 | 옛 클라이언트가 새 서버의 응답을 읽음 | 상위 호환성 |

### 5.3 비동기 메시지 전달

송신자가 메시지를 수신자에게 직접 보내지 않고 **메시지 브로커**(Kafka, RabbitMQ 등)를 거쳐 보낸다.

```
[RPC]      송신자 ───(수신자 IP:Port)───▶ 수신자

[브로커]   송신자 ──▶ [브로커: topic "orders"] ◀── 수신자
                   (송신자는 토픽 이름만 앎)   (수신자가 직접 연결해 구독)
```

**왜 수신자의 IP와 포트를 몰라도 되는가**
- 송신자와 수신자가 **서로가 아니라 브로커에 연결**한다.
- 송신자가 아는 것은 브로커 주소와 토픽 이름뿐이다.
- 수신자는 스스로 브로커에 접속해 토픽을 구독한다.
- 토픽이라는 **논리적 주소**가 수신자의 **물리적 주소**를 대신한다.

| 이점 | 설명 |
|---|---|
| 버퍼링 | 수신자가 다운되거나 과부하여도 메시지가 브로커에 쌓임 |
| 재전달 | 수신자 프로세스가 죽으면 메시지를 다시 보냄 |
| 팬아웃 | 한 메시지를 여러 수신자가 받을 수 있음 |
| 자유로운 확장 | 수신자를 늘리거나 줄여도 송신자 코드는 그대로 |
| 논리적 분리 | 송신자는 누가 받는지 몰라도 됨 |

**짚고 갈 점**
- 주소 관리가 사라지는 것이 아니라 **브로커로 책임이 옮겨가는 것**이다.
- RPC 쪽에도 서비스 디스커버리(DNS, Consul, Kubernetes Service)가 있어서 IP를 하드코딩하지 않는다.
- 본질적인 차이는 **동기 요청/응답 대 비동기 단방향 전달**이다.
- 프로듀서와 컨슈머가 따로 배포되므로 **양방향 호환성이 모두** 필요하다.

## 6. 현업의 API 버전 관리

### 6.1 버전을 올릴지 결정하는 기준

> 내부냐 외부냐보다 **"클라이언트의 업데이트 시점을 우리가 통제할 수 있느냐"**로 결정된다.

| 상황 | 클라이언트 통제 | 일반적인 방식 |
|---|---|---|
| 같은 팀이 관리하는 내부 서비스 간 API | 가능 | 버전을 올리지 않고 호환 가능한 변경으로 진행 |
| 모바일 앱 (같은 회사라도) | 불가 | 최소 지원 버전 + 강제 업데이트, 앱 버전 헤더로 분기 |
| 외부 공개 API | 불가 | URL(`/v1`), `Accept` 헤더, API 키별 버전 고정 |

### 6.2 내부 API에서도 호환성이 필요한 이유

- 서버와 클라이언트를 같이 바꿔도 배포는 **같은 순간에** 일어나지 않는다.
- 롤링 배포 중에는 구버전 인스턴스와 신버전 인스턴스가 섞여 있다.
- 응답 필드 추가가 문제없이 되는 이유: **구버전 클라이언트가 모르는 필드를 무시하기 때문** (= 상위 호환성)

### 6.3 실무 함정: Jackson의 `FAIL_ON_UNKNOWN_PROPERTIES` (Jackson 2 기준)

| 상황 | 설정값 | 모르는 필드를 받으면 |
|---|---|---|
| Spring Boot가 자동 설정한 `ObjectMapper` | `false` | 무시 → 안전 |
| 직접 생성한 `new ObjectMapper()` | `true` (Jackson 기본값) | `UnrecognizedPropertyException` → 장애 |

응답에 필드 하나 추가했을 뿐인데 다른 팀의 클라이언트가 깨질 수 있다.

### 6.4 변경 유형별 안전도

| 변경 | 안전한가 | 방법 |
|---|---|---|
| 응답에 필드 추가 | 대체로 안전 | 클라이언트가 모르는 필드를 무시하는지 확인 |
| 요청에 선택 필드 추가 | 안전 | 서버가 "필드 없음"을 기본값으로 처리 |
| 요청에 필수 필드 추가 | 위험 | 구버전 클라이언트는 이 값을 보내지 않음 |
| 필드 삭제 | 위험 | 클라이언트가 먼저 사용 중단 → 그다음 서버에서 삭제 |
| 필드 이름 / 타입 변경 | 위험 | expand-contract 패턴 |

**expand-contract 패턴**
한 번의 호환 불가 변경을 여러 번의 호환 가능 변경으로 쪼갠다.

1. **Expand**: 새 필드 추가, 옛 필드와 함께 제공
2. **Migrate**: 클라이언트를 새 필드로 전환
3. **Contract**: 아무도 쓰지 않는 옛 필드 삭제

DB 컬럼 이름 변경에도 똑같이 적용된다.

## 7. 한 줄 요약

- 부호화 = 메모리 속 데이터를 바이트 열로 바꾸는 것
- 핵심 문제 = 구버전과 신버전 코드가 공존할 때의 **하위 / 상위 호환성**
- 바이너리 + 스키마 = 작고, 스키마가 곧 문서이며, 호환성을 규칙으로 관리할 수 있음
- 데이터는 DB, 서비스 호출, 메시지 브로커 세 경로로 흐르고, 경로마다 호환성 요구가 다름
- 버전을 올릴지는 **클라이언트 업데이트 시점을 통제할 수 있는지**로 결정
