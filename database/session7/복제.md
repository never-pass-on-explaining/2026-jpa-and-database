## 복제란?

복제는 같은 데이터의 복사본을 네트워크로 연결된 여러 서버(노드)에 두는 것이다.

> 각 복사본을 **레플리카(replica)** 라고 한다.

### 복제를 하는 이유

- **가용성**: 서버 한 대가 죽어도 다른 레플리카로 서비스를 계속할 수 있다.
- **읽기 처리량 확장**: 읽기 요청을 여러 레플리카에 나눠 처리할 수 있다.
- **지연 시간 감소**: 사용자와 가까운 지역에 레플리카를 두면 응답이 빨라진다.

### 복제가 어려운 이유

데이터가 바뀌지 않는다면 한 번 복사해두면 끝이다. 하지만 실제 DB에는 쓰기가 계속 들어오기 때문에, 한 서버에 쓴 내용을 다른 서버들에도 반영해야 한다.

이때 언제, 어떤 방식으로 반영하느냐가 복제에서 다루는 문제의 대부분이다.


## 단일 리더 복제

### 동작 방식

레플리카 중 한 대를 **리더**로 정하고, 나머지는 **팔로워**가 된다.

1. 쓰기 요청은 반드시 리더로 보낸다. 리더는 자기 저장소에 먼저 쓴다.
2. 리더는 변경 내용을 **복제 로그**로 팔로워들에게 보낸다.
3. 팔로워는 받은 로그를 리더와 같은 순서로 적용한다.
4. 읽기는 리더나 팔로워 아무 곳에서나 할 수 있다.

- 예: MySQL 소스-레플리카, PostgreSQL 스트리밍 복제, MongoDB 레플리카 셋, Kafka 파티션 리더

#### 장점

- **쓰기 충돌이 없다**: 모든 쓰기가 리더 한 곳을 거치므로, 쓰기 순서를 리더가 정한다. 다중 리더나 리더 없는 복제처럼 충돌을 해결할 필요가 없다.
- **읽기 확장이 쉽다**: 팔로워를 늘리면 그만큼 읽기 처리량이 늘어난다.

### 동기 복제 / 비동기 복제

![[Pasted image 20261126214131.png]]

사용자가 프로필 사진을 바꾸면 리더가 쓰기를 받고 두 팔로워에 전달한다.

- **팔로워 1 (동기)**: 리더는 팔로워 1의 완료 응답을 기다린 뒤에 사용자에게 성공을 응답한다.
- **팔로워 2 (비동기)**: 리더는 팔로워 2의 응답을 기다리지 않는다.

동기는 팔로워에 최신 데이터가 보장되지만, 팔로워가 느리거나 죽으면 쓰기가 멈춘다. 비동기는 빠르지만, 리더가 죽으면 아직 전달되지 않은 쓰기가 유실된다.

### 새 팔로워 추가

리더가 계속 쓰기를 받는 중이라, 단순히 파일을 복사하면 복사 도중에 데이터가 바뀌어 일관성이 깨진다. 그래서 다음 순서로 진행한다.

1. 리더의 특정 시점 **스냅샷**을 뜬다. 이때 스냅샷이 복제 로그의 어느 위치에 해당하는지도 같이 기록한다.
    - 예: MySQL binlog 좌표(파일명 + 포지션), PostgreSQL LSN
2. 스냅샷을 새 팔로워에 복사한다.
3. 팔로워가 리더에게 "기록한 위치 이후의 변경분"을 요청한다.
4. 밀린 변경분을 다 적용하면(따라잡으면) 그때부터 일반 팔로워처럼 동작한다.

### 노드 장애 처리

#### 리더가 죽었을 경우

리더가 죽으면 쓰기를 받을 곳이 없어지므로, 팔로워 중 하나를 새 리더로 올려야 한다. 순서는 다음과 같다.

1. **리더 장애 감지**: 보통 일정 시간 응답이 없으면(타임아웃) 죽었다고 판단한다.
2. **새 리더 선택**: 리더의 최신 데이터를 가장 많이 가진 팔로워를 고른다. 
3. **시스템 재설정**: 클라이언트의 쓰기가 새 리더로 가도록 바꾼다. 옛 리더가 살아 돌아오면 팔로워로 내려가게 해야 한다.

페일오버에서 생길 수 있는 문제는 다음과 같다.

- **쓰기 유실**: 비동기 복제라면 옛 리더에만 있던 쓰기는 사라진다.
- **스플릿 브레인**: 두 노드가 동시에 자기가 리더라고 믿고 둘 다 쓰기를 받는다.
- **타임아웃 설정**: 너무 길면 복구가 늦고, 너무 짧으면 불필요한 페일오버가 일어난다.

이런 문제들 때문에 자동 페일오버를 두지 않고 운영자가 직접 전환하는 곳도 많다.

### 복제 지연 문제

비동기 복제에서 팔로워로 읽기를 분산하면, 팔로워가 리더보다 늦게 반영되는 순간이 생긴다(복제 지연). 시간이 지나면 결국 맞춰지지만(최종적 일관성), 그 사이에 몇 가지 문제가 생긴다.

#### 자기가 쓴 내용 읽기 (read-after-write)

![[Pasted image 20261126214228.png]]

사용자가 댓글을 쓰면 쓰기는 리더로 간다. 바로 이어서 댓글 목록을 조회하는데, 이 읽기가 아직 반영되지 않은 팔로워로 가면 방금 쓴 댓글이 보이지 않는다. 사용자 입장에서는 저장이 안 된 것처럼 보인다.

다른 사람의 글이 조금 늦게 보이는 건 괜찮지만, **내가 쓴 글은 바로 보여야 한다**는 보장이 필요하다.

해결 방법

- **내가 수정할 수 있는 데이터는 리더에서 읽기**: 예를 들어 내 프로필은 리더에서, 남의 프로필은 팔로워에서 읽는다.
- **마지막 쓰기 후 일정 시간 동안은 리더에서 읽기**: 예를 들어 쓰고 나서 1분 동안은 리더에서 읽는다.
- **마지막 쓰기 시점을 기억하기**: 클라이언트가 마지막 쓰기 시점을 들고 있다가, 그 시점까지 반영된 레플리카에서만 읽는다.

#### 그 밖의 문제

- **단조 읽기**: 새로고침했더니 보였던 데이터가 사라진다. → 같은 사용자는 항상 같은 레플리카에서 읽게 한다.
- **일관된 순서로 읽기**: 질문보다 대답이 먼저 보인다. → 순서가 중요한 쓰기는 같은 파티션에 기록한다.

## 다중 리더 복제

### 동작 방식

쓰기를 받는 리더를 여러 대 둔다. 각 리더는 쓰기를 처리하고, 그 변경을 다른 리더들에게 전달한다. 리더는 동시에 다른 리더의 팔로워 역할도 한다.

단일 리더는 모든 쓰기가 리더 한 대를 거쳐야 한다. 리더와 연결이 끊기거나 리더가 멀리 있으면 쓰기를 못 하거나 느려지는데, 다중 리더는 이 제약을 없앤다.

### 사용 사례: 다중 데이터센터

데이터센터마다 리더를 둔다. 각 지역의 쓰기는 가까운 리더가 처리하고, 데이터센터끼리는 비동기로 복제한다. 쓰기 지연이 줄고, 한 데이터센터가 통째로 죽거나 데이터센터 간 네트워크가 끊겨도 각자 계속 동작한다.

### 쓰기 충돌

![[Pasted image 20261126214249.png]]

다중 리더의 가장 큰 문제다. 두 리더에서 같은 데이터를 동시에 다르게 수정하면, 각자는 성공했지만 나중에 복제할 때 충돌이 드러난다.

- 예: 위키 문서 제목을 사용자 1은 리더 A에서 "B"로, 사용자 2는 리더 B에서 "C"로 동시에 바꿈 → 최종 값은?

단일 리더라면 두 번째 쓰기가 첫 번째를 기다리거나 실패하면 되지만, 다중 리더는 둘 다 이미 성공한 뒤라 사후에 해결해야 한다.

#### 충돌 처리 방법

- **충돌 회피**: 특정 데이터는 항상 같은 리더에서만 쓰게 한다.
- **LWW (Last Write Wins)**: 
	1.  모든 쓰기에 타임스탬프를 붙인다.
	2. 같은 데이터에 쓰기가 여러 개 있으면, 타임스탬프가 가장 큰 쓰기만 남기고 나머지는 버린다.
	3. 모든 레플리카가 같은 규칙을 따르므로, 결국 모든 레플리카가 같은 값으로 맞춰진다.
- **사용자 정의 해소**: 충돌을 기록해두고 애플리케이션이나 사용자가 해결한다.

## 리더 없는 복제

### 동작 방식

![[Pasted image 20261126214323.png]]

리더 없이 모든 레플리카가 쓰기를 받는다. 클라이언트(또는 코디네이터 노드)가 쓰기를 여러 레플리카에 동시에 보내고, 읽기도 여러 레플리카에 동시에 요청한다.

- 예: Amazon Dynamo, Cassandra, Riak

리더가 없으니 페일오버도 없다. 일부 레플리카가 죽어 있어도, 정해진 수 이상만 응답하면 성공으로 본다.

### 죽었던 노드의 복구

죽었다 살아난 노드는 그동안의 쓰기를 놓쳐서 오래된 값을 가지고 있다. 이를 맞추는 방법은 두 가지다.

- **읽기 복구**: 여러 레플리카에서 읽었을 때 오래된 값을 가진 레플리카가 있으면, 그 자리에서 최신 값으로 덮어쓴다.
- **안티 엔트로피**: 백그라운드 프로세스가 레플리카 간 차이를 계속 찾아서 맞춘다.

### 정족수 (Quorum)

전체 레플리카 중 정해진 개수 이상에서 쓰기·읽기가 성공해야 성공으로 보는 방식이다. 쓰기와 읽기의 성공 개수를 충분히 크게 잡으면, 쓴 노드와 읽은 노드가 최소 하나는 겹쳐서 최신 값을 읽을 수 있다.

### 동시 쓰기 충돌

리더가 없으니 다중 리더처럼 같은 키에 동시 쓰기가 들어오면 충돌이 생긴다. 네트워크 지연 때문에 레플리카마다 쓰기가 도착하는 순서도 다를 수 있다.

- **LWW**: 가장 늦은 타임스탬프만 남긴다. 간단하지만 나머지 쓰기는 유실된다. Cassandra가 기본으로 쓰는 방식이다.
- **버전 벡터**: 각 쓰기에 버전을 붙여서 "한 쓰기가 다른 쓰기를 알고 덮어쓴 것인지, 서로 모르고 동시에 쓴 것인지"를 구분한다. 동시에 쓴 값은 둘 다 보관하고 병합은 애플리케이션이 한다.
