# 7장. 트랜잭션 (Transactions) — 정리 초안

> 초안 상태. 제품별 동작은 사용하는 버전에 따라 다를 수 있으므로 실습으로 확인이 필요한 항목은 `확인 필요`로 표시함.

## 0. 한눈에 보기

- 트랜잭션은 여러 읽기·쓰기를 하나의 논리적 단위로 묶는 추상화다.
- 묶인 연산은 전부 성공(commit)하거나 전부 실패(abort)한다. 부분 성공은 없다.
- 이 추상화 덕분에 애플리케이션은 장애와 동시성 문제의 상당수를 신경 쓰지 않아도 된다.
- 다만 "격리"의 강도는 DB마다, 설정마다 다르다. 이름만 믿고 쓰면 사고가 난다.
- 책의 흐름은 다음 순서다.
    1. 트랜잭션이 보장하는 것 (ACID)
    2. 약한 격리 수준과 그 아래에서 생기는 이상 현상
    3. 이상 현상을 모두 막는 직렬성(serializability)과 그 구현 방식 세 가지

---

## 1. 트랜잭션이란 무엇인가

### 1.1 왜 필요한가

- 데이터 시스템은 언제든 실패한다.
    - 쓰기 도중 DB 소프트웨어 또는 하드웨어가 죽는다.
    - 애플리케이션이 연산 중간에 죽는다.
    - 네트워크가 끊겨 클라이언트와 DB, 또는 DB 노드끼리 연결이 끊어진다.
    - 여러 클라이언트가 같은 데이터를 동시에 덮어쓴다.
    - 클라이언트가 일부만 반영된 중간 상태를 읽는다.
- 트랜잭션은 이 문제들을 DB가 대신 처리하도록 하는 수단이다.
- 트랜잭션이 없는 시스템은 모든 장애 조합을 애플리케이션 코드가 직접 다뤄야 한다.

### 1.2 ACID

ACID는 Atomicity(원자성), Consistency(일관성), Isolation(격리성), Durability(지속성)의 약자다.

> [!NOTE]
> **용어 설명 — 중단 가능성(abortability)**
> 트랜잭션이 도중에 실패하면 지금까지의 쓰기를 모두 취소할 수 있어야 한다는 성질이다. 책은 원자성을 "중단 가능성"이라 부르는 편이 더 정확하다고 본다.

| 속성 | 의미 | 주의할 점 |
|---|---|---|
| 원자성 (Atomicity) | 실패 시 부분 반영 없이 전부 취소됨 | 동시성과 무관함. 동시 접근은 격리성의 영역임 |
| 일관성 (Consistency) | 데이터가 항상 "좋은 상태"라는 애플리케이션 불변식이 유지됨 | DB가 아니라 애플리케이션의 책임임. DB는 불변식 유지를 돕는 도구(제약 조건 등)를 제공할 뿐임 |
| 격리성 (Isolation) | 동시에 실행되는 트랜잭션이 서로 간섭하지 않음 | 교과서 정의는 직렬성이나 실제 DB는 대부분 더 약하게 구현함 |
| 지속성 (Durability) | 커밋된 데이터는 장애가 나도 사라지지 않음 | 디스크 쓰기, WAL, 복제 등으로 확률을 낮출 뿐 절대 보장은 아님 |

- 일관성의 C는 다른 의미의 "일관성"(복제 일관성, 일관된 해싱 등)과 혼동되기 쉽다. 용어가 겹치는 점이 ACID라는 말이 모호해지는 이유 중 하나다.
- 지속성은 단일 노드에서는 WAL(Write-Ahead Log, 선행 기록 로그)로, 복제 환경에서는 여러 노드에 쓰였음을 확인하는 것으로 구현한다. 동시에 모든 복제본과 디스크가 손상되면 어떤 보장도 소용없다.
- "ACID를 지원한다"는 말은 구현마다 의미가 달라 마케팅 용어에 가깝다. 어느 수준의 격리를 주는지 확인해야 한다.

### 1.3 단일 객체 연산과 다중 객체 연산

- 다중 객체 트랜잭션: 여러 행·문서·테이블을 하나의 단위로 묶는다. 어떤 연산이 같은 트랜잭션에 속하는지는 보통 클라이언트 연결 단위(`BEGIN`~`COMMIT`)로 판단한다.
- 단일 객체 연산도 쓰기 도중 장애가 나면 문제가 된다. 대부분의 저장소는 단일 객체에 대해서는 원자성(로그로 복구)과 격리성(객체 단위 락)을 제공한다.
- 단일 객체용 보조 기능은 다음과 같다.
    - 원자적 증가 연산 (읽고-수정하고-쓰기 사이클 제거)
    - compare-and-set (CAS): 마지막으로 읽은 이후 값이 바뀌지 않았을 때만 쓰기를 허용함
- 이들은 "트랜잭션"이라 불리기도 하나 엄밀한 의미의 트랜잭션은 아니다. 트랜잭션은 여러 객체에 걸친 연산을 묶는 개념이다.

다중 객체 트랜잭션이 필요한 대표 사례는 다음과 같다.

- 관계형 모델에서 외래 키가 다른 테이블의 행을 가리킬 때
- 문서 모델에서 비정규화된 정보를 여러 문서에 함께 갱신할 때
- 보조 인덱스를 쓰는 DB에서 본 데이터와 인덱스를 함께 갱신할 때

일부 분산 데이터 저장소는 파티션을 넘나드는 트랜잭션의 비용 때문에 다중 객체 트랜잭션을 포기했다. 그 경우 오류 처리와 일관성 유지는 애플리케이션 몫이 된다.

### 1.4 중단과 재시도

- 중단(abort)의 목적은 안전한 재시도다. 그러나 재시도는 만능이 아니다.
    - 트랜잭션은 성공했으나 커밋 응답이 네트워크에서 유실되면, 클라이언트의 재시도로 중복 실행이 일어난다. 중복 제거 장치(트랜잭션 식별자 등)가 필요하다.
    - 오류가 과부하 때문이면 재시도가 상황을 악화시킨다. 재시도 횟수를 제한하고 지수 백오프를 쓴다.
    - 제약 위반처럼 영구적인 오류는 재시도해도 소용없다.
    - DB 밖에서 부수 효과(이메일 발송 등)가 있으면 재시도 시 되돌릴 수 없다.
    - 클라이언트가 재시도 도중 죽으면 그 데이터는 사라진다.
- 책의 관점: 중단 후 안전한 재시도는 트랜잭션이 주는 핵심 가치이지만, 애플리케이션이 이를 올바르게 처리하는 것은 별개의 문제다.

## 2. 약한 격리 수준 (Weak Isolation Levels)

- 직렬 격리는 성능 비용이 크다. 그래서 대부분의 DB는 기본값으로 더 약한 격리를 쓴다.
- 약한 격리는 이상 현상(race condition)을 일부만 막는다. 어떤 현상이 막히고 어떤 현상이 남는지 알아야 안전하게 쓸 수 있다.
- 실제 서비스에서 약한 격리가 낳은 버그는 금전 손실과 데이터 훼손으로 이어진 사례가 있다.

### 2.1 Read Committed (커밋 후 읽기)

가장 기본적인 격리 수준이며 두 가지를 보장한다.

1. **더티 읽기 방지**: 커밋되지 않은 다른 트랜잭션의 쓰기를 읽지 않는다.
2. **더티 쓰기 방지**: 커밋되지 않은 다른 트랜잭션의 쓰기를 덮어쓰지 않는다.

> [!NOTE]
> **용어 설명 — 더티 읽기 / 더티 쓰기**
> 더티 읽기는 아직 커밋되지 않은 값을 다른 트랜잭션이 읽는 것이다. 더티 쓰기는 아직 커밋되지 않은 값을 다른 트랜잭션이 덮어쓰는 것이다.

- 더티 읽기가 문제인 이유
    - 일부만 갱신된 상태가 보인다.
    - 이후 롤백되면 존재한 적 없는 값을 본 셈이 된다.
- 더티 쓰기가 문제인 이유: 여러 객체를 갱신하는 트랜잭션 두 개가 겹치면 결과가 뒤섞인다. (예: 중고차 판매에서 판매 목록은 A에게, 청구서는 B에게 가는 경우)
- 구현 방식
    - 더티 쓰기 방지: 행 단위 락. 쓰려는 트랜잭션이 락을 잡고, 다른 트랜잭션은 커밋 또는 중단까지 대기한다.
    - 더티 읽기 방지: 읽기에는 락을 쓰지 않는다. 쓰기 락을 읽기도 기다리게 하면 긴 쓰기 하나가 읽기를 막기 때문이다. 대신 DB는 이전 커밋된 값과 새 값을 둘 다 기억해 두고, 읽기에는 이전 값을 돌려준다.
- 이 수준에서도 남는 문제: 같은 트랜잭션 안에서 같은 행을 두 번 읽었는데 값이 다른 **반복 불가능 읽기(nonrepeatable read, 읽기 스큐)**.

### 2.2 스냅숏 격리와 반복 읽기 (Snapshot Isolation / Repeatable Read)

> [!NOTE]
> **용어 설명 — 읽기 스큐(read skew)**
> 한 트랜잭션이 읽는 도중 다른 트랜잭션이 커밋되어, 서로 다른 시점의 데이터가 섞여 보이는 현상이다. 예를 들어 두 계좌의 잔액을 차례로 읽는 사이에 송금이 커밋되면 합계가 맞지 않게 보인다.

- 읽기 스큐가 치명적인 경우
    - 백업: 오래 걸리는 백업이 새·옛 데이터를 섞어 담으면 복원 시 불일치가 영구화됨
    - 분석 쿼리, 무결성 검사: 서로 다른 시점의 값을 합산하면 의미 없는 결과가 나옴
- 해결책이 스냅숏 격리다. 각 트랜잭션은 시작 시점에 커밋되어 있던 데이터만 일관되게 본다. 이후 다른 트랜잭션의 변경은 보이지 않는다.
- 핵심 원칙: **읽는 쪽은 쓰는 쪽을 막지 않고, 쓰는 쪽은 읽는 쪽을 막지 않는다.** 그래서 긴 읽기 전용 쿼리를 쓰기 부하와 함께 돌릴 수 있다.

#### MVCC (Multi-Version Concurrency Control)

- 객체의 여러 버전을 동시에 보관해 구현한다.
- 각 쓰기에는 트랜잭션 ID가 붙고, 각 행은 생성한 트랜잭션과 삭제한 트랜잭션 정보를 가진다.
- 가시성 규칙(요약)
    - 읽기 트랜잭션이 시작되는 시점에 진행 중이던 트랜잭션의 쓰기는 무시한다.
    - 중단된 트랜잭션의 쓰기는 무시한다.
    - 더 늦은 트랜잭션 ID의 쓰기는 무시한다.
    - 나머지는 보인다.
- 더 이상 어떤 트랜잭션에도 보이지 않는 옛 버전은 가비지 컬렉션으로 정리한다.
- 인덱스는 구현에 따라 모든 버전을 가리키거나(필터링 필요), 추가 전용 B-트리처럼 쓰기마다 새 루트를 만드는 방식을 쓴다.

#### 이름의 혼란

- SQL 표준이 정의한 격리 수준 이름은 모호하며, 제품마다 의미가 다르다.
- Oracle의 "Serializable"은 사실 스냅숏 격리다.
- PostgreSQL과 MySQL의 "Repeatable Read"는 스냅숏 격리에 해당하나 세부 동작은 다르다. `확인 필요`
- 이름이 아니라 **어떤 이상 현상이 막히는지**로 판단해야 한다.

### 2.3 갱신 손실 (Lost Update)

> [!NOTE]
> **용어 설명 — 읽고-수정하고-쓰기 (read-modify-write)**
> 값을 읽어 애플리케이션에서 계산한 뒤 다시 쓰는 패턴이다. 두 트랜잭션이 같은 값을 동시에 읽고 각자 계산해 쓰면, 먼저 쓴 쪽의 갱신이 사라진다.

- 사례: 카운터 증가, 계좌 잔액 변경, JSON 문서의 일부 수정, 위키 문서 동시 편집
- 해결책
    1. **원자적 쓰기 연산**: `UPDATE counters SET value = value + 1 WHERE key = 'foo'` 처럼 DB가 읽고-수정하고-쓰기를 한 번에 처리한다. 가능하면 가장 먼저 선택할 방법이다.
    2. **명시적 잠금**: `SELECT ... FOR UPDATE`로 읽을 행을 미리 잠근다. 잠금 누락 시 버그가 생긴다.
    3. **갱신 손실 자동 감지**: 스냅숏 격리 환경에서 DB가 충돌을 감지해 한쪽을 중단한다. PostgreSQL의 반복 읽기, Oracle의 직렬화 가능, SQL Server의 스냅숏 격리가 해당한다. MySQL InnoDB의 반복 읽기는 감지하지 않는다고 책이 지적한다. `버전 확인 필요`
    4. **compare-and-set**: `UPDATE ... WHERE id = 1 AND content = '읽은 값'`. 조건 불일치 시 갱신되지 않는다. 주의: `WHERE`가 옛 스냅숏을 기준으로 평가되면 무력화될 수 있다.
- 복제 환경(다중 리더, 리더 없는 복제)에서는 락과 CAS가 통하지 않는다.
    - 충돌 시 여러 버전(sibling)을 만들고 애플리케이션이 병합한다.
    - 교환 법칙이 성립하는 연산(카운터 증가 등)은 복제본 간에도 병합할 수 있다.
    - 마지막 쓰기 승리(LWW, Last Write Wins)는 갱신 손실이 발생하기 쉬워 기본 해법으로 부적합하다.

### 2.4 쓰기 스큐와 팬텀 (Write Skew and Phantoms)

> [!NOTE]
> **용어 설명 — 쓰기 스큐(write skew)**
> 두 트랜잭션이 같은 데이터를 읽고 판단한 뒤 서로 **다른** 객체를 갱신해, 각자는 정상이나 합치면 불변식이 깨지는 현상이다. 갱신 손실(같은 객체를 덮어씀)의 일반화로 볼 수 있다.

- 대표 사례: 당직 의사 교대. 최소 한 명은 당직이어야 하는데, 두 의사가 동시에 "나 말고 한 명 더 있네"라고 읽고 각자 휴가를 신청하면 0명이 된다.
- 다른 사례
    - 회의실 예약 중복
    - 다중 플레이어 게임에서 두 말이 같은 칸으로 이동
    - 사용자명 선점 (중복 가입)
    - 이중 지출 (잔고 확인 후 두 건 차감)
- 공통 패턴
    1. `SELECT`로 조건을 확인한다.
    2. 결과에 따라 애플리케이션이 진행 여부를 결정한다.
    3. 쓰기를 수행한다. 이 쓰기가 1단계 결과의 전제를 바꾼다.
- 스냅숏 격리에서는 두 트랜잭션 모두 옛 스냅숏을 보므로 충돌이 감지되지 않는다. 갱신 대상 객체가 다르기 때문에 자동 감지도 소용없다.
- 막는 방법
    - 진정한 직렬성 격리 (가장 확실함)
    - 트랜잭션이 읽은 행에 `FOR UPDATE` 잠금. 단, 조회 결과가 "행이 없음"인 경우 잠글 대상이 없어 쓸 수 없다.
    - 제약 조건: 고유성 제약은 대부분 DB가 지원하나, 다중 객체에 걸친 제약은 지원이 드물다. 트리거나 실체화된 뷰로 흉내 낼 수 있다.

> [!NOTE]
> **용어 설명 — 팬텀(phantom)**
> 한 트랜잭션의 쓰기가 다른 트랜잭션의 검색 쿼리 결과를 바꾸는 현상이다. 검색 시점에는 없던 행이 쓰기 시점에 생겨나는 경우가 대표적이다.

- 팬텀 때문에 `FOR UPDATE`로는 "존재하지 않는 행"을 보호할 수 없다.
- 우회책: **충돌 실체화(materializing conflicts).** 시간대×회의실 조합을 미리 행으로 만들어 두고, 예약 시 그 행을 잠근다.
    - 단점: 동시성 제어 메커니즘이 데이터 모델에 새어 들어오는 보기 흉한 방식이다.
    - 직렬 격리를 쓸 수 없을 때의 최후 수단으로 본다.

## 3. 직렬성 (Serializability)

- 가장 강한 격리 수준이다. 동시에 실행되어도 결과가 어떤 순차 실행과 동일함을 보장한다.
- 앞선 이상 현상(읽기 스큐, 갱신 손실, 쓰기 스큐, 팬텀)이 모두 사라진다.
- 구현 방식은 크게 세 가지다.

| 방식 | 핵심 아이디어 | 성격 |
|---|---|---|
| 실제 직렬 실행 | 한 번에 하나씩 정말로 순차 실행 | 단순하나 처리량이 한 CPU 코어에 묶임 |
| 2PL | 읽기·쓰기 모두 락으로 막음 | 비관적, 대기·교착 상태 발생 |
| SSI | 스냅숏 격리 위에서 충돌을 감지해 중단 | 낙관적, 충돌 시 재시도 비용 |

### 3.1 실제 직렬 실행 (Actual Serial Execution)

- 동시성 문제를 피하는 가장 단순한 방법: 트랜잭션을 단일 스레드에서 하나씩 실행한다.
- 최근에야 현실적인 선택이 되었다.
    - RAM이 저렴해져 활성 데이터 전체를 메모리에 올릴 수 있다. 디스크 대기가 없어 단일 스레드로도 충분히 빠르다.
    - OLTP(Online Transaction Processing, 온라인 트랜잭션 처리) 트랜잭션은 짧고 읽기·쓰기가 적다는 점이 확인되었다. 긴 분석 쿼리는 별도의 스냅숏 읽기 전용 경로에서 처리한다.
- 대표 구현: VoltDB/H-Store, Redis, Datomic
- **저장 프로시저**: 사용자 입력을 기다리는 상호작용형 트랜잭션은 이 방식에서 쓸 수 없다. 트랜잭션 전체 코드를 미리 DB에 제출해 네트워크 왕복을 없앤다.
    - 장단점: 언어가 제각각이고 디버깅·버전 관리·모니터링이 어려우며, DB 서버에서 잘못된 코드는 모든 클라이언트에 영향을 준다.
    - 최근에는 범용 언어(Java, Groovy, Lua 등)를 지원하는 구현이 나왔다.
- **파티셔닝과의 관계**
    - 파티션마다 스레드 하나를 두면 파티션 수만큼 처리량을 늘릴 수 있다.
    - 단일 파티션 트랜잭션은 빠르다. 여러 파티션을 건드리는 트랜잭션은 파티션 간 조율(락 단계 동기화)이 필요해 크게 느려진다.
    - 따라서 데이터 모델이 파티셔닝에 잘 맞아야 한다. (6장의 파티셔닝 설계와 직결됨)
- **제약**
    - 처리량 상한은 단일 CPU 코어
    - 모든 트랜잭션이 작고 빨라야 함 (느린 하나가 전체를 막음)
    - 활성 데이터셋이 메모리에 들어가야 함 (디스크 접근이 필요한 트랜잭션은 큰 지연을 일으킴)
    - 파티션을 넘는 쓰기는 비쌈

### 3.2 2PL (Two-Phase Locking, 2단계 락킹)

> [!NOTE]
> **용어 설명 — 2PL과 2PC의 구분**
> 2PL(Two-Phase Locking)은 단일 DB 안에서 직렬성을 얻는 락 기법이다. 2PC(Two-Phase Commit, 2단계 커밋)는 여러 노드가 함께 커밋하도록 합의하는 프로토콜이며, 두 개념은 이름만 비슷하고 서로 무관하다. 2PC는 9장에서 다룬다.

- 약 30년간 사실상 유일한 직렬성 알고리즘이었다.
- 규칙
    - 읽기 락은 **공유(shared)** 모드. 다른 읽기와는 공존하나 쓰기와는 공존하지 못한다.
    - 쓰기 락은 **배타(exclusive)** 모드. 다른 어떤 접근도 허용하지 않는다.
    - 락은 트랜잭션 끝(커밋·중단)까지 유지한다.
- 스냅숏 격리와의 결정적 차이: **쓰는 쪽이 읽는 쪽을 막고, 읽는 쪽이 쓰는 쪽을 막는다.**
- 락이 많아지므로 **교착 상태(deadlock)** 가 쉽게 일어난다. DB가 감지해 한쪽을 중단하면 애플리케이션이 재시도한다.
- **성능 문제**
    - 락 획득·해제 오버헤드
    - 동시성 감소: 한 트랜잭션이 느리면 줄줄이 대기함
    - 지연 시간의 변동폭이 큼 (최악의 경우가 매우 느림)
- **술어 락(predicate lock)과 인덱스 범위 락**
    - 팬텀을 막으려면 "존재하지 않는 행"에 대한 조건도 잠가야 한다.
    - 술어 락: 조건(예: 특정 회의실·시간대)에 일치하는 모든 객체(미래에 추가될 객체 포함)에 락을 건다. 정확하나 검사 비용이 크다.
    - 인덱스 범위 락(next-key locking): 조건을 더 넓은 범위로 근사해 인덱스에 락을 건다. 과잉 잠금이지만 훨씬 싸므로 실무에서 주로 쓴다.
    - 적합한 인덱스가 없으면 테이블 전체에 락을 걸어 성능이 급락한다.

### 3.3 SSI (Serializable Snapshot Isolation, 직렬성 스냅숏 격리)

- 비교적 최근(2008년 박사 논문)에 제안된 알고리즘이다. 직렬성과 좋은 성능을 함께 얻으려는 시도다.
- **낙관적(optimistic) 동시성 제어**
    - 스냅숏 격리 위에서 충돌 가능성을 막지 않고 일단 진행시킨다.
    - 커밋 시점에 위험한 패턴이 있었는지 검사하고, 있으면 중단한다.
    - 반대로 2PL과 실제 직렬 실행은 **비관적** 방식이다.
- 감지해야 하는 것: **오래된 전제(outdated premise).** 트랜잭션이 읽은 결과를 근거로 쓰기를 결정했는데, 그 읽은 값이 이미 바뀌었을 가능성이다.
- 감지 방법 두 가지
    1. **오래된 MVCC 읽기 감지**: 트랜잭션이 읽을 때 무시된(아직 커밋되지 않았던) 쓰기가 있었다면, 그 쓰기가 커밋되었을 때 해당 트랜잭션의 읽기 근거가 낡았다고 보고 중단한다.
    2. **이전 읽기에 영향을 주는 쓰기 감지**: 인덱스 범위·행 단위로 "누가 읽었는지"를 기록해 두고, 다른 트랜잭션이 쓸 때 해당 읽기 트랜잭션에 알린다. 락과 달리 막지 않고 정보만 기록한다.
- 성능 특성
    - 읽기가 쓰기를 막지 않아 2PL보다 읽기 위주 부하에 유리하다.
    - 직렬 실행처럼 단일 CPU 코어에 묶이지 않는다.
    - 읽기 추적 정보는 너무 세밀하면 기록 오버헤드가 커지고, 너무 느슨하면 불필요한 중단이 늘어난다.
    - 읽기·쓰기 충돌이 많은 부하에서는 중단율이 높아져 성능이 떨어질 수 있다.
    - 읽기와 쓰기를 함께 하는 긴 트랜잭션은 중단될 가능성이 높다. 읽기·쓰기가 섞인 트랜잭션은 짧을수록 유리하다.
- 구현: PostgreSQL 9.1 이상의 직렬화 가능 격리 수준, FoundationDB 등. `확인 필요`

## 4. 격리 수준별 방지 현상 요약

| 격리 수준 | 더티 읽기 | 반복 불가능 읽기 (읽기 스큐) | 갱신 손실 | 쓰기 스큐 | 팬텀 |
|---|---|---|---|---|---|
| Read Uncommitted | 허용 | 허용 | 허용 | 허용 | 허용 |
| Read Committed | **방지** | 허용 | 허용 | 허용 | 허용 |
| 스냅숏 격리 (Repeatable Read) | **방지** | **방지** | 구현에 따라 다름 | 허용 | 허용(읽기 전용 쿼리는 일관되게 보임) |
| 직렬성 (Serializable) | **방지** | **방지** | **방지** | **방지** | **방지** |

- 스냅숏 격리의 "갱신 손실" 칸은 DB마다 다르다. 자동 감지가 있는 DB와 없는 DB가 있다.
- 스냅숏 격리의 "팬텀" 칸은 해석에 주의한다. 읽기 전용 쿼리는 일관된 스냅숏을 보지만, 읽고 쓰는 트랜잭션에서는 쓰기 스큐를 일으키는 팬텀이 여전히 가능하다.

### 기본 격리 수준 (대표 제품) `버전 확인 필요`

- PostgreSQL: Read Committed
- MySQL (InnoDB): Repeatable Read
- Oracle: Read Committed (이름은 Serializable이나 실제는 스냅숏 격리)
- SQL Server: Read Committed

## 5. 연결 지점: JPA 16장 (트랜잭션과 락)

같은 세션에서 다루는 JPA(Java Persistence API) 16장과의 대응 관계를 정리한다. `검토 필요`

| 책 7장 개념 | JPA에서의 대응 |
|---|---|
| compare-and-set | `@Version` 기반 낙관적 락. 갱신 시 버전을 비교하고 불일치하면 예외 발생 |
| `SELECT ... FOR UPDATE` | 비관적 락 (`PESSIMISTIC_WRITE`, `PESSIMISTIC_READ`) |
| 갱신 손실 | 낙관적 락 또는 비관적 락으로 방지 |
| 쓰기 스큐 | 서로 다른 엔티티를 갱신하므로 각 엔티티의 `@Version` 검사만으로는 막지 못함. 읽은 엔티티에도 락을 걸거나 직렬성 격리가 필요함 |
| 격리 수준 | DB 설정에 따른다. JPA가 격리 수준을 대신 올려 주지 않음 |

- 낙관적 락은 책에서 말하는 SSI의 낙관적 철학과 같은 계열이지만 같은 메커니즘은 아니다. 낙관적 락은 **단일 행 버전 비교**일 뿐, 읽은 근거의 유효성까지 추적하지는 않는다.
