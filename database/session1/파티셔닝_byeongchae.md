# 데이터베이스 파티셔닝(Partitioning) 개념 정리

## 1. 파티셔닝은 왜 필요한가

단일 서버 데이터베이스는 저장 용량, 쓰기 처리량, CPU 자원에 물리적 한계가 있다.

다음과 같은 상황이 오면 서버 사양을 올리는 것(스케일업)만으로는 한계에 부딪힌다.

- 데이터셋이 한 대의 디스크에 담을 수 없을 만큼 커졌을 때
- 초당 쓰기 요청량이 단일 노드의 처리 능력을 넘어설 때

이때 필요한 것이 **파티셔닝**이다.

> 파티셔닝: 데이터셋을 여러 파티션으로 나누고, 이를 여러 노드에 분산 배치하여 데이터와 부하를 나눠 처리하는 기법

노드가 10대면 이상적으로는 노드 하나가 전체 부하의 1/10만 처리하면 된다. 그래서 노드를 늘리는 것만으로 시스템 전체 처리 용량을 확장할 수 있다. 이것이 파티셔닝이 **확장성(scalability)** 확보의 핵심 수단인 이유다.

### 파티셔닝 vs 복제

자주 헷갈리는 개념이 복제(replication)다. 둘은 목적이 다르다.

| 구분 | 목적 | 데이터 총량 확장 |
|---|---|---|
| 복제 (Replication) | 고가용성, 지연시간 감소, 읽기 확장 | ❌ (모든 복제본이 전체 데이터를 동일하게 가짐) |
| 파티셔닝 (Partitioning) | 데이터/쓰기 부하 확장 | ✅ (각 노드가 일부만 담당) |

실무에서는 **둘을 함께 쓴다.** 데이터를 여러 파티션으로 나누고, 각 파티션을 다시 여러 노드에 복제한다. 이렇게 확장성과 고가용성을 동시에 확보한다.

## 2. 기본 용어

**노드 (Node)**
데이터베이스 소프트웨어가 실행되는 서버 하나. 여러 노드가 모여 클러스터를 구성한다.

**파티션 (Partition)**
전체 데이터셋을 나눈 하위 집합. 시스템마다 이름이 다르다.

- Cassandra → vnode
- HBase → region
- Bigtable → tablet
- MongoDB, Elasticsearch → shard

이름은 달라도 개념은 같다.

- 레코드 하나는 반드시 파티션 하나에만 속한다
- 각 파티션은 그 자체로 작은 독립 데이터베이스처럼 동작한다
- 노드 하나가 여러 파티션을 동시에 담당할 수 있다 (1:N)

**핫스팟 (Hot Spot)**
부하가 특정 파티션(=특정 노드)에 쏠리는 현상.

- 예: 유명인 계정에 접근이 몰림
- 예: 타임스탬프를 파티션 키로 써서 "오늘 데이터" 파티션에만 쓰기가 집중됨

나머지 노드는 한가한데 한 노드만 과부하 → 파티셔닝의 이점이 무력화됨. **파티션 키 설계가 핫스팟 방지의 핵심 과제.**

## 3. 파티셔닝의 범위 — 디스크 분할인가, 서버 분산인가

결론: **둘 다 파티셔닝이라 부를 수 있지만, 목적과 효과가 다르다.**

### 3-1. 단일 서버 내 분할 (RDBMS 테이블 파티셔닝)

하나의 테이블을 여러 물리 파일로 나누어 저장하는 방식. 얻는 이점:

- **파티션 프루닝**: 조회 조건에 안 맞는 파티션은 스캔 자체를 건너뜀 → 질의 속도 향상
- **유지보수 효율화**: 오래된 데이터를 지울 때 파티션을 통째로 drop 가능. 인덱스 재구성도 파티션 단위로 가능
- **스토리지 계층화**: 최근 데이터는 SSD, 오래된 데이터는 저렴한 스토리지로 분리
- **병렬 처리**: 멀티코어로 여러 파티션을 동시에 스캔

**한계**: 결국 한 대 서버의 CPU·메모리·디스크 IO 한도 안에서의 최적화일 뿐이다. 시스템 전체 처리 용량은 늘지 않는다.

### 3-2. 여러 서버에 걸친 분산 (DDIA가 다루는 파티셔닝)

데이터셋을 나눠서 **공유 자원이 없는(shared-nothing) 여러 노드**에 분산 배치. 각 노드가 전체 데이터/부하의 일부만 담당 → 이게 진짜 확장성을 준다.

> 실무에서는 두 방식을 같이 쓴다. 분산 시스템의 노드 하나가 담당하는 파티션 내부에서, 다시 로컬 디스크 수준의 파티셔닝(3-1)을 적용하는 경우가 흔하다.

## 4. 파티셔닝 도입 시 함께 고려해야 할 문제

### 4.1 요청 라우팅 — "이 데이터, 어느 노드에 있지?"

데이터가 여러 노드에 흩어지면, 클라이언트는 원하는 데이터가 어느 노드에 있는지 알아야 한다. (노드 발견 문제, node discovery problem)

**해결 방식 3가지**

1. 아무 노드에나 요청 → 담당 노드가 아니면 그 노드가 알아서 전달(forward)
2. 별도 라우팅 계층(routing tier)을 두고, 클라이언트는 항상 여기로만 요청
3. 클라이언트가 파티셔닝 규칙을 직접 알고 처음부터 정확한 노드로 요청

셋 다 공통 과제: **"파티션이 어느 노드에 있는가" 매핑 정보를 최신으로 유지하는 것.** 노드 추가/제거·리밸런싱이 일어나면 이 매핑이 바뀌기 때문이다.

**매핑 정보를 관리하는 두 방식**

- 코디네이션 서비스(ZooKeeper 등)를 두고 각 노드가 구독 → HBase, Kafka
- 코디네이션 서비스 없이 노드끼리 가십 프로토콜로 상태 전파 → Cassandra, Riak

이 매핑은 캐시되어 쓰이므로, 평상시엔 라우팅이 큰 부담이 아니다. 리밸런싱 도중 일시적으로 어긋나면 재시도로 처리한다.

> ⚠️ 오해하기 쉬운 지점: Cassandra, Kafka는 "RDBMS에 라우팅 기능을 붙이는 솔루션"이 아니다. **그 자체가 파티셔닝·라우팅을 내장한 분산 시스템**이다. 개발자는 클러스터 아무 노드에나 드라이버로 요청을 보내면 되고, 라우팅·리밸런싱은 내부에서 자동 처리된다.

**RDBMS는 분산 파티셔닝이 기본 내장이 아니므로, 확장하려면 선택지가 3가지다**

| 방식 | 설명 | 예시 |
|---|---|---|
| 애플리케이션 레벨 샤딩 | 앱 코드가 직접 어느 DB에 쿼리할지 계산 | 초기 대형 서비스들의 수동 샤딩 |
| 미들웨어/프록시 | 앱과 DB 사이에 라우팅 전담 계층 | Vitess(MySQL), Citus(PostgreSQL) |
| 분산 SQL (NewSQL) | 처음부터 SQL + 자동 파티셔닝 내장 | CockroachDB, Spanner, TiDB |

애플리케이션 레벨 샤딩은 구현은 단순하지만, 파티션 경계를 넘는 조인·트랜잭션·리밸런싱을 전부 앱이 직접 떠안아야 한다.

### 4.2 트랜잭션 관리 — 여러 노드에 걸친 트랜잭션은 왜 어려운가

단일 노드 DB에서는 모든 데이터가 한 곳에 있어 ACID를 한 프로세스 안에서 보장할 수 있었다.

파티셔닝 후에는 하나의 트랜잭션이 **여러 노드**에 걸친 데이터를 동시에 수정해야 할 수 있다.

> 예: 서로 다른 파티션에 있는 두 계좌 간 송금 → 두 노드가 함께 성공하거나 함께 실패해야 함

**어려운 이유**: 네트워크가 끼기 때문이다. 지연, 타임아웃, 부분 실패(partial failure) 가능성이 항상 있다. 한쪽만 성공하면 정합성이 깨진다.

표준 해법은 **2단계 커밋(2PC)** 이지만, 모든 노드가 응답할 때까지 블로킹되고 코디네이터 장애 시 시스템이 멈출 수 있어 비용이 크다.

> **2PC(Two-Phase Commit)란?**
> 여러 노드에 걸친 트랜잭션을 원자적으로 처리하기 위한 프로토콜. 별도의 **코디네이터**가 각 노드(참여자)를 두 단계로 조율한다.
>
> 1. **준비 단계(Prepare)**: 코디네이터가 모든 참여 노드에 "커밋할 수 있는지" 묻는다. 각 노드는 실제 커밋은 하지 않고, 커밋이 가능한 상태로 준비만 해둔 뒤 "예/아니오"로 응답한다.
> 2. **커밋 단계(Commit)**: 모든 노드가 "예"라고 답하면 코디네이터가 전체에 커밋 명령을 보낸다. 하나라도 "아니오"거나 응답이 없으면 전체에 롤백을 지시한다.
>
> 이렇게 하면 모든 노드가 함께 성공하거나 함께 실패하는 원자성을 보장할 수 있다. 하지만 **모든 참여 노드가 응답할 때까지 다른 요청들이 대기(블로킹)** 해야 하고, **준비 단계 이후 코디네이터가 죽으면** 참여 노드들은 커밋해야 할지 롤백해야 할지 알 수 없는 상태로 멈춰버릴 수 있다. 이런 이유로 성능과 가용성 측면에서 비용이 큰 프로토콜로 여겨진다.

**실무 대응 방식 2가지**

- 대다수 NoSQL: 단일 파티션 내 원자성만 보장, 여러 파티션 트랜잭션은 미지원/제한적 지원 → **함께 쓰이는 데이터를 같은 파티션에 두도록 설계**해서 회피
- NewSQL(Spanner, CockroachDB 등): 파티션 간 분산 트랜잭션 지원, 대신 2PC급 합의 프로토콜의 지연시간 비용을 감수

**핵심 통찰**: 분산 환경에서는 단일 노드였다면 공짜였던 원자성·즉각적 일관성에 비용이 붙는다. 얼마나 강한 보장이 정말 필요한지 파티션 설계 단계에서 미리 고민해야 한다.

## 5. 리밸런싱 — 노드 추가/제거 시 파티션 재분배

노드를 추가하거나(트래픽 증가) 제거할 때(자원 절약), 파티션을 노드 사이에 다시 나누는 과정이 **리밸런싱(rebalancing)**이다.

**만족해야 할 조건 3가지**

- 리밸런싱 후에도 부하가 노드 간에 고르게 분산될 것
- 진행 중에도 읽기·쓰기가 계속 가능할 것 (무중단)
- 꼭 필요한 최소한의 데이터만 이동할 것

**대표 전략 3가지**

| 전략 | 방식 | 예시 |
|---|---|---|
| 고정 개수 파티션 | 노드보다 훨씬 많은 파티션(예: 1,000개)을 미리 만들고, 통째로 옮김 | Cassandra, Elasticsearch |
| 동적 파티셔닝 | 파티션이 커지면 분할, 작아지면 병합 | HBase, RethinkDB |
| 노드 비례 파티셔닝 | 노드당 파티션 개수를 고정 비율로 유지 | 초기 Cassandra |

**주의**: 리밸런싱 완전 자동화는 위험할 수 있다. 일시적으로 느려진 노드를 장애로 오판 → 불필요한 대규모 이동 → 부하 가중 → 연쇄 장애로 이어질 수 있다. 그래서 **사람이 승인하는 반자동 방식**이 흔히 쓰인다.

## 6. 파티셔닝 안 된 기존 시스템을 무중단 전환하기

이미 운영 중인 단일 DB를 파티셔닝 구조로 바꿔야 할 때, 일반적인 절차는 다음과 같다.

1. **이중 쓰기 또는 CDC 동기화** — 앱이 기존 DB와 새 DB에 동시에 쓰거나, CDC 도구로 기존 DB의 로그를 실시간 복제
2. **백필(Backfill)** — 기존 데이터 전체를 배치로 새 구조에 복사
3. **검증(Shadowing)** — 읽기 요청을 양쪽 DB에 보내 결과 비교 (새 DB 응답은 사용자에게 노출 안 함)
4. **읽기 전환(Cutover)** — 검증 후 읽기 트래픽을 1% → 10% → 100% 점진적으로 이전
5. **쓰기 전환 및 기존 시스템 폐기** — 마지막으로 쓰기까지 이전 후 기존 DB 정지

> CDC 도구(예: Debezium)를 쓰면 앱 코드를 이중 쓰기로 직접 고치지 않아도, 기존 DB의 변경 로그를 실시간으로 새 시스템에 반영할 수 있다. 그래서 실무에서 널리 쓰인다.

## 7. 한 줄 정리

- 파티셔닝 = 데이터를 나눠서 여러 노드에 분산 → **확장성** 확보
- 복제와 결합해서 확장성 + 고가용성을 함께 확보하는 게 일반적
- 도입하면 따라오는 3대 과제: **요청 라우팅 / 트랜잭션 관리 / 리밸런싱**
- 이 과제들은 단일 노드 환경엔 없던, **분산 환경 고유의 비용**
- RDBMS를 파티셔닝하려면: 앱 레벨 샤딩 / 미들웨어 / NewSQL 중 선택
- 기존 시스템 전환은: CDC + 점진적 트래픽 이전이 실무 표준
