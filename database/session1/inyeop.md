## 파티셔닝이란

대용량 데이터셋을 작은 단위인 파티션으로 나누는 것.

주된 목적은 확장성이다. 너무 큰 데이터셋에 대한 읽기와 쓰기 부담을 줄이기 위해
독립된 자원을 가진 여러 노드에 파티션을 분산할 수 있다.

- 노드: 하나의 컴퓨터
- 클러스터: 여러 노드의 묶음

## 파티션의 쏠림

파티셔닝이 고르게 이뤄지지 않으면 특정 파티션에 데이터나 요청이 집중될 수 있다.
이를 **쏠림(skew)**이라고 한다.

불균형하게 부하가 높은 파티션을 **핫스팟(hot spot)**이라고 한다.


# 키-값 데이터 파티셔닝

`key`를 기준으로 데이터를 여러 파티션에 분배하는 것.

여기서 `key`는 **파티션을 결정하는 기준이 되는 데이터의 키**이며, 반드시 기본키를 의미하는 것은 아니다.

## 1. 키 범위 기준 파티셔닝

각 파티션에 **연속된 범위의 키**를 할당하는 기법.

```
id 1~100    → 파티션 1
id 101~200  → 파티션 2
id 201~300  → 파티션 3
```

파티션의 경계를 **적절하게 설정해 데이터가 고르게 분산되도록** 해야 한다.

**장점**

- 어떤 키가 어느 파티션에 속하는지 쉽게 알 수 있다.
- 키가 정렬되어 있으므로 **범위 스캔에 유리하다.**

**단점**

- 키의 분포나 접근 패턴에 따라 **핫스팟**이 발생할 수 있다.
- 예: 타임스탬프를 키로 사용하면 최근 데이터가 저장되는 파티션에 요청이 집중될 수 있다.

---

## 2. 키의 해시값 기준 파티셔닝

`key`의 **해시값을 이용해 파티션을 결정**하는 기법.

**파티셔닝용 해시 함수의 조건**

- 암호학적으로 강력할 필요는 없다.
- 같은 키를 입력하면 **여러 노드에서 항상 같은 해시값**이 나와야 한다.
- 해시값이 **고르게 분포**되어야 한다.

**장점**

- 데이터를 여러 파티션에 **고르게 분산**시키기 쉽다.
- 해시값을 이용해 특정 키가 어느 파티션에 있는지 **계산할 수 있다.**

**단점**

- 키의 순서가 보존되지 않아 **범위 쿼리에 불리하다.**
- 범위 쿼리에서는 여러 파티션을 조회해야 할 수 있다.

### 여러 필드로 구성된 키

키의 첫 번째 부분에 해싱을 적용해 **파티션을 결정**하고, 나머지 컬럼은 **파티션 내부의 데이터 정렬 순서**에 사용할 수 있다.

예:
```
(user_id, timestamp)

user_id
  ↓
해싱
  ↓
파티션 결정

timestamp
  ↓
파티션 내부 정렬 기준
```

```
파티션 내부

(user_id=100, timestamp=09:00)
(user_id=100, timestamp=10:00)
(user_id=100, timestamp=11:00)
```

이렇게 하면 관련 데이터가 정렬된 범위에 모이므로 **범위 스캔과 여러 관련 레코드 조회에 유리**하다.


---

## 해시 파티셔닝과 핫스팟

해시 파티셔닝은 **서로 다른 키를 여러 파티션에 고르게 분산**하는 데 효과적이다.

하지만 특정 키 하나에 요청이 집중되는 경우에는 핫스팟을 완전히 제거할 수 없다.

예:

```
유명인 ID = 123
       ↓
   hash(123)
       ↓
   파티션 2
       ↓
🔥🔥🔥🔥🔥🔥🔥
수백만 명의 팔로워 요청
```

### 애플리케이션을 통한 쏠림 완화

키 앞이나 뒤에 **임의의 숫자 등을 추가하여 하나의 키를 여러 키로 분산**할 수 있다.

```
123 → 123-1
123 → 123-2
123 → 123-3
...
```

이를 통해 여러 파티션으로 분산시킬 수 있다.

**단점**

- 읽을 때 여러 파티션에 흩어진 데이터를 **다시 조합해야 한다.**
- 분할된 데이터를 추적하기 위한 **추가 저장 공간과 관리 로직**이 필요하다.


**범위 쿼리가 중요한지, 데이터가 고르게 분산되는 것이 중요한지, 핫스팟 가능성이 있는지 등 요구사항에 따라 적절한 키 전략을 선택하고 트레이드오프를 고려해야 한다.**


## 파티션과 인덱스
파티션을 여러 개로 나누면 각 파티션이 실제 데이터를 저장하고, 인덱스도 파티션별로 존재할 수 있다.

```
events
│
├── Partition 1
│   ├── 실제 데이터
│   └── 인덱스
│
├── Partition 2
│   ├── 실제 데이터
│   └── 인덱스
│
└── Partition 3
    ├── 실제 데이터
    └── 인덱스
```



## 파티셔닝과 보조 색인
보조 색인은 PK가 아닌 다른 컬럼으로 빠른 조회를 위한 색인이다.  
기본 키를 기준으로 파티셔닝했다면, 보조 색인을 이용한 조회 시 그 값만으로는 데이터가 어느 파티션에 있는지 알 수 없다 — 파티셔닝 기준(PK)과 조회 기준(보조 색인 컬럼)이 다르기 때문이다.  
파티셔닝을 하지 않은 단일 노드에서는 모든 데이터가 한곳에 있으므로 이 문제 자체가 생기지 않는다.

이를 해결하기 위해 2가지 방법이 있다.

1. 문서 기준 보조 색인 파티셔닝(지역 색인)
   각 파티션이 자기 파티션에 속한 데이터에 대해서만 보조 색인을 유지한다.

- 장점: 쓰기(생성, 삭제, 수정) 작업에 좋다
    - 문서 하나를 쓸때 데이터와 색인이 해당 파티션 내에서만 갱신하면 됨.(로컬 트랜잭션)
- 단점: 읽기에 안좋음
    - 조회 조건에 맞는 데이터가 여러 파티션에 흩어져 있을 수 있어 어느 파티션에 있는지 특정할 수 없다.
      => 모든 파티션에 질의를 보내야함.(scatter/gather)

최대한 단일 파티션에서 조회될 수 있도록 파티셔닝 키를 설계해야한다.
서비스상 자주 사용되는 필터를 파티셔닝 키로 설계한다면 예를 들어 자동차 조회 서비스에서 항상 where user_id = ? 필터가 들어간다면 user_id를 파티셔닝 키로 설계할 수 있다. 이렇게 하면 조회시 파티셔닝키가 조회조건으로 들어가기 때문에 파티셔닝키로 파티션을 바로 찾을 수 있다.


**2. 용어 기준 보조 색인 파티셔닝(글로벌 색인)**

- 모든 파티션의 데이터를 담당하는 **전역 색인**
- → **보조 색인 키를 기준으로 색인 자체도 파티셔닝함**
- **장점: 읽기에 좋다.**
    - 보조 색인으로 **색인 파티션을 찾고**
    - 거기서 **기본키(또는 데이터 위치 정보)**를 찾아
    - 실제 데이터가 있는 파티션을 찾음
    - → **최대 2단계로 찾아갈 수 있음**
- **단점: 쓰기에 안 좋다.**
    - 데이터가 갱신되면 **데이터 파티션뿐만 아니라 다른 노드에 있는 보조 색인 파티션도 갱신해야 할 수 있음**
    - → **분산 트랜잭션이 필요할 수 있음**
- **전역 보조 색인은 대개 비동기로 적용된다.**
    - → 그래서 **색인과 실제 데이터 사이에 잠시 불일치가 발생할 수 있음**
