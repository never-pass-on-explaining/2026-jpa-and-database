# 파티셔닝 (Partitioning)

## 파티셔닝이란

대용량 데이터셋을 작은 단위인 파티션으로 나누는 것.
샤딩은 나뉜 파티션을 여러 노드에 분산하는 것이며, 각 조각을 샤드라 부른다.

분산 환경에서의 주된 목적은 확장성이다. 너무 큰 데이터셋에 대한 읽기와 쓰기 부담을 줄이기 위해
독립된 자원을 가진 여러 노드에 파티션을 분산할 수 있다.

- **노드**: 하나의 컴퓨터
- **클러스터**: 여러 노드의 묶음

## 파티션의 쏠림

파티셔닝이 고르게 이뤄지지 않으면 특정 파티션에 데이터나 요청이 집중될 수 있다.
이를 **쏠림(skew)** 이라고 한다.

불균형하게 부하가 높은 파티션을 **핫스팟(hot spot)** 이라고 한다.

쏠림과 핫스팟은 결국 **어떤 기준으로 데이터를 나눴는가**에서 비롯된다.
따라서 파티셔닝의 핵심은 **파티션을 나누는 기준이 되는 키를 잘 설계하는 것**이다.
여기서 `key`는 **파티션을 결정하는 기준이 되는 데이터의 키**이며, 반드시 기본키를 의미하는 것은 아니다.


### 1. 키 범위 기준 파티셔닝

각 파티션에 **연속된 범위의 키**를 할당하는 기법.

```text
id 1~100    → 파티션 1
id 101~200  → 파티션 2
id 201~300  → 파티션 3
```

파티션의 경계를 **적절하게 설정해 데이터가 고르게 분산되도록** 해야 한다.

**장점**

- 어떤 키가 어느 파티션에 속하는지 쉽게 알 수 있다.
- 키가 정렬되어 있으므로 **범위 스캔에 유리하다.**

**단점**

- 키의 분포나 접근 패턴에 따라 **핫스팟**이 발생할 수 있다.
- 예: 타임스탬프를 키로 사용하면 최근 데이터가 저장되는 파티션에 요청이 집중될 수 있다.

### 2. 키의 해시값 기준 파티셔닝

`key`의 **해시값을 이용해 파티션을 결정**하는 기법.

해시값은 해시 함수를 실행한 결과로
해시 함수는 데이터를 특정 규칙에 따라 숫자나 다른 값으로 변환하는 함수이다.

**파티셔닝용 해시 함수의 조건**

- 암호학적으로 강력할 필요는 없다.
- 같은 키를 입력하면 **여러 노드에서 항상 같은 해시값**이 나와야 한다.
- 해시값이 **고르게 분포**되어야 한다.

**장점**

- 데이터를 여러 파티션에 **고르게 분산**시키기 쉽다.
- 해시값을 이용해 특정 키가 어느 파티션에 있는지 **계산할 수 있다.**

**단점**

- 키의 순서가 보존되지 않아 **범위 쿼리에 불리하다.**
- 범위 쿼리에서는 여러 파티션을 조회해야 할 수 있다.

### 3. 여러 필드로 구성된 키(복합키)

키의 첫 번째 부분에 해싱을 적용해 **파티션을 결정**하고, 나머지 컬럼은 **파티션 내부의 데이터 정렬 순서**에 사용할 수 있다.

예:

```text
(user_id, timestamp)

user_id
  ↓
해싱
  ↓
파티션 결정

timestamp
  ↓
파티션 내부 정렬 기준
```

```text
파티션 내부

(user_id=100, timestamp=09:00)
(user_id=100, timestamp=10:00)
(user_id=100, timestamp=11:00)
```

이렇게 하면 관련 데이터가 정렬된 범위에 모이므로 **범위 스캔과 여러 관련 레코드 조회에 유리**하다.

| 조회 형태 | 범위 키 | 해시 키 | 복합 키 |
| --- | --- | --- | --- |
| `user_id=500` | 빠름 | 빠름 | 빠름 |
| `user_id=500 AND date BETWEEN ...` | 빠름 | 스캐터 | **빠름** |
| `date BETWEEN ...` (user_id 없이) | 빠름 | 스캐터 | 스캐터 |

### 4. 해시 파티셔닝과 핫스팟

해시 파티셔닝은 **서로 다른 키를 여러 파티션에 고르게 분산**하는 데 효과적이다.

하지만 특정 키 하나에 요청이 집중되는 경우에는 핫스팟을 완전히 제거할 수 없다.

예:

```text
유명인 ID = 123
       ↓
   hash(123)
       ↓
   파티션 2
       ↓
수백만 명의 팔로워 요청
```

#### 애플리케이션을 통한 쏠림 완화

키 앞이나 뒤에 **임의의 숫자 등을 추가하여 하나의 키를 여러 키로 분산**할 수 있다.

```text
123 → 123-1
123 → 123-2
123 → 123-3
...
```

이를 통해 여러 파티션으로 분산시킬 수 있다.

**단점**

- 읽을 때 여러 파티션에 흩어진 데이터를 **다시 조합해야 한다.**
- 분할된 데이터를 추적하기 위한 **추가 저장 공간과 관리 로직**이 필요하다.

> 범위 쿼리가 중요한지, 데이터가 고르게 분산되는 것이 중요한지, 핫스팟 가능성이 있는지 등
> 요구사항에 따라 적절한 키 전략을 선택하고 트레이드오프를 고려해야 한다.


## 파티셔닝과 보조 색인


파티션을 여러 개로 나누면 각 파티션이 실제 데이터를 저장하고, 인덱스도 파티션별로 존재한다.

```text
events
│
├── Partition 1
│   ├── 실제 데이터
│   └── 인덱스
│
├── Partition 2
│   ├── 실제 데이터
│   └── 인덱스
│
└── Partition 3
    ├── 실제 데이터
    └── 인덱스
```


보조 색인은 PK가 아닌 다른 컬럼으로 빠른 조회를 위한 색인이다.
기본 키를 기준으로 파티셔닝했다면, 보조 색인을 이용한 조회 시 데이터가 어느 파티션에 있는지 알 수 없다.

이를 해결하기 위해 2가지 방법이 있다.

### 1. 문서 기준 보조 색인 파티셔닝 (지역 색인)

각 파티션이 자기 파티션에 속한 데이터에 대해서만 보조 색인을 유지한다.

- **장점: 쓰기(생성, 삭제, 수정) 작업에 좋다.**
  - 문서 하나를 쓸 때 데이터와 색인을 해당 파티션 내에서만 갱신하면 된다. (로컬 트랜잭션)
- **단점: 읽기에 좋지 않다.**
  - 조회 조건에 맞는 데이터가 여러 파티션에 흩어져 있을 수 있어 어느 파티션에 있는지 특정할 수 없다.
  - → 모든 파티션에 질의를 보내야 한다. (scatter/gather)

최대한 단일 파티션에서 조회될 수 있도록 파티셔닝 키를 설계해야 한다.
서비스상 자주 사용되는 필터를 파티셔닝 키로 설계한다. 예를 들어 자동차 조회 서비스에서 항상 `WHERE user_id = ?` 필터가 들어간다면 `user_id`를 파티셔닝 키로 설계할 수 있다.
이렇게 하면 조회 시 파티셔닝 키가 조회 조건으로 들어가기 때문에 파티셔닝 키로 파티션을 바로 찾을 수 있다.

### 2. 용어 기준 보조 색인 파티셔닝 (글로벌 색인)

모든 파티션의 데이터를 담당하는 **전역 색인**
→ **보조 색인 키를 기준으로 색인 자체도 파티셔닝한다.**

- **장점: 읽기에 좋다.**
  - 보조 색인으로 **색인 파티션을 찾고**
  - 거기서 **기본키(또는 데이터 위치 정보)** 를 찾아
  - 실제 데이터가 있는 파티션을 찾는다.
  - → **최대 2단계로 찾아갈 수 있다.**
- **단점: 쓰기에 좋지 않다.**
  - 데이터가 갱신되면 **데이터 파티션뿐만 아니라 다른 노드에 있는 보조 색인 파티션도 갱신해야 할 수 있다.**
  - → **분산 트랜잭션이 필요할 수 있다.**
- **전역 보조 색인은 대개 비동기로 적용된다.**
  - → 그래서 **색인과 실제 데이터 사이에 잠시 불일치가 발생할 수 있다.**

## 파티션 재균형화

시간이 지나면 **DB에 노드가 추가되거나 삭제, 교체**될 수 있다.

**파티션을 노드 간에 재분배하여 부하를 균등하게 만드는 과정**을 재균형화라고 한다.

### 최소 요구사항

- 재균형화 후 **부하가 균등하게 분배**되어야 함
- 재균형화 도중에도 **읽기/쓰기가 가능**해야 함
- 빠른 재균형화를 위해 **노드들 사이에 데이터가 필요 이상으로 옮겨져서는 안 됨**

### 전략

#### 1. 파티션 개수 고정

- **노드보다 파티션 수를 많이 설정**
- **파티션 수를 고정**

4개의 노드가 있고 파티션을 20개로 나누면 각 노드당 5개의 파티션을 가진다.

```text
노드 4개 / 파티션 20개

A → 5개
B → 5개
C → 5개
D → 5개
```

노드가 5개로 늘어나면 기존 노드에서 파티션을 일부 떼서 새로운 노드에 나눠준다.

```text
노드 5개 / 파티션 20개

A → 4개
B → 4개
C → 4개
D → 4개
E → 4개
```

**파티션이 통째로 이동**하므로 파티션 내부의 데이터나 **할당된 키를 변경할 필요가 없다.**

운영이 단순해지지만 **파티션 수를 초기에 고정**하기 때문에 미래의 데이터 증가와 노드 증가를 고려해 충분히 높은 값을 설정해야 한다.

파티션 개수가 적으면 **파티션 하나당 담기는 데이터 양이 많아진다.**

```text
노드 하나가 장애 발생
  → 해당 노드가 맡던 파티션을 다른 노드로 복구
  → 파티션이 크면 복사해야 할 데이터가 많음
  → 네트워크/디스크 작업이 많아짐
  → 복구 완료까지 오래 걸림
```

반대로 파티션 개수가 너무 많으면 **파티션 관리 비용이 커질 수 있다.**

→ **적절한 파티션 개수를 설정해야 한다.**

#### 2. 동적 파티셔닝

- **파티션 크기가 설정된 임계값을 넘으면 2개로 분할**
- 반대로 **파티션 크기가 임계값보다 작아지면 인접한 파티션과 병합**

따라서 **데이터가 적으면 파티션 개수도 적고, 데이터가 많아지면 파티션 개수도 많아진다.**

빈 DB에서 시작하면 **파티션이 하나**일 수 있다.

데이터가 적을 때는 파티션이 분리되지 않아 **하나의 노드에만 부하가 집중되고 다른 노드는 유휴 상태**가 될 수 있다.

일부 DB에서는 이러한 문제를 해결하기 위해 **사전 분할(pre-splitting)** 을 지원한다.

#### 3. 노드 비례 파티셔닝

- **노드당 할당되는 파티션 수를 고정**
- 노드가 추가되면 **파티션도 추가**

예를 들어:

```text
노드 4개 → 파티션 40개 → 노드당 10개

노드 5개 → 파티션 50개 → 노드당 10개
```

노드 수가 적으면 **파티션 크기가 커지고**, 노드 수가 많아지면 **파티션 크기는 작아진다.**

### 자동/수동 재균형화

#### 완전 자동화

시스템이 **자동으로 파티션을 재배치**한다.

- 장점: **유지보수가 편하다.**
- 단점: **예상하지 못한 데이터 이동이 발생할 수 있다.**

#### 완전 수동화

관리자가 **직접 파티션 배치를 결정하고 재균형화를 수행**한다.

- 장점: **데이터 이동을 직접 통제할 수 있다.**
- 단점: **운영 및 유지보수 부담이 크다.**

#### 중간 방식

시스템이 **적절한 파티션 배치를 제안**하고, 관리자가 확인한 후 **실제로 반영**한다.

## 요청 라우팅

재균형화 등으로 인해 **파티션이 어느 노드에 있는지 계속 변경될 수 있다.**
따라서 클라이언트가 요청을 보낼 때 **어느 노드가 해당 파티션을 담당하는지 알아야 한다.**

### 요청 라우팅 방법

#### 1. 아무 노드에 접근

아무 노드에 요청을 보낸다.

- 해당 노드에 찾는 파티션이 있으면 **직접 처리**
- 없으면 **올바른 노드로 요청을 전달**
- → **모든 노드가 노드-파티션 정보를 알고 있어야 한다.**

#### 2. 전용 라우팅 계층

별도의 **라우팅 계층**에서 요청을 처리할 노드를 알아내고 해당 노드로 요청을 전달한다.

→ **라우팅 계층이 노드-파티션 정보를 알고 있어야 한다.**

#### 3. 클라이언트가 알고 있음

클라이언트가 **노드-파티션 정보를 알고 있어서** 해당 파티션을 담당하는 노드에 직접 요청한다.

### 코디네이션 서비스

**ZooKeeper 같은 코디네이션 서비스를 사용**할 수 있다.

노드-파티션 정보를 저장하는 **중앙 저장소** 역할을 한다.

- 어느 노드에 어느 파티션이 있는지 정보를 저장
- 노드, 라우팅 계층, 클라이언트가 정보를 구독
- **파티션 매핑이 변경되면 구독한 대상에게 알림**

→ **중앙에서 노드-파티션 정보를 관리한다.**

### 가십 프로토콜

별도의 **중앙 서비스가 없다.**

노드들이 서로 정보를 전달하면서 **노드-파티션 정보를 공유**한다.

예:

- 노드 A가 **새로운 파티션 매핑 변경**을 알게 됨
- A가 무작위로 선택한 몇몇 이웃 노드(B, C 등)에게 전달
- B, C도 다시 다른 이웃 노드에게 전달
- 이런 방식으로 **변경된 정보가 전체 노드로 전파됨**

→ **중앙 서비스 없이 노드들끼리 정보를 전파한다.**
