# 목표
데이터 사용 목적(OLTP/OLAP)에 따른 저장소 엔진의 동작 방식과 트레이드오프를
이해하고, 상황에 맞는 저장소 엔진을 선택할 수 있다.

# OLTP vs OLAP

**Online Transaction Processing**
- 요청마다 인덱스로 소수 레코드를 찾아 저지연으로 읽고 쓰는 처리
- 예) 입출금 거래, 쿠폰 발급, 블로그 댓글

**Online Analytical Processing**
- 대량 레코드를 스캔해 소수 컬럼을 집계하는 분석용 처리
- 예) 월별 매출, 쿠폰 사용률

초기엔 한 DB에서 거래와 분석을 같이 했지만, 데이터가 커지고 여러 시스템으로
흩어지면서 분석 쿼리가 운영에 부담을 주자 분석 전용 DB를 따로 두게 됨.
이 분석 전용 DB를 데이터 웨어하우스라고 함.

# 디스크 I/O 비용
저장소 엔진마다 구조가 다른 이유는 디스크 I/O 비용을 줄이는 방식이 다르기 때문이다.

**요청 횟수가 비용을 결정한다**
디스크는 바이트 단위로 접근할 수 없고 고정 크기 블록 단위로만 읽고 쓴다.
요청 한 번마다 고정 비용(HDD는 헤드 이동, SSD는 커맨드 처리)이 붙는데,
이 비용이 데이터를 옮기는 비용보다 훨씬 크다.
→ 읽는 양이 아니라 요청 횟수를 줄여야 한다.

**순차 I/O와 랜덤 I/O**
연속된 위치를 읽고 쓰는 것은 빠르지만, 흩어진 위치를 오가는 것은 느리다.

저장소 엔진은 이 비용에 각각 다르게 대응한다.
- 랜덤 쓰기를 순차 쓰기로 바꾼다 → **로그 구조 계열**
- 한 번의 요청으로 최대한 많이 가져온다 → **페이지 지향 계열**
- 읽는 양 자체를 줄인다 → **컬럼 지향 (OLAP)**

# 로그 구조 계열

## 로그
파일 끝에 레코드를 추가(append)만 하는 저장 방식.

**장점**
- 데이터를 덮어쓰지 않고 끝에 순차적으로 쓰기 때문에 쓰기 성능이 좋다.

**단점**
- 키를 찾으려면 수정·삭제된 옛 값까지 포함한 파일 전체를 훑어야 한다.
- 수정·삭제도 새 레코드로 추가되므로, 옛 값이 계속 남아 용량이 커진다.

조회 성능 문제는 색인으로 보완할 수 있다.
다만 색인은 별도 구조를 함께 갱신해야 하므로 쓰기에 오버헤드가 발생한다.

## 해시 색인 (Bitcask)
키를 디스크 오프셋(파일 내 바이트 위치)에 매핑한 인메모리 해시맵.

**동작**
- 쓰기: 로그 끝에 레코드를 추가하고, 해시맵의 오프셋을 갱신
- 읽기: 해시맵에서 오프셋을 찾아 디스크 접근 한 번으로 값을 가져옴

**장점**
- 조회당 디스크 접근이 한 번뿐이라 읽기가 빠르다.
- 쓰기는 순차 추가 + 오프셋 갱신뿐이라 쓰기도 빠르다.

**적합한 상황**
각 키의 값이 자주 갱신되는 경우.
갱신이 잦아도 키 개수는 늘지 않아 메모리 제약을 건드리지 않고, 쓰기 비용도 낮다.
예) 키가 동영상 URL, 값이 재생 수인 경우

**한계**
- 모든 키가 메모리에 들어가야 한다.
- 범위 조회가 불가능하다. 해시는 키를 흩뿌리므로 인접한 키의 위치를 알 수 없다.

## 세그먼트와 컴팩션
파일에 계속 추가만 하면 용량이 부족해진다.
그래서 로그를 일정 크기로 잘라 세그먼트 단위로 관리한다.
특정 크기가 되면 세그먼트 파일을 닫고 새 세그먼트에서 작업하며,
닫힌 세그먼트는 더 이상 수정하지 않는다.

**컴팩션**: 닫힌 세그먼트를 읽어 중복된 키를 버리고 각 키의 최신 값만 남기는 작업.

1. 백그라운드 스레드가 옛 세그먼트를 읽어 새 파일에 결과를 쓴다.
   이 과정에서 읽기 요청은 옛 세그먼트를 본다.
2. 병합이 끝나면 읽기 요청을 새 세그먼트로 전환한다.
3. 옛 세그먼트를 제거한다.

파일을 잘라 닫는 이유는 컴팩션 때문이다.
쓰는 중인 파일은 계속 변해서 "전체"를 정할 수 없고, 정리하는 사이에도 값이
바뀌어 결과가 어긋난다. 닫힌 세그먼트는 변하지 않으므로 안전하게 병합할 수 있고,
그동안 쓰기는 새 세그먼트에서 계속된다.

## SS테이블 (Sorted String Table)
세그먼트를 키로 정렬해 저장한 것. 해시 색인의 두 한계를 해결한다.

- 범위 조회 불가 → 키로 정렬되어 있어 구간을 순차적으로 읽으면 된다.
- 모든 키가 메모리에 있어야 함 → 정렬되어 있어 색인에 키를 드문드문 담아도 된다.
  색인에 없는 키는 앞뒤 키의 오프셋 사이 구간만 스캔하면 찾을 수 있다. (희소 색인)

추가로 세그먼트끼리 정렬되어 있으므로 머지 소트 방식으로 병합할 수 있어
컴팩션도 쉬워진다.

그렇다면 쓰기는 순서 없이 들어오는데 정렬을 어떻게 유지하는가? → LSM 트리

## LSM 트리 (Log-Structured Merge Tree)
멤테이블, SS테이블, 컴팩션을 묶은 구조.

**쓰기**
1. 요청이 오면 메모리의 균형 트리(레드-블랙 트리 등)에 정렬된 상태로 저장.
   이 메모리 구조를 멤테이블(memtable)이라고 한다.
2. 멤테이블이 임계 크기를 넘으면 정렬된 상태 그대로 디스크에 SS테이블로 쓴다.
3. 이후 쓰기는 새 멤테이블에서 받는다.

멤테이블은 메모리에 있어 크래시 시 유실될 수 있으므로,
쓰기 요청이 오면 멤테이블과 함께 디스크의 로그에도 추가한다.
이 로그는 크래시 복구용이며, 멤테이블이 SS테이블로 저장되면 버린다.

**읽기**
멤테이블 → 최신 SS테이블 → 그다음 SS테이블 순으로 찾는다.

**컴팩션**
백그라운드에서 SS테이블들을 병합해 각 키의 최신 값만 남긴다.
전략에 따라 쓰기 부담과 조회 성능·공간 효율 사이의 트레이드오프가 있다.

**디스크 I/O 관점**
- 쓰기: 요청마다 디스크에 쓰지 않고 멤테이블에 모았다가 한 번에 내려쓴다.
  제자리 갱신이 없어 항상 순차 쓰기다.
- 읽기: 여러 SS테이블을 확인해야 해 불리하므로, 디스크 접근 전에 메모리에서 거른다.
    - 블룸 필터: "이 파일에 없다"를 메모리에서 판단해 디스크 접근을 건너뜀
    - 희소 색인: 파일 전체가 아니라 블록 하나만 읽도록 위치를 좁힘
- 대가: 컴팩션이 같은 데이터를 반복해 다시 쓰므로 디스크 대역폭을 소모한다.
  쓰기가 몰리면 일반 요청과 경합해 지연이 튈 수 있다.

**사용하는 DB**
- LevelDB, RocksDB (임베디드 엔진. 다른 DB가 내장해서 쓰기도 함)
- Cassandra, HBase (분산 DB)
- InfluxDB (시계열)

# 페이지 지향 계열
로그 구조가 순차 쓰기를 택했다면, 페이지 지향은 I/O 요청 횟수를 줄이는 쪽을 택했다.

## B 트리
디스크를 고정 크기 페이지로 나누고, 트리의 노드 하나를 페이지 하나에 담는다.
페이지에는 키와 자식 페이지 참조가 함께 들어간다. (InnoDB 16KB, PostgreSQL 8KB)

한 페이지에 키를 수백 개 담을 수 있으므로, 한 번의 I/O로 탐색 범위를
수백 분의 1로 줄인다. 이 자식 참조 개수를 분기 계수라고 한다.

분기 계수가 크면 트리가 얕아진다. 분기 계수 500이면 깊이 4로 키 600억 개.
트리의 깊이가 곧 I/O 횟수이므로, 데이터가 커져도 몇 번이면 조회가 끝난다.

이진 트리(AVL, 레드-블랙)는 자식이 2개뿐이라 같은 데이터에서 깊이가 30까지
깊어진다. 메모리에서는 문제없지만 디스크에서는 I/O가 30번이라 쓸 수 없다.

**조회**
루트에서 키 범위를 따라 자식 페이지를 타고 리프까지 내려간다.

**갱신과 추가**
- 갱신: 리프 페이지를 찾아 제자리에서 덮어쓴다.
- 추가: 들어갈 페이지에 공간이 없으면 페이지를 둘로 나누고(분할)
  부모 페이지에 참조를 추가한다.

**WAL (쓰기 전 로그)**
제자리에 덮어쓰는 도중 크래시가 나면 옛 값과 새 값이 섞여 페이지가 깨진다.
특히 페이지 분할 중에 죽으면 트리 구조 자체가 망가진다.
그래서 페이지를 고치기 전에 변경 내용을 로그에 먼저 기록한다.
LSM의 복구 로그와 역할은 같지만, B 트리는 제자리에 덮어쓰기 때문에 필요하다.

**단점**
- 쓰기가 랜덤 I/O다. 페이지 위치를 찾아가 고쳐야 한다.
- 쓰기 증폭: 한 컬럼만 바꿔도 페이지 전체를 다시 쓰고, WAL에도 쓴다.
- 여러 스레드가 같은 페이지를 건드릴 수 있어 동시성 제어(latch)가 필요하다.
- 페이지 분할이 반복되면 빈 공간이 생겨 단편화된다.

**B 트리가 RDB 색인의 표준이 된 이유**
- 디스크 페이지 구조에 맞아 트리가 얕고, I/O 횟수가 적다.
- 키가 정렬되어 있고 리프끼리 연결되어 범위 조회와 정렬이 순차 읽기로 처리된다.
- 키 하나가 한 곳에만 존재하므로 락을 걸기 쉬워 트랜잭션 구현에 유리하다.
- 조회 성능이 예측 가능하다. 항상 깊이만큼만 I/O가 발생한다.

## 색인 종류
- **클러스터드 인덱스**: 리프 페이지에 행 전체가 들어 있다. (InnoDB의 PK)
- **보조 인덱스**: 리프에 인덱스 컬럼 값과 PK만 있다. 나머지 컬럼이 필요하면
  그 PK로 클러스터드 인덱스를 다시 타야 한다.
- **커버링 인덱스**: 필요한 컬럼이 전부 보조 인덱스에 있어 다시 탈 필요가 없다.
