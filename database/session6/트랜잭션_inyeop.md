read committed

더티쓰기 방지법
로우 수준 잠금을 사용해 더티 쓰기를 방지한다. 트랜잭션에서 특정 객테를 변경하고 싶다면 해당 객체에 대한 잠금을 획득하고 트랜잭션이 커밋되거나 롤백될때까지 잠금을 보유한다.


더티읽기 방지법
쓰기와 마찬가지로 동일한 잠금을 사용해 읽기를 원하는 트랜잭션은 잠금을 획득하고 읽기가 끝나면 해제
잠금 대기 떄문에 어플리케이션에서 지연이 발생할수있다.

![[Pasted image 20261112234401.png]]
이 처럼 쓰여진 모든 객체에 대해 db는 과거에 커밋된 값과 현재 쓰기 잠금을 갖고 있는 트랜잭션에서 쓴 새로운 값을 모두 기억한다. (스냅샷을 쿼리마다.)


read committed은 더티읽기와 더티쓰기를 방지해주지만 완벽하게 동시성을 제어해주진 않음.
읽는 도중에 다른 트랜잭션이 커밋해서, **서로 다른 시점의 데이터를 섞어 읽는** 읽기 스큐 , 비반복 읽기가 발생할수있다.

![[Pasted image 20261113000017.png]]
앨리스는 계좌 두 개에 500원씩, 총 1000원.  
그 사이 계좌2 → 계좌1로 100원 이체가 일어남.

1. 앨리스: 계좌1 조회 → **500** (이체 전)
2. 이체 트랜잭션: 계좌1 +100 = 600, 계좌2 −100 = 400, 커밋
3. 앨리스: 계좌2 조회 → **400** (이체 후)
   앨리스가 본 합계: 500 + 400 = **900원**. 100원이 사라진 것처럼 보임.
   **둘 다 커밋된 값**이라 read committed로는 못 막는다

원자적 쓰기 연산
쿼리를 원자적으로 작성해 다른 트랜잭션이 끼어들 틈을 안주는것.
`update counters set value = value+1 where key = 'foo'`

명시적 잠금
객체를 잠그는것.
```
begin transaction;

select * from figures
where name = 'robot' and game_id = 222
for update; // 잠금획득

update figures set posistion = 'c4' where id = 1234;

commit; // 잠금 반환
```

잠금을 할때 신중해야함. 경쟁이 발생할수있음


갱신 손실 자동 감지
트랜잭션들을 그냥 병렬로 돌리다가, DB가 "갱신 손실 생겼다"고 감지하면 한쪽을 중단시키고 재시도하게 하는 방식.

- PostgreSQL repeatable read, Oracle serializable, SQL Server 스냅샷 격리 → **자동 감지함**
- **MySQL InnoDB repeatable read → 감지 안 함**

MySQL에선 DB가 알아서 안 막아주니까, 동시에 같은 값을 읽고 고치는 로직(재고 차감, 쿠폰 수량, 포인트)은 직접 막아야 함

쓰기스큐와 팬텀




![[Pasted image 20261113002443.png]]규칙: 당직 의사는 최소 1명 있어야 함. 지금 앨리스·밥 2명 당직 중.  
둘 다 아파서 동시에 당직 빼달라고 요청.

1. 앨리스: "당직 몇 명?" → 2명 → 빠져도 되겠네
2. 밥: "당직 몇 명?" → 2명 → 빠져도 되겠네
3. 앨리스: 내 행 `on_call = false`, 커밋
4. 밥: 내 행 `on_call = false`, 커밋

결과: **당직 0명.** 규칙 깨짐.

**왜 갱신 손실이랑 다르냐**  
갱신 손실은 **같은 행**을 둘이 고친 것. 쓰기 스큐는 **각자 다른 행**을 고쳤음. 그래서 행 잠금 충돌도 없고, 스냅샷 격리로도 못 막음. 둘 다 "스냅샷 기준으론 2명"이라 판단이 맞았거든.

해결
1번에서 읽은 행에 잠금: `SELECT ... WHERE on_call = true FOR UPDATE` → 밥은 앨리스 끝날 때까지 대기

위 해결책 `FOR UPDATE`가 **안 통하는 경우**가 팬텀이야.

**예시 (회의실 예약)**

1. “12~13시에 이 방 예약 있어?” → **0건**
2. 없으니까 예약 INSERT

두 명이 동시에 하면 둘 다 0건 보고 둘 다 INSERT → 중복 예약.

당직 의사는 **있는 행**을 확인했으니 잠글 수 있었는데, 여긴 **"없음"을 확인**한 거라 잠글 행 자체가 없음.

**팬텀 정의**: 한 트랜잭션의 쓰기가 다른 트랜잭션의 검색 결과를 바꾸는 것. 1번에서 0건이던 게, 남이 INSERT하면 1건이 되는 것처럼 "유령 행"이 튀어나옴.

**해결**
- **serializable**: 제대로 된 해결

MySQL InnoDB는 `FOR UPDATE` 같은 잠금 읽기에서 **넥스트 키 락(갭 락)**을 걸어서, “12~13시 범위”처럼 빈 구간까지 잠가. 그래서 MySQL에선 인덱스만 잘 잡혀 있으면 `FOR UPDATE`로 팬텀도 어느 정도 막을 수 있음.

serializable

트랜잭션을 병렬로 돌려도 **하나씩 순서대로 돌린 것과 같은 결과**를 보장

3가지 방법이 있음.

1. 실제 직렬 실행
   **진짜로 한 번에 하나씩**, 단일 스레드로 실행.
   예전엔 느려서 안 썼는데 가능해진 이유:
- 램이 싸져서 데이터를 전부 메모리에 올릴 수 있음 → 디스크 대기 없음

앱이랑 여러 번 주고받는 대화형 트랜잭션 불가 → **스토어드 프로시저**로 한 번에 보내야 함
Redis(Redis에서 스토어드 프로시저 역할을 하는 게 Lua 스크립트야.)


2. 2단계 잠금 (2PL)
   30년 동안 사실상 유일한 방법이었던 전통 방식.
   **규칙**: 읽기도 잠금, 쓰기도 잠금

- 읽기 → 공유 잠금 (여러 명 동시 읽기 OK)
- 쓰기 → 독점 잠금 (아무도 못 읽고 못 씀)
- 잠금은 **트랜잭션 끝날 때까지** 안 풀음

2단계인 이유: 잠금을 획득하는 단계 → 끝날 때 한 번에 해제하는 단계

**스냅샷 격리랑 차이**

- 스냅샷 격리: 읽기는 쓰기를 안 막고, 쓰기는 읽기를 안 막음
- 2PL: **읽기와 쓰기가 서로 막음**

**팬텀 대응**: 조건에 맞는 "범위" 자체를 잠금 (서술 잠금 → 실제론 인덱스 범위 잠금으로 근사)

**단점**

- 대기가 많아서 성능이 나쁘고 응답 시간이 들쭉날쭉
- 교착 상태 자주 발생 → DB가 감지해서 하나 중단


3. 직렬성 스냅샷 격리 (SSI)
   최신 방식. **일단 스냅샷 격리로 막 돌리고, 커밋할 때 문제 있으면 중단**하는 낙관적 방식.
   쓰기 스큐의 본질이 “**읽은 전제가 커밋 시점엔 이미 바뀌어 있음**”이잖아. 그걸 감지함:

- 내가 읽을 때 아직 커밋 안 됐던 쓰기가, 내 커밋 전에 커밋됐나?
- 내가 읽은 데이터를 다른 트랜잭션이 바꿨나?

→ 그러면 전제가 깨졌으니 중단, 재시도.

당직 의사 예시에 대입하면: 앨리스가 먼저 커밋 → 밥이 커밋하려는 순간 "네가 읽은 당직 2명이 이미 바뀌었음" → 밥 중단.

**장점**: 잠금 대기 없음. 읽기 전용 쿼리는 아예 안 막힘  
**단점**: 충돌 잦으면 중단·재시도 폭증

PostgreSQL의 serializable이 이 방식.
