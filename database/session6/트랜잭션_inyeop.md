# 트랜잭션

## 1. 트랜잭션이란

데이터 시스템에선 여러 가지 문제가 생길 수 있다.
- 소프트웨어나 하드웨어에 문제가 생길 수 있다.
- 네트워크가 끊길 수 있다.
- 여러 클라이언트가 동시에 쓰기를 실행해서 다른 클라이언트가 쓴 내용을 덮어쓸 수 있다.
- 일부만 갱신된 상태의 데이터를 다른 클라이언트가 읽을 수 있다.

이런 결함이 애플리케이션 전체의 치명적인 장애로 이어지는 걸 막기 위한 장치가 트랜잭션이다.

**여러 읽기·쓰기를 하나의 논리적 단위로 묶은 것.**
전체가 성공하면 **커밋**, 하나라도 실패하면 **롤백**하는 간단한 메커니즘으로 동작한다.

그럼 트랜잭션은 구체적으로 뭘 보장해줄까? 앞의 문제들에 대응해서 4가지를 보장하고, 이걸 ACID라고 한다.

---

## 2. ACID — 트랜잭션이 보장하는 것

**A — 원자성 (Atomicity)**
중간에 실패하면 전부 취소.
→ 소프트웨어·하드웨어 문제, 네트워크 단절로 작업이 중간에 끊겨도 반쯤 반영된 상태가 남지 않는다.

**C — 일관성 (Consistency)**
"계좌 잔액 합은 항상 같아야 한다" 같은 규칙이 지켜지는 것.
→ 결국 트랜잭션으로 지키고 싶은 목표.

**I — 격리성 (Isolation)**
동시에 실행되는 트랜잭션끼리 서로 간섭하지 않는 것.
→ 동시에 쓰다가 덮어쓰거나, 일부만 갱신된 데이터를 읽는 문제를 막는다.

**D — 지속성 (Durability)**
커밋된 건 장애가 나도 사라지지 않음.
→ 장애가 나도 커밋한 데이터가 날아가지 않는다.

이 중 격리성(I)은 완벽하게 지키면 성능이 크게 떨어져서, 실제 DB는 격리 수준을 단계별로 나눠 제공한다. 이게 격리 레벨이다.

---

## 3. 트랜잭션 격리 레벨

**완벽한 격리 = 트랜잭션을 하나씩 순서대로 실행한 것과 같은 결과.**
그런데 이걸 보장하려면 동시에 실행되는 트랜잭션끼리 잠금으로 서로 기다리게 하거나, 충돌이 나면 중단시키고 재시도해야 한다. 그만큼 동시 처리량이 떨어진다.

그래서 DB는 **"이 정도 이상 현상은 허용할 테니 대신 빠르게"**라는 선택지를 단계별로 준다.
- 약한 레벨: 동시성 높음, 대신 일부 이상 현상(읽기 스큐, 갱신 손실 등)이 생길 수 있음
- 강한 레벨: 이상 현상을 더 많이 막음, 대신 대기·중단이 늘어남

격리 레벨은 **어떤 이상 현상까지 막아주느냐**로 구분되고, 아래로 갈수록 강하다.

```
Read Committed → 스냅샷 격리 (Repeatable Read) → Serializable
```

> SQL 표준엔 Read Committed보다 약한 Read Uncommitted도 있지만 더티 읽기까지 허용해서 거의 안 쓴다.

**기본값은 DB마다 다르다.**
- MySQL InnoDB: Repeatable Read
- PostgreSQL, Oracle: Read Committed

**이름도 DB마다 의미가 다르다.**
같은 Repeatable Read라도 PostgreSQL은 갱신 손실을 자동 감지하고 MySQL은 감지 안 한다. Oracle의 Serializable은 실제론 스냅샷 격리다. 그래서 레벨 이름만 보지 말고 **우리 DB가 실제로 뭘 막아주는지** 확인해야 한다.

### 3.1 Read Committed

가장 보편적인 단계. 2가지를 보장한다.
- 읽을 때 **커밋된 데이터만** 보게 된다. → 더티 읽기 방지
- 쓸 때 **커밋된 데이터만** 덮어쓰게 된다. → 더티 쓰기 방지

#### 더티 읽기
다른 트랜잭션에서 **커밋되지 않은 데이터를 보는 것**.

![더티읽기](../../images/session6/Pasted%20image%2020261112234401.png)

방지해야 하는 이유
- 트랜잭션이 여러 객체를 갱신하는 중에 더티 읽기가 생기면, 다른 트랜잭션은 일부는 갱신된 값, 일부는 갱신 안 된 값을 보게 된다.

#### 더티 쓰기
**커밋 안 된 값을 덮어쓰는 것**.

![더티쓰기](../../images/session6/Pasted%20image%2020261112234557.png)

문제는 아직 커밋 중인, 작업 중인 행에 다른 트랜잭션이 접근하기 때문.

#### 구현 방법

**더티 쓰기 방지 → 로우 수준 잠금**
객체를 변경하려면 해당 객체의 잠금을 획득하고, 커밋 또는 롤백될 때까지 보유한다.

**더티 읽기 방지 → 옛 값 기억**
- 읽기에도 같은 잠금을 거는 방법이 있지만, 쓰기 하나가 길어지면 읽기들이 전부 대기 → 응답 지연이 커서 실제로는 잘 안 씀.
- 대신 DB는 쓰여진 객체마다 **과거에 커밋된 값**과 **쓰기 잠금을 가진 트랜잭션이 쓴 새 값**을 모두 기억한다. 다른 트랜잭션이 읽으면 커밋된 옛 값을 돌려준다.

![더티읽기_방지](../../images/session6/Pasted%20image%2020261112234401.png)

> Read committed는 이 스냅샷을 **쿼리마다** 새로 잡는다.

#### 한계 — 읽기 스큐 (비반복 읽기)

더티 읽기·쓰기는 막아주지만 완벽한 동시성 제어는 아니다.
읽는 도중에 다른 트랜잭션이 커밋하면 **서로 다른 시점의 데이터를 섞어 읽게** 된다.

![읽기스큐](../../images/session6/Pasted%20image%2020261113000017.png)

앨리스는 계좌 두 개에 500원씩, 총 1000원. 그 사이 계좌2 → 계좌1로 100원 이체가 일어남.

1. 앨리스: 계좌1 조회 → **500** (이체 전)
2. 이체 트랜잭션: 계좌1 +100 = 600, 계좌2 −100 = 400, 커밋
3. 앨리스: 계좌2 조회 → **400** (이체 후)

앨리스가 본 합계: 500 + 400 = **900원**. 100원이 사라진 것처럼 보임.
**둘 다 커밋된 값**이라 read committed로는 못 막는다.

### 3.2 스냅샷 격리 (Repeatable Read)

트랜잭션이 **시작한 시점의 스냅샷**을 끝날 때까지 계속 본다. → 읽기 스큐 해결
(read committed는 쿼리마다, 스냅샷 격리는 트랜잭션마다 스냅샷)

- 읽는 쪽이 쓰는 쪽을 차단하지 않고, 쓰는 쪽이 읽는 쪽을 차단하지 않는다.
- DB는 객체마다 커밋된 버전 여러 개를 유지한다.
- 이를 **다중 버전 동시성 제어(MVCC)**라고 한다.

#### PostgreSQL의 MVCC 구현

![MVCC](../../images/session6/Pasted%20image%2020261113000725.png)

**1. txid**
트랜잭션이 시작되면 계속 증가하는 ID(txid)를 받는다.

**2. 행마다 두 필드**
- `created_by`: 이 행을 만든 txid
- `deleted_by`: 이 행을 지운 txid

**3. 가시성 규칙** — 읽을 때 이 행을 볼지 말지 판단
트랜잭션이 시작할 때 "지금 진행 중인 트랜잭션 목록"을 기억해두고, 다음 쓰기는 **없던 걸로** 친다.
- 내가 시작할 때 진행 중이던 트랜잭션이 쓴 것 (나중에 커밋해도 무시)
- 롤백된 트랜잭션이 쓴 것
- 나보다 txid가 큰(나중에 시작한) 트랜잭션이 쓴 것

앨리스(12)가 계좌2를 읽을 때:
- 500짜리 행: 3이 만들었으니 보임. 13이 지웠지만 13은 앨리스보다 늦게 시작 → **삭제 무시** → 보임
- 400짜리 행: 13이 만들었으니 → **무시**

스냅샷 격리의 장점

1. 트랜잭션 내내 일관된 데이터를 봄
여러 행을 읽는 동안 중간에 누가 커밋해도 한 시점 기준으로만 본다.
2. 읽기와 쓰기가 서로 안 막음
읽기는 옛 버전을 보고 쓰기는 새 버전을 만드니까 서로 기다릴 필요가 없다.

---

#### 스냅샷 격리로도 남는 문제 ① — 갱신 손실 (Lost Update)

read-modify-write 주기에서 발생. 두 트랜잭션이 같은 값을 읽고 각자 수정해서 쓰면, 나중 쓰기가 먼저 쓰기를 덮어버린다.

![갱신손실](../../images/session6/Pasted%20image%2020261113001510.png)

**해결책**

**원자적 쓰기 연산**
쿼리를 원자적으로 작성해서 다른 트랜잭션이 끼어들 틈을 안 주는 것.
```sql
UPDATE counters SET value = value + 1 WHERE key = 'foo';
```

**명시적 잠금**
읽을 때부터 객체를 잠그는 것.
```sql
BEGIN TRANSACTION;

SELECT * FROM figures
WHERE name = 'robot' AND game_id = 222
FOR UPDATE;  -- 잠금 획득

UPDATE figures SET position = 'c4' WHERE id = 1234;

COMMIT;  -- 잠금 반환
```
잠금은 신중하게. 잠그는 걸 빠뜨리면 그대로 경쟁 조건이 생긴다.

**갱신 손실 자동 감지**
트랜잭션들을 그냥 병렬로 돌리다가, DB가 갱신 손실을 감지하면 한쪽을 중단시키고 재시도하게 하는 방식.
- PostgreSQL repeatable read, Oracle serializable, SQL Server 스냅샷 격리 → **자동 감지함**
- **MySQL InnoDB repeatable read → 감지 안 함**

> MySQL에선 DB가 알아서 안 막아주니까, 동시에 같은 값을 읽고 고치는 로직(재고 차감, 쿠폰 수량, 포인트)은 원자적 연산이나 `FOR UPDATE`로 직접 막아야 한다.

**Compare-and-set**
내가 읽었던 값이 그대로일 때만 쓰는 방식.
```sql
UPDATE wiki_pages SET content = '새 내용'
WHERE id = 1234 AND content = '예전 내용';
```
영향받은 행이 0이면 누가 먼저 바꾼 것 → 재시도.

#### 스냅샷 격리로도 남는 문제 ② — 쓰기 스큐

![쓰기스큐](../../images/session6/Pasted%20image%2020261113002443.png)

규칙: 당직 의사는 최소 1명 있어야 함. 지금 앨리스·밥 2명 당직 중.
둘 다 아파서 동시에 당직 빼달라고 요청.

1. 앨리스: "당직 몇 명?" → 2명 → 빠져도 되겠네
2. 밥: "당직 몇 명?" → 2명 → 빠져도 되겠네
3. 앨리스: 내 행 `on_call = false`, 커밋
4. 밥: 내 행 `on_call = false`, 커밋

결과: **당직 0명.** 규칙 깨짐.

**갱신 손실이랑 다른 점**
갱신 손실은 **같은 행**을 둘이 고친 것. 쓰기 스큐는 **각자 다른 행**을 고쳤다.
그래서 행 잠금 충돌도 없고, 스냅샷 격리로도 못 막는다. 둘 다 "스냅샷 기준으론 2명"이라 판단이 맞았으니까.

**해결**
1번에서 읽은 행에 잠금을 건다.
```sql
SELECT * FROM doctors WHERE on_call = true FOR UPDATE;
```
→ 밥은 앨리스가 끝날 때까지 대기.

---

#### 스냅샷 격리로도 남는 문제 ③ — 팬텀

위 해결책(`FOR UPDATE`)이 **안 통하는 경우**가 팬텀이다.

**예시 (회의실 예약)**
1. "12~13시에 이 방 예약 있어?" → **0건**
2. 없으니까 예약 INSERT

두 명이 동시에 하면 둘 다 0건 보고 둘 다 INSERT → 중복 예약.

당직 의사는 **있는 행**을 확인했으니 잠글 수 있었는데, 여긴 **"없음"을 확인**한 거라 잠글 행 자체가 없다.

**팬텀 정의**: 한 트랜잭션의 쓰기가 다른 트랜잭션의 검색 결과를 바꾸는 것. 1번에서 0건이던 게, 남이 INSERT하면 1건이 되는 것처럼 "유령 행"이 튀어나온다.

**해결**
- 제대로 된 해결은 **serializable**.
- MySQL InnoDB는 `FOR UPDATE` 같은 잠금 읽기에서 **넥스트 키 락(갭 락)**을 걸어서 "12~13시 범위"처럼 빈 구간까지 잠근다. 그래서 MySQL에선 인덱스만 잘 잡혀 있으면 `FOR UPDATE`로 팬텀도 어느 정도 막을 수 있다.

---

### 3.3 Serializable

트랜잭션을 병렬로 돌려도 **하나씩 순서대로 돌린 것과 같은 결과**를 보장한다. 위의 모든 문제를 막는 가장 강한 격리 레벨.

구현 방법은 3가지.

#### ① 실제 직렬 실행
**진짜로 한 번에 하나씩**, 단일 스레드로 실행.

예전엔 느려서 안 썼는데 가능해진 이유:
- 램이 싸져서 데이터를 전부 메모리에 올릴 수 있음 → 디스크 대기 없음
- OLTP 트랜잭션은 대부분 짧고 작음

제약:
- 앱이랑 여러 번 주고받는 대화형 트랜잭션 불가 → **스토어드 프로시저**로 한 번에 보내야 함
- 처리량이 CPU 코어 하나에 묶임

예: Redis (스토어드 프로시저 역할을 하는 게 Lua 스크립트)

#### ② 2단계 잠금 (2PL)
30년 동안 사실상 유일한 방법이었던 전통 방식.

**규칙**: 읽기도 잠금, 쓰기도 잠금
- 읽기 → 공유 잠금 (여러 명 동시 읽기 OK)
- 쓰기 → 독점 잠금 (아무도 못 읽고 못 씀)
- 잠금은 **트랜잭션 끝날 때까지** 안 풀음

2단계인 이유: 잠금을 획득하는 단계 → 끝날 때 한 번에 해제하는 단계

**스냅샷 격리와 차이**
- 스냅샷 격리: 읽기는 쓰기를 안 막고, 쓰기는 읽기를 안 막음
- 2PL: **읽기와 쓰기가 서로 막음**

**팬텀 대응**: 조건에 맞는 "범위" 자체를 잠금 (서술 잠금 → 실제론 인덱스 범위 잠금으로 근사)

**단점**
- 대기가 많아서 성능이 나쁘고 응답 시간이 들쭉날쭉
- 교착 상태 자주 발생 → DB가 감지해서 하나 중단

#### ③ 직렬성 스냅샷 격리 (SSI)
최신 방식. **일단 스냅샷 격리로 막 돌리고, 커밋할 때 문제 있으면 중단**하는 낙관적 방식.

쓰기 스큐의 본질은 "**읽은 전제가 커밋 시점엔 이미 바뀌어 있음**"이다. 그걸 감지한다.
- 내가 읽을 때 아직 커밋 안 됐던 쓰기가, 내 커밋 전에 커밋됐나?
- 내가 읽은 데이터를 다른 트랜잭션이 바꿨나?

→ 그러면 전제가 깨졌으니 중단, 재시도.

당직 의사 예시에 대입하면: 앨리스가 먼저 커밋 → 밥이 커밋하려는 순간 "네가 읽은 당직 2명이 이미 바뀌었음" → 밥 중단.

- **장점**: 잠금 대기 없음. 읽기 전용 쿼리는 아예 안 막힘
- **단점**: 충돌이 잦으면 중단·재시도 폭증

PostgreSQL의 serializable이 이 방식.
