# 5장. 복제 (Replication)

## 1. 복제의 목적

복제는 네트워크로 연결된 여러 장비에 동일한 데이터 사본을 유지하는 것이다. 책은 목적을 세 가지로 정리한다.

| 목적 | 내용 |
|---|---|
| 가용성 | 일부 노드에 장애가 나도 서비스가 계속 동작함 |
| 읽기 처리량 | 읽기 요청을 여러 노드로 분산함 |
| 지연 시간 | 사용자와 지리적으로 가까운 곳에 데이터를 둠 |

데이터가 변하지 않는다면 한 번 복사하면 끝난다. 복제의 어려움은 **변경을 여러 노드에 어떻게 전파하는가**에 있으며, 이는 두 축으로 구분된다.

- 누가 쓰기를 받는가 → 단일 리더 / 다중 리더 / 리더 없음
- 언제 쓰기 성공으로 응답하는가 → 동기식 / 비동기식

---

## 2. 동기식 vs 비동기식 복제

- **동기식**: 팔로워 반영까지 확인한 뒤 클라이언트에 성공을 응답함
- **비동기식**: 리더에 기록하면 즉시 응답하고, 팔로워에는 이후에 전파함

| 구분 | 동기식 | 비동기식 |
|---|---|---|
| 장점 | 팔로워가 항상 최신 상태, 리더 장애 시 유실 없음 | 쓰기가 빠름, 팔로워 장애와 무관하게 쓰기 가능 |
| 단점 | 팔로워 하나가 느리거나 죽으면 전체 쓰기가 멈춤 | 리더 장애 시 미전파된 쓰기가 유실됨 |

### 완전 동기식이 쓰이지 않는 이유

노드 수가 늘수록 그중 하나가 느리거나 장애 상태일 확률이 높아진다. 가용성을 위해 복제했으나 복제 때문에 가용성이 떨어지는 결과가 된다.

### 실무의 절충안

| 방식 | 내용 | 예시 |
|---|---|---|
| 반동기식 | 팔로워 하나만 동기식, 나머지는 비동기식. 최소 2개 노드에 최신 데이터 보장 | MySQL semi-sync, PostgreSQL `synchronous_standby_names = 'ANY 1 (...)'` |
| 과반수 동기식 | N개 중 과반이 확인하면 성공 | Raft/Paxos 기반 시스템 (etcd, CockroachDB, Spanner) |
| 완전 비동기식 | 여전히 가장 흔함. 리전 간 복제는 대부분 이 방식 | 리전 간 DR(Disaster Recovery, 재해 복구) 복제 |

## 3. 단일 리더 복제

쓰기는 리더 한 곳에서만 받고, 리더가 변경 로그를 팔로워에 전달한다. 읽기는 리더와 팔로워 모두에서 가능하다. MySQL, PostgreSQL, Oracle, MongoDB, Kafka 등 대부분의 시스템이 기본으로 채택한다.

**지배적인 이유**: 쓰기 지점이 하나이므로 쓰기 충돌이 원천적으로 발생하지 않음

### 3.1 장애 복구 (Failover)

> [!NOTE]
> **장애 복구(Failover)**: 리더 장애 시 팔로워 하나를 새 리더로 승격하고, 클라이언트와 나머지 팔로워가 새 리더를 따르도록 재설정하는 과정

| 문제 | 내용 |
|---|---|
| 쓰기 유실 | 비동기식이면 새 리더가 옛 리더의 마지막 쓰기를 받지 못했을 수 있음. 옛 리더 복귀 시 해당 쓰기는 보통 폐기됨 |
| 스플릿 브레인 | 두 노드가 동시에 자신을 리더로 인식하고 쓰기를 받음 |
| 타임아웃 설정 | 짧으면 불필요한 장애 복구, 길면 복구 지연 |

책은 GitHub 사례를 소개한다. 뒤처진 팔로워가 리더로 승격되며 auto-increment 키가 재사용되었고, 같은 키를 쓰던 Redis와 불일치가 발생해 일부 사용자 데이터가 다른 사용자에게 노출되었다. 이런 위험 때문에 수동 장애 복구를 선호하는 운영 조직도 있다.

> [!NOTE]
> **스플릿 브레인(Split Brain)**: 두 노드가 모두 자신이 리더라고 판단하는 상황. 양쪽에서 쓰기를 받아 데이터 충돌·유실이 발생함

### 3.2 복제 로그 구현 방식

| 방식 | 내용 | 현황 |
|---|---|---|
| 구문 기반 | SQL 문을 그대로 전달 | **거의 사용하지 않음.** `NOW()`, `RAND()`, auto-increment, 트리거 등 비결정적 요소로 노드마다 결과가 달라짐. MySQL은 5.7부터 행 기반이 기본값 |
| WAL 전달 | 디스크 블록 수준의 변경을 전달 | PostgreSQL 물리 복제. 저장 엔진 형식에 종속되어 리더·팔로워 버전이 달라지면 안 되므로 무중단 업그레이드가 어려움 |
| 논리(행 기반) 로그 | 행 단위 변경을 저장 엔진과 분리된 형식으로 전달 | MySQL binlog(row), PostgreSQL logical replication. 버전 독립적이며 CDC의 기반이 됨 |
| 트리거 기반 | 애플리케이션 계층에서 트리거로 복제 | 유연하나 오버헤드와 버그 위험이 커 특수한 경우에만 사용 |

> [!NOTE]
> **WAL(Write-Ahead Log, 쓰기 전 로그)**: 데이터 변경을 실제 저장 구조에 반영하기 전에 먼저 기록하는 추가 전용 로그
>
> **CDC(Change Data Capture, 변경 데이터 캡처)**: 데이터베이스의 변경 사항을 로그에서 읽어 외부 시스템으로 전파하는 기법

### 3.3 복제 지연 문제

비동기식 팔로워는 결국 리더를 따라잡지만(최종적 일관성), 그 사이 사용자는 비정상적인 결과를 볼 수 있다.

| 보장 | 위반 시 증상 | 해결 방법 |
|---|---|---|
| 자신이 쓴 내용 읽기 | 글 작성 후 새로고침하면 글이 없음 | 본인이 수정 가능한 데이터는 리더에서 읽기, 쓰기 직후 일정 시간 리더로 라우팅 |
| 단조 읽기 | 새로고침마다 다른 팔로워에 접속해 데이터가 사라졌다 나타남 | 사용자별로 동일한 복제본에서 읽기 |
| 일관된 순서로 읽기 | 질문보다 답변이 먼저 보임 | 인과 관계가 있는 쓰기를 같은 파티션에 기록 |

> [!NOTE]
> **최종적 일관성(Eventual Consistency)**: 쓰기를 멈추고 충분히 기다리면 모든 복제본이 결국 같은 값으로 수렴한다는 약한 보장

## 4. 다중 리더 복제

여러 노드가 쓰기를 받고, 리더끼리 변경 사항을 서로 전파한다.

### 등장 배경

- **다중 데이터센터**: 데이터센터마다 리더를 두어 쓰기를 로컬에서 처리하고, 데이터센터 간 단절에도 독립적으로 동작함
- **오프라인 클라이언트**: 캘린더 앱처럼 기기 자체가 리더 역할을 하며 온라인 복귀 시 동기화함
- **협업 편집**: 여러 사용자가 동시에 같은 문서를 편집함

### 핵심 문제: 쓰기 충돌

동일 데이터를 두 리더에서 동시에 수정하면, 양쪽 모두 성공 응답이 나간 이후에 충돌이 발견된다.

| 해결 방법 | 내용 | 한계 |
|---|---|---|
| 충돌 회피 | 특정 레코드는 항상 같은 리더로만 쓰기 | 가장 실용적이나 리더 변경 시 깨짐 |
| LWW | 타임스탬프가 가장 큰 쓰기를 채택 | 데이터가 조용히 유실됨 |
| 병합 | 값을 합침 (예: 장바구니 합집합) | 도메인별 로직이 필요함 |
| CRDT | 자동 병합되도록 설계된 자료구조 사용 | 지원 자료구조가 제한적 |

> [!NOTE]
> **LWW(Last Write Wins)**: 동시 쓰기 중 타임스탬프가 가장 늦은 값만 남기는 충돌 해소 방식
>
> **CRDT(Conflict-free Replicated Data Type)**: 복제본들이 독립적으로 수정되어도 충돌 없이 자동 병합되도록 설계된 자료구조

### 잘 쓰이지 않는 이유

- 단일 데이터센터 내에서는 이점에 비해 충돌 처리 복잡도가 과도함
- auto-increment 키, 트리거, 무결성 제약조건과 호환성이 떨어짐. 책도 가능하면 피해야 할 영역으로 평가함
- 글로벌 강한 일관성이 필요한 영역은 합의 기반 분산 DB(Spanner, CockroachDB)로 대체됨
- 반면 오프라인·협업 영역에서는 CRDT, 로컬 우선(local-first) 소프트웨어 형태로 활용이 늘고 있음

## 5. 리더 없는 복제

리더 없이 클라이언트(또는 코디네이터 노드)가 여러 노드에 직접 쓰고 읽는다. 아마존 내부 Dynamo 논문을 계기로 확산되었으며 Cassandra, Riak, Voldemort가 이 방식을 따른다.

> [!NOTE]
> Dynamo 논문과 AWS DynamoDB 서비스는 다르다. DynamoDB는 내부적으로 파티션마다 리더를 둔다.

### 등장 배경

- 장애 복구 개념이 없음. 노드가 죽어도 나머지 노드로 읽기·쓰기를 계속함
- 느린 노드 하나가 전체를 막지 않아 쓰기 가용성과 꼬리 지연 시간에 강함

### 핵심 메커니즘

| 개념 | 내용 |
|---|---|
| 정족수 | n개 복제본 중 w개 쓰기 성공, r개 읽기 응답. **w + r > n**이면 읽은 노드 중 최소 하나는 최신값을 보유함 |
| 읽기 복구 | 읽기 중 오래된 값을 발견하면 해당 노드에 최신값을 기록함 |
| 안티 엔트로피 | 백그라운드 프로세스가 복제본 간 차이를 지속적으로 맞춤 |
| 느슨한 정족수 + 힌트 핸드오프 | 담당 노드 장애 시 임시 노드에 기록 후 복구 시 이관함. 가용성은 높아지나 w + r > n 보장이 깨짐 |
| 버전 벡터 | 동시 쓰기 여부를 판별해 덮어쓰기 또는 병합을 결정함 |

> [!NOTE]
> **정족수(Quorum)**: 연산이 유효하다고 인정받기 위해 필요한 최소 노드 수

### 한계와 현황

- w + r > n이어도 선형성은 보장되지 않음. 동시 쓰기, 부분 실패 등 경계 사례가 많음
- 동시 쓰기를 LWW로 처리하면 데이터가 유실됨 (Cassandra 기본 동작)
- Cassandra, ScyllaDB는 대량 쓰기·시계열 데이터 영역에서 여전히 사용됨
- Riak은 개발사 Basho가 2017년 파산하며 사실상 쇠퇴함
- 최종적 일관성을 애플리케이션이 감당하는 비용이 크다는 인식이 확산되어, 강한 일관성을 제공하는 합의 기반 시스템이 다시 늘어나는 추세

## 6. 방식 선택 시 고려 사항

| 질문 | 판단 기준 |
|---|---|
| 쓰기 충돌을 감당할 수 있는가 | 불가능하면 단일 리더 |
| 리더 장애 시 허용 가능한 유실 범위(RPO)는 | 0이어야 하면 동기식·반동기식·과반수 동기식 |
| 허용 가능한 복구 시간(RTO)은 | 자동 장애 복구 여부, 스플릿 브레인 방지(펜싱) |
| 읽기·쓰기 비율은 | 읽기 위주면 단일 리더 + 읽기 복제본으로 충분 |
| 복제 지연이 드러나면 안 되는 화면은 | 해당 경로만 리더에서 읽기 |
| 다중 리전이 필요한가 | 리전 간은 보통 비동기식, 강한 일관성이 필요하면 합의 기반 DB |

> [!NOTE]
> **RPO(Recovery Point Objective)**: 장애 시 허용 가능한 데이터 유실 시점의 범위
>
> **RTO(Recovery Time Objective)**: 장애 발생부터 서비스 복구까지 허용 가능한 시간

## 7. 실무 복제 사례

### 7.1 이중화 (고가용성)

- Primary–Standby 구성. AWS RDS Multi-AZ가 대표적이며, 다른 가용 영역에 동기식으로 복제하고 장애 시 DNS를 전환함
- 기존 RDS Multi-AZ 인스턴스의 standby는 읽기 트래픽을 받지 않는 순수 고가용성 용도임
- 고려 사항: 장애 복구 중 커넥션 재연결(커넥션 풀, DNS TTL), 스플릿 브레인, 허용 유실 범위

### 7.2 읽기·쓰기 분리 (Read Replica)

- 대부분의 서비스가 읽기 위주이므로 가장 흔한 패턴임
- Spring에서는 `AbstractRoutingDataSource`와 `@Transactional(readOnly = true)`로 라우팅하고, `LazyConnectionDataSourceProxy`로 트랜잭션 속성 확인 후 커넥션을 획득함
- 고려 사항: 복제 지연. 회원가입 직후 프로필 조회처럼 쓰기 직후 읽는 경로는 리더로 보내야 함. 지연 지표(MySQL `Seconds_Behind_Source`, RDS `ReplicaLag`)를 모니터링함

### 7.3 기타 사례

| 사례 | 목적 | 고려 사항 |
|---|---|---|
| 재해 복구 | 리전 전체 장애 대비 | 리전 간 비동기식 복제로 인한 유실 범위 합의, 정기 전환 훈련 |
| 글로벌 서비스 | 사용자 인접 리전에서 읽기 | Aurora Global Database 등. 쓰기는 보통 단일 리전 |
| 분석·배치용 복제본 | 무거운 쿼리를 운영 DB에서 격리 | 장시간 쿼리가 복제 적용을 막아 지연이 커질 수 있음 |
| CDC 기반 파생 시스템 | 검색 엔진, 캐시, 데이터 웨어하우스로 변경 전파 | binlog·WAL을 Debezium 등으로 읽어 Kafka로 전달함 (11장과 연결) |
| 무중단 마이그레이션·업그레이드 | 새 DB가 복제로 따라잡은 뒤 전환 | 논리 복제가 필요함 (물리 복제는 버전 종속). RDS Blue/Green 배포가 이 원리 |
| 백업 부하 분산 | 복제본에서 백업 수행 | **복제는 백업이 아님.** 잘못된 `DELETE`도 그대로 복제되므로 지연 복제본이나 시점 복구(PITR)를 병행함 |

> [!NOTE]
> **PITR(Point-In-Time Recovery)**: 백업과 로그를 이용해 특정 시점의 상태로 데이터베이스를 복원하는 기능

## 8. 정리: 실무의 귀결

대부분의 서비스는 **단일 리더 + 비동기식(또는 반동기식) + 읽기 복제본 + 관리형 자동 장애 복구**로 귀결된다.

- 쓰기 충돌이 없어 애플리케이션 로직이 단순함
- 읽기 위주 서비스는 읽기 복제본만으로 충분히 확장됨
- RDS, Aurora 같은 관리형 서비스가 장애 복구의 어려운 부분을 대신 처리함
- 복제 지연은 쓰기 직후 읽기만 리더로 보내는 국소 처리로 감당 가능함

예외적인 요구사항이 있을 때만 다른 방식을 선택한다.

| 요구사항 | 선택 |
|---|---|
| 글로벌 쓰기 + 강한 일관성 | 합의 기반 분산 SQL (Spanner, CockroachDB) |
| 대량 쓰기 + 높은 가용성 + 최종적 일관성 허용 | 리더 없는 복제 (Cassandra) |
| 오프라인 동작·실시간 협업 | 다중 리더 / CRDT |
